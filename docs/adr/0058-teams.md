# ADR-0058: チーム(利用者の作業単位と代表者)

**Status:** Proposed
**Date:** 2026-11-01

2026-11-01 にユーザーが次のように決めた。

- IP 素材(ADR-0059)を誰に使わせるかを決めるために、利用者をまとめる単位を作る。
- 単位はフラットにする(階層は持たない)。
- 単位には代表者を置き、代表者が自分の単位と担当の IP を管理する。

## Context

認証モードでは、利用者どうしは互いの Run や画像を見られない(ADR-0025)。利用者をまとめる仕組みは、ロールの `user` と `admin` しかない(ADR-0019)。ADR-0006 は「プロジェクト単位の認可」を設計したが、作らないまま ADR-0025 で「本人だけ」に改めた。

他社から預かった版権の素材(ADR-0059)は、許可を受けた人だけが使い、許可の範囲をあとから示せなければならない。人に1人ずつ許可を出すと、異動や増員のたびに許可を出し直すことになり、許可の一覧も読みにくい。作業の実態は「この案件を担当する班」なので、班を単位に許可を出せるようにする。

画像を整理する「グループ」(ADR-0022)が既にあるので、人の単位は「チーム」と呼んで分ける。

## Decision

### 1. 範囲

- **チームは利用者の集まりで、階層を持たない。** 入れ子、部署の階層、チームどうしの親子は作らない。1人が複数のチームに入ってよい。
- **認証モード(`AUTH_MODE=oidc`)のときだけ使う。** 個人モードでは利用者が1人なので、チームの画面を出さない。
- **チームは利用者の分類で、証跡ではない。** 名前の変更、メンバーの出し入れ、チームの削除(論理削除)は自由に行える。ただし、出し入れと削除は証跡(ADR-0059 7章の `audit_event`)に残す。いつ誰がどのチームにいたかは、IP の許可の範囲を示すのに要るため。

### 2. 役割

| 役割 | できること |
|---|---|
| 管理者(`admin`) | チームを作る・名前を変える・消す。代表者を決める。どのチームのメンバーも出し入れできる |
| 代表者 | 自分のチームのメンバーを出し入れする。代表者を足す・外すことはできない(管理者だけ) |
| メンバー | チームに入っていることで、チームに出た許可を受ける。チームの一覧とメンバーを見られる |

- 代表者は、チームのメンバーの中の印(`team_member.role = 'lead'`)で表す。1つのチームに代表者は複数いてよい。
- 代表者は IP の担当にもなれる(ADR-0059 2章)。チームの代表者であることと、IP の担当であることは別に決める。

### 3. データモデル

| 表 | 列 |
|---|---|
| `team` | id、name、description、created_by_user_id、created_at、updated_at、deleted_at |
| `team_member` | team_id、user_id、role(`member` / `lead`)、added_by_user_id、added_at。主キーは (team_id, user_id) |

- メンバーを外したら行を消す。出し入れの経過は `audit_event` に残す。
- チームを消したら、そのチームに出た IP の許可(ADR-0059 4章)は効かなくなる。

### 4. API

`/api/teams`(認証モードでないときは 404)。一覧(`scope=mine` は自分が入っているチーム、`scope=all` は管理者だけ)、作成・名前の変更・削除(管理者)、詳細(管理者とメンバー。それ以外は 404)、メンバーの追加(メールアドレス)・役割の変更(管理者)・外す。

### 5. 利用者の選び方

- メンバーに足せるのは、一度ログインして `app_user` がある人だけ。メールアドレスで探す。
- IdP のグループ(`groups` クレーム)からの同期は、今回は作らない。必要になったら、この ADR に足す。

### 6. 画面

- 管理者設定に「チーム」のページ(`/settings/teams-admin`)を足す。チームの一覧、作成、名前の変更、削除(確認あり)、メンバーと代表者。
- ユーザー設定に「チーム」のページ(`/settings/teams`)を足す。自分が入っているチームとメンバーを見る。代表者はここでメンバーを出し入れする。
- どちらも1つの一覧で、チームの行を押すとその下にメンバーを開く。
- 狭い幅でも一覧と出し入れができること(ADR-0009)。

### 7. ADR-0025 との関係

チームに入っても、メンバーどうしの Run や画像はこれまでどおり見えない。チームが効くのは、IP 素材と、その派生物だけ(ADR-0059 6章)。

## Options Considered

### Option A: 許可を人ごとに出す
**Pros:** 表が1つ減る。
**Cons:** 異動や増員のたびに許可を出し直す。許可の一覧が人の数だけ長くなり、権利者への説明もしにくい。

### Option B: フラットなチーム(採用)
**Pros:** 作業の実態(案件の班)に合う。許可がチームの単位で読める。
**Cons:** 部署の階層で許可を継がせたい組織には、チームを並べて作ってもらう必要がある。

### Option C: 階層のある組織(会社 > 部署 > チーム)
**Pros:** 大きな組織の構造をそのまま写せる。
**Cons:** 許可の継承の規則が要り、範囲の説明が難しくなる。単一組織向けのツールには大きすぎる(ADR-0001)。

### Option D: IdP のグループをそのまま使う
**Pros:** 人の管理が IdP に一本化される。
**Cons:** IdP によってグループの出し方が違い、IdP の管理者に頼まないと班を作れない。後から同期を足せる形にして、今回は見送る。

## Trade-off Analysis

決め手はユーザーの判断で、フラットにする。許可の単位を人ではなくチームにすることで、異動の手間と許可の一覧の読みやすさを両立する。階層と IdP の同期は、必要になったときに足せるよう、許可の判定を「利用者が入っているチームの集合」を返す1つの関数に集める。

## Consequences

- 管理者設定とユーザー設定に「チーム」のページが加わる。
- `team`、`team_member` の表が加わる(マイグレーション)。
- IP の許可(ADR-0059)は、チームか個人に出せる。
- ADR-0006 の「プロジェクト単位の認可」は作らないまま、チームと IP の許可で置き換える(ADR-0006 に注記)。
