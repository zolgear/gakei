# ADR-0036: 派生画像(サムネイル・プレビュー)に版を持たせる

**Status:** Proposed
**Date:** 2026-10-06

## Context

派生画像(長辺 512px のサムネイルと 2048px のプレビュー、WebP。ADR-0004 4章)は、取り込み(`ingest`)のときに1回だけ作り、`derived/{sha256}/thumb.webp` / `preview.webp` に置く(ADR-0026、ADR-0028)。作り方(大きさ、WebP の品質、色の扱い、透過の扱い)を変えても、既存の派生は古いまま残る。作り直す手段はなく、配信のときに派生が無ければ 404 を返す。

ブラウザ側も古いものを持ち続ける。配信の URL(`/api/assets/{id}/content?variant=thumb`)は作り方を変えても同じで、`Cache-Control: private, immutable, max-age=31536000` と `ETag: "{sha256}-{variant}"` を付けているため、ブラウザは問い合わせ直さない。

派生を読むのは配信の API だけではない。埋め込み(`worker/embedder.py`)、自動タイトルとタグ(`worker/annotator.py`)、MCP がエージェントに見せる画像(`domain/agent_images.py`)、共有リンクの配信も読む。

storytold の lightcraft(Apache-2.0 / MIT)は、プレビューのキャッシュのキーに「描画処理の版」を含め、版が変われば古いキャッシュを使わず作り直す。明示的な無効化の処理を持たない(Issue #83)。

## Decision

### 1. 版を決める
- 派生の作り方の版を、`domain/derivatives.py` の定数 `DERIVED_VERSION`(整数)で持つ。作り方を変えたら 1 つ上げる。
- **今ある派生を版 1 とする。** 版 1 のキーは今のまま `derived/{sha256}/thumb.webp` / `preview.webp`。版を入れても、既存のファイルを移したり作り直したりしない。
- 版 2 以降のキーは `derived/{sha256}/thumb.v{N}.webp` / `preview.v{N}.webp`。ローカル FS とオブジェクトストレージで同じキー(ADR-0028)。

### 2. 無ければその場で作る
- 派生を読む口を1つにまとめる(例: `ensure_derived(store, asset, variant)`)。今の版の派生が無ければ、原本から作って保存し、それを返す。配信の API、共有リンク、埋め込み、自動タグ、MCP の画像は、すべてこの口を通す。
- 原本が無い・読めないときだけ 404(今と同じ文言)。
- 同時に2つの要求が同じ派生を作っても、同じ内容を上書きするだけなので、排他はしない。
- 版を上げた直後は、一覧を開くたびに原本のデコードが走って重くなる。前もって作っておきたいときのために、サーバーを止めずに動かせるツール `python -m app.tools.regenerate_derivatives [--dry-run]` を用意する(論理削除済みも含め、今の版の派生が無い Asset について作る)。
- 取り込みのときは、これまでどおり今の版の派生を作る。

### 3. ブラウザのキャッシュ
- 派生の `ETag` に版を含める(`"{sha256}-{variant}-d{N}"`)。
- 画面が作る配信の URL(`frontend/src/api/assetUrl.ts`)の thumb / preview に `dv={N}` を付け、版が変わると URL が変わるようにする。`immutable` はそのまま使える。原本(`original`)には付けない。
- フロントの版はフロントの定数に書き、バックエンドの `DERIVED_VERSION` と一致することをバックエンドのテストで確かめる(同じリポジトリでビルドするため、API で配る必要はない)。サーバーは `dv` を見ない(古い `dv` でも今の版を返す)。

### 4. 古い版の派生
- 古い版の派生は、配信にも処理にも使わない。消さなくても動く。
- 掃除は `regenerate_derivatives` の `--prune` で行う(今の版以外の派生を消す。`--dry-run` で件数だけ見られる)。原本と、今の版の派生には触れない。
- `migrate_storage`(ADR-0028)は `derived/` の下をまとめて移す今の作りのままでよい。

## Options Considered

### A. 版のキー + その場で作る(採用)
**Pros:** 作り方を変えるだけで済み、移行の手順が要らない。派生が欠けていたときも自己修復する(今は 404)。
**Cons:** 版を上げた直後に負荷が出る(ツールで前もって作れる)。

### B. 版を持たず、作り方を変えたらツールで全部上書きする
**Pros:** キーが変わらない。
**Cons:** ツールを動かすまで古い派生と新しい派生が混ざる。URL が変わらないので、ブラウザの `immutable` のキャッシュを破れない(`immutable` をやめると、一覧の表示のたびに問い合わせが増える)。

### C. 派生を保存せず、毎回作る
**Cons:** 4K の原本のデコードが表示のたびに走る。Raspberry Pi などで重すぎる。

## Trade-off Analysis

作り方を変える頻度は低いが、変えたときに既存の画像が古いまま残る・ブラウザが更新されない、という問題は利用者には直せない。A は版 1 を今のキーのまま扱うので、入れた時点では何も移らず、版を上げたときだけ働く。

## Consequences

- 派生を読む箇所は `ensure_derived` を通すことになる。新しく派生を読む処理を足すときもこれを使う。
- 派生が欠けていても、原本があれば表示できるようになる。
- 埋め込みと知覚ハッシュ(ADR-0033)はサムネイルから計算している。版を上げると、既存のベクトルとハッシュは古い版のサムネイルから作ったままになる。版を上げるときは、作り直し(埋め込みの再計算、知覚ハッシュの作り直し)が要るかをあわせて決める。
- フロントの配信 URL に `dv` が付く。`dragDropAssets.ts` の URL の判定(`/content` までを見る)は影響を受けない。
