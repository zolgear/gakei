# ADR-0044: 画像の埋め込みのモデルに EmbeddingGemma 2 を加える

**Status:** Proposed
**Date:** 2026-10-11

## Context

画像の埋め込み(ADR-0033)は、ローカルの ONNX で CLIP 系の3つ(`clip-vit-b32-u8`、`clip-vit-b32`、`clip-japanese-base`)から管理者が1つを選ぶ。CLIP 系には次の弱点がある。

- 文章は 77 トークンで切れる。GAKEI のプロンプトは長いものが多い(実データで中央値 285 字)。
- 英語の CLIP は日本語に弱い。日本語の CLIP(LY)は英語に弱い。言語に合わせて使い分けが要る。

2026-10-06 に Google DeepMind が EmbeddingGemma 2(`google/embeddinggemma-2`、Apache-2.0)を公開した。テキスト・画像などを同じ 768 次元の空間に埋め込むモデルで、100 以上の言語に対応し、文章は 8,192 トークンまで扱える。MRL で 512 / 256 / 128 次元に切り詰められる。`onnx-community/embeddinggemma-2-ONNX` に、画像側と文章側を分けた ONNX(fp32、q8、q4 など)がある。

Issue #99 で、GAKEI の実データ(Run 153 件、画像 171 枚)を使って比べた。

- **検索の質:** 文章で画像を探したときの R@1 は、EG2 が 0.451、CLIP ViT-B/32 が 0.170、LY が 0.209。日本語・英語・77 トークン超のどの区分でも EG2 が上回った。
- **CPU での動作(ONNX、x86 の 8 コア、4 スレッド):** q8 の精度は PyTorch(BF16)とほぼ同じ(画像の cos 平均 0.999)。ただし画像は1枚約 3.2 秒で、今の CLIP(61〜133ms)の数十倍かかる。計算中のメモリは画像1枚で約 0.7GB。文章はトークン数とともに急に増え、1,024 トークンで約 0.5GB、4,168 トークンで約 2.3GB。
- **依存:** トークナイザー(sentencepiece)と画像の前処理(numpy、Pillow)は、torch・transformers なしで書ける。新しい依存は要らない。

2026-10-11 にユーザーが「CLIP は軽い既定のまま残し、EmbeddingGemma 2 を選べるモデルの候補として足す」と決めた(時代に合わせて選択肢を増やす)。

## Decision

### 1. 範囲

- ローカルの ONNX のモデルの候補に `embeddinggemma-2-q8` を加える。既定は今の `clip-vit-b32-u8` のまま。
- ADR-0033 の作りはそのまま使う: 使うモデルは管理者が1つ選ぶ。ベクトルは `model_key` ごとに保存する。文章での検索、似た画像、重複の候補、マップは、選んだモデルのベクトルを使う。
- 次は今回作らない。
  - CLIP と EG2 の併用と、2つの検索結果の統合(RRF など)。EG2 は検証したすべての区分で CLIP 系を上回ったので、1つ選ぶ形で足りる。
  - 画像と文章をまとめた入力(interleaved)。検証で、「親画像+Edit の指示」のベクトルは子より親に近く、編集後を予想する使い方は成り立たなかった。
  - 系列の親子の変化量や、プロンプトと画像の一致を、スコアとして保存・表示すること。指示の反映度の自動判定は、ADR-0001 の非ゴール「自動品質採点」のまま。
  - 音声・動画の埋め込み。
  - プロンプトのベクトル。Run のプロンプト(指示)を埋め込んで探す機能は ADR-0045 で決める。
  - リモート(推論サーバー)での EG2。Infinity は画像を CLIP / SigLIP 系でしか扱わず、EG2 の画像は埋め込めない(2026-10 時点)。対応する推論サーバーが出てから、ADR-0033 のリモートの形式として検討する。

### 2. モデル

| モデル | 取得元 | サイズ | 言語 | ライセンス |
|---|---|---|---|---|
| `embeddinggemma-2-q8` | `onnx-community/embeddinggemma-2-ONNX` の画像側 q8 と文章側 q8(`.onnx` と `.onnx_data`)、`tokenizer.model` | 約 0.5GB | 多言語(日本語・英語を含む) | Apache-2.0 |

- リビジョンを固定し、ファイルごとのハッシュを確かめる(ADR-0033 2章と同じ)。リビジョンは検証で使った `daa72c51243991dfcaf9f9137d2c573d8f7790c0` から始める。
- 型は画像側・文章側とも q8 にする。
  - 画像は q8 がいちばん速かった(fp32 の約 0.6 倍の時間)。
  - fp32 は精度がわずかに高いが、ダウンロードが約 1.7GB、画像の計算中のメモリが約 2 倍になる。
  - q4 は速くも小さくもなく、精度だけが落ちた(cos 平均 0.986)。
  - fp16 は使わない(EG2 は fp16 で NaN になるという報告がある)。
- 次元は 768 のまま使う。256 に切り詰めても検索の質はほとんど落ちなかったが、ベクトルは1枚 3KB で、保存と検索の負担は小さい。

### 3. 計算の流れ

- **画像:** 画像側(`vision_encoder`)が、ソフトトークンごとの特徴を返す。その特徴を、画像のトークン列(`<bos>`、画像の開始、画像のトークン × ソフトトークン数、画像の終わり、`<eos>`)と一緒に、文章側(`model`)へ渡す。文章側の出力 `sentence_embedding` が 768 次元のベクトルになる。
  - **画像の埋め込みにも文章側が要る。** ADR-0033 2章の「画像の索引付けでは画像側だけ読み込む」は、このモデルでは成り立たない。画像を計算するときは両方を読み込む。文章での検索だけのときは、今までどおり文章側だけを読み込む。
- **文章:** sentencepiece(`tokenizer.model`)で分割し、前に `<bos>`、後ろに `<eos>` を付ける。
  - 検索の文章には、クエリのタスクのプレフィックス(`SearchQuery`)を付ける。実際の文字列はモデルの設定から取り、カタログの定数に置く。画像にはプレフィックスを付けない。
  - 文章は 1,024 トークンで切る(`<bos>` と `<eos>` を含めて数え、切った後も末尾に `<eos>` を残す。transformers の切り方と同じ)。長い文章では計算中のメモリが急に増えるため。
    - 計算中のメモリのピーク(q8、4 スレッド、文章側だけ): 512 トークンで約 370MiB、1,024 で約 520MiB、2,048 で約 940MiB、4,168 で約 2.3GB。
    - 1,024 なら、画像の計算(約 0.72GB)より小さく収まる。検索の文章としては十分な長さで、CLIP の 77 トークンよりずっと長い。
  - GAKEI が文章を埋め込むのは、文章での検索の文章だけ(ADR-0033 6章)。プロンプトは埋め込まない(画像のベクトルは画素だけから計算する)。上限が効くのは、長いプロンプトを貼り付けて検索したときだけで、1,024 トークンより後ろは検索に効かない。
  - 画像の計算で文章側に渡すトークン列(画像1枚あたり約 260〜280 トークンと特殊トークン)には、この上限を掛けない。
- **後処理:** プーリング、512→768 次元の射影、L2 正規化は ONNX の中にある。GAKEI は何もしない。
- **使わない入力:** 動画・音声の入力も必須なので、空の配列(`[0, 512]`)を渡す。
- **入力名:** ONNX の入力名は transformers の processor のキー名と違うところがある(`pixel_position_ids` など)。カタログかエンジンの定数に置く。
- **画像の前処理:** 縦横比を保ってリサイズし、パッチに分け、位置の ID を作る。transformers の processor の処理を numpy と Pillow で書き直す。リサイズは Pillow の bicubic にする(transformers は torchvision を使う)。検証では、画素値の差は 1/255 刻みで 2 段まで、埋め込みの cos は最小 0.9994 で、q8 の量子化の誤差より小さかった。
  - 透明な部分は、ほかのモデルと同じく白で合成してから RGB にする(ADR-0033 2章)。
- **まとめる件数:** 画像も文章も1件ずつ計算する。q8 は動的量子化で、まとめて計算する件数によって値が変わるため(ADR-0033 2章の、量子化したモデルの規則と同じ)。

### 4. メモリと読み込み

- ONNX のセッションの作り方、WD Tagger と同時に読み込まないこと、使わなければ解放することは、ADR-0033 2章と同じ。
- メモリの目安(読み込む前に空きメモリと比べる値)は、検証の実測から決める。
  - 画像を計算するとき(画像側+文章側): 約 0.75GB。
  - 文章だけのとき: 約 0.55GB(1,024 トークンで約 520MiB の実測から)。
  - 重みは `.onnx_data` から mmap で読むので、読み込み直後の RSS は小さい。目安は計算中のピークで決める。

### 5. 重複のしきい値

- EG2 の類似度は、CLIP より全体に高く出る(無関係な文章どうしでも約 0.7)。重複の候補のしきい値(ADR-0033 12章。CLIP の既定は 0.90)は、そのままでは使えない。
- しきい値の既定は、モデルごとにカタログに持つ。管理者が変えた値は、モデルごとに保存する。モデルを切り替えると、そのモデルの値を使う。
- EG2 の既定は、ADR-0033 12章と同じ画像の組(劣化と色違い)で実装時に決め、テストに残す。知覚ハッシュの併用はそのまま。

### 6. 画面

- 埋め込みの設定のモデルの一覧に `embeddinggemma-2-q8` を加える。サイズ、対応言語、ライセンスは、ほかのモデルと同じく出す。
- このモデルの説明に、検索の質が高い代わりに計算が重いこと(CLIP の数十倍)を一言で出す。目安の時間などの詳しい数値は `docs/embeddings.md` に書く。
- EG2 は多言語なので、英語専用のモデルのときに出す「日本語ではほとんど当たらない」という注意は出さない。

## Options Considered

### どう入れるか

| 案 | 内容 | 評価 |
|---|---|---|
| A. 選べるモデルの候補として足す(採用) | 既定は CLIP のまま。管理者が選べば EG2 を使う | ADR-0033 の作りに収まる。軽い環境では今までどおり |
| B. 既定を EG2 に替える | 新しく埋め込みを有効にした環境は EG2 になる | 検索の質は高いが、CPU だけの環境で画像1枚 3 秒かかり、取り込みのたびに重い |
| C. CLIP と EG2 を併用し、結果を統合する | 両方のベクトルを持ち、RRF などで混ぜる | EG2 がすべての区分で上回ったので、混ぜる理由が無い。計算と保存が2倍になる |

### 型

| 案 | 画像1枚(4 スレッド) | 画像の計算中のメモリ | ダウンロード | 精度(画像の cos 平均) |
|---|---|---|---|---|
| q8 / q8(採用) | 3.2 秒 | 約 0.72GB | 約 0.5GB | 0.9990 |
| fp32 / fp32 | 5.4 秒 | 約 1.48GB | 約 1.7GB | 0.9999 |
| q8 / fp32 | 5.5 秒 | 約 1.07GB | 約 1.2GB | 0.9991 |
| q4 / q4 | 5.8 秒 | 約 0.58GB | 約 0.3GB | 0.9857 |

q8 / fp32 にすると、短い検索の文章は 229ms から 107ms に速くなる。ただし、画像の計算が遅くなり、ダウンロードも増える。検索の文章が 0.2 秒台なら操作の妨げにならないので、q8 / q8 にした。

### 次元

| 案 | 評価 |
|---|---|
| 768(採用) | 検索の質がいちばん高い。保存と検索の負担は小さい |
| 256 | R@1 はわずかに下がるだけ(0.451 → 0.425)。保存は 3 分の 1 になるが、今の規模では差が小さい |

## Trade-off Analysis

検索の質と計算の重さの交換になる。EG2 は、今の CLIP 系の2つの弱点(日本語と長いプロンプト)をどちらも解消し、言語に合わせたモデルの使い分けも要らなくなる。代わりに、画像の計算は CPU で CLIP の数十倍かかる。2〜4 vCPU の VM で 1,000 枚をまとめて計算すると、1時間ほどかかる見込み。

既定を CLIP のままにし、EG2 を管理者が選ぶ候補にしたので、軽さを優先する環境は今までどおり使える。検索の質を優先する環境は、EG2 を選び、既存の画像を一括で計算し直せばよい。ADR-0033 がモデルごとにベクトルを保存するので、CLIP に戻しても計算し直しは要らない。

## Consequences

- ローカルの ONNX エンジンに、EG2 の型(family)が加わる。画像側の出力を文章側に渡す、2段の計算になる。
- 画像を計算するとき、このモデルでは画像側と文章側を両方読み込む(ADR-0033 2章の例外)。
- 重複のしきい値が、モデルごとの値になる。既存の設定の値は、今使っているモデルの値として引き継ぐ。
- 検索の文章のトークン数に上限ができる(このモデルでは 1,024)。画像のベクトルには影響しない。
- 新しい依存は要らない(sentencepiece は既にある)。
- ADR-0033 2章のモデルの表に、このモデルを指す行を足す。

## Action Items

1. ADR-0033 2章のモデルの表に `embeddinggemma-2-q8` の行と、この ADR への参照を足す。
2. カタログ(`backend/app/embedding/catalog.py`)にモデルを加える(ファイル、ハッシュ、サイズ、メモリの目安、プレフィックスの文字列、入力名)。
3. トークナイザー(sentencepiece + `<bos>` / `<eos>`)と画像の前処理を書き、検証のスクリプトと同じ値になることをテストで確かめる。
4. ONNX エンジンに、EG2 の2段の計算と、文章の 1,024 トークンの上限を加える。
5. メモリの目安が、GAKEI のエンジンでも実測と合うかを確かめる。
6. 重複のしきい値をモデルごとにし、EG2 の既定を決める。
7. 設定画面のモデルの一覧と説明、`docs/embeddings.md`、文言(ja / en)を更新する。
8. 実際に EG2 で既存の画像を一括で計算し、文章での検索、似た画像、重複の候補、マップを確かめる。
