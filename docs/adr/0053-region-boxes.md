# ADR-0053: 領域の指示(入力画像に四角を描き、四角ごとに指示を書く。四角の検出は VLM とローカルのモデル)

**Status:** Proposed
**Date:** 2026-10-20

2026-10-20 に、ユーザーが次のように指示した。

- 入力画像の上に四角(バウンディングボックス)を描き、四角ごとに指示を書く機能を作る。
- 四角の指示を学習した画像生成モデルが出てきている。API に専用の項目が無くても、指示の形が決まっていれば、ほかのモデルにも同じ画面とデータで使える。
- 四角の検出は、VLM を使うものと、ローカルの軽いモデルを使うものの2通りを用意する。ローカルのモデルは、イラストに強いものから入れる。

同日、ユーザーが渡し方の最初の範囲(ComfyUI への差し込みと、OpenAI への画像と文)を承認した。

## Context

- 2026-10 に、四角での指示を受けるモデルが続けて出た。どれも渡し方が違う。
  - **FLUX 3 Image(API)と FLUX.3 Image Klein(重みを公開):** プロンプトの文の後ろに、四角の JSON の配列を付ける。四角は `[上, 左, 下, 右]` で 0〜1000 に正規化する。要素ごとに、元の画像のどこにあるか(`src_bbox`)とどこに置くか(`tgt_bbox`)を持つ。これで移動、置き換え、足す、消す、そのまま残す(アンカー)を表す。四角は配置と大きさの目安で、マスクのような厳密な範囲ではない。
  - **MOSS-Image(重みを公開、Apache-2.0):** プロンプトを JSON にし、要素ごとに種類・説明・描く文字・四角を持つ。四角は画面の中心を原点にしたピクセルの `[y0, x0, y1, x1]`。生成のみで、入力画像を受ける編集はできない。
  - **Krea 3(API、ベータ):** 局所の編集(`regional_edit`)はあるが、四角を渡す項目は公開されていない。
  - **ComfyUI:** 本体に、四角を描くノード(Create Bounding Boxes)が入った。出力は、ピクセルの四角の一覧(`BOUNDING_BOXES`)、説明文の配列、プレビューの画像。外から四角を受ける入力(`bboxes`)もある。モデルごとの形には、別の変換ノード(FLUX.3 Layout Prompt、MOSS-Image Layout Prompt、Ideogram の JSON)で直す。
- 共通に使えるのは、四角と指示のデータと、それを描く画面である。モデルへの渡し方は、モデルごとに変換する必要がある。ComfyUI もこの作りになっている。
- 今の GAKEI は、場所の指示をマスク(ADR-0004 の Edit の入力)とスケッチ(ADR-0010)と配置(ADR-0050)で伝える。四角ごとに別々の指示を付ける手段は無い。
- OpenAI の画像の API は、四角を受ける項目を持たない。番号付きの四角を描いた画像と、番号を使った文の指示で伝えることはできる(効き方はモデル任せ)。
- 画像を見て物の位置を答える処理は、今の GAKEI には無い。サムネイルの焦点(ADR-0043)は顔の検出の中心だけを使い、四角は捨てている。モデルも OpenCV のカスケードで、一般の物は見つけられない。

## Decision

### 1. 範囲

画面の名前は「領域」(英語は Regions)。マスク・スケッチ・配置と並ぶ、入力画像に付ける道具の1つにする。

- 生成のフォームの入力の1枚目(主たる入力)の上に、四角を描く。最大 16 個。
- 四角ごとに番号と色のバッジを付ける。画像の下(狭い幅では下の一覧)に、四角ごとの札を出す。
- 札で決めること:
  - **種類:** 変える(既定)/足す/そのまま残す/消す/動かす。
  - **指示:** その四角で何をするかの文。
  - **描く文字:** 看板などに描かせる文字(任意。指示とは分け、そのまま渡す)。
  - **参照画像:** その四角に使う画像(任意。ストックか入力から選ぶ)。参照画像は Run の入力(`role = reference`)にもなる。
- 「動かす」の四角は、元の位置と移す先の2つの四角を持つ。
- 四角の移動、大きさの変更、削除、番号の並べ替え、元に戻す・やり直す。
- 四角は画像の座標で持つので、画像を拡大しても位置はずれない。
- 狭い幅(ADR-0009)では、タッチで四角を描き、動かせること。
- 全体の指示(今のプロンプト)はそのまま使う。四角の指示は、全体の指示に足す形で渡す。

### 2. 作らないもの

四角以外の形(多角形、自由な線、楕円)、四角の回転、四角の中だけのマスクの生成、四角を絵として描くこと(四角は指示であって、画像の編集ではない)。形の細かい指定はマスクとスケッチで行う。

### 3. データ(どのモデルにも依らない形)

- 四角の座標は、主たる入力の画像に対する割合(0〜1)で、左上を原点にした `[x0, y0, x1, y1]` にする。モデルごとの形(0〜1000、中心を原点にしたピクセル、yx の順など)には、渡すときに変換する。
- 1つの四角は次の値を持つ: 番号、種類、四角(「動かす」では移す先)、元の四角(「動かす」だけ)、指示、描く文字、参照画像の Asset id。
- Run を作る要求(`RunCreateRequest`)に `regions` を足す。サーバーは、四角の数、座標の範囲、文字の長さ、参照画像が見える範囲にあるか(ADR-0025)を確かめる。

### 4. 記録(ADR-0003 に足す)

- **`run.regions`(JSON の列。追記のみ):** 利用者が付けた四角(3章の形)と、どの渡し方で送ったか(5章)と、変換の版。証跡なので、Run を作った後は変えない。再実行やパラメーターの読み込みでは、ここから四角を戻す。
- **`run.params`:** 今までどおり、API に送った値そのもの(ADR-0003 4項)。四角を文に変えて送ったなら、その文を含んだプロンプトが入る。ComfyUI なら、差し込んだ四角の値が入る。
- **四角を描いた画像(5章の「画像と文」):** サーバーが描く。新しい Asset の種類 `regions` として保存し、Run の入力(`role = reference`)にする。主たる入力の Asset を `source_asset_id` で指す(スケッチと同じ)。ストックには既定で出さない(ADR-0035。スケッチ・マスク・配置と同じ設定の対象にする)。
- 四角の検出の結果(7章)は保存しない。保存するのは、利用者が使うと決めた四角だけで、それも Run の記録としてだけ残す。

### 5. モデルへの渡し方

プロバイダーは `capabilities()` で、四角を受けられるかと、その渡し方を答える。受けられないプロバイダーでは、フォームに「領域」を出さない(ADR-0005 と同じく、フォームは `capabilities()` から組み立てる)。

| 渡し方 | 使う先 | 中身 |
|---|---|---|
| **ComfyUI に差し込む** | 四角の差し込み先を持つワークフロー(6章) | Create Bounding Boxes の `bboxes` 入力に、ピクセルの四角の一覧を差し込む。モデルごとの形への変換は、ワークフローの中の変換ノードに任せる |
| **画像と文** | OpenAI の Edit | 番号と色の付いた四角を描いた画像を参照として足し、プロンプトの後ろに番号ごとの指示を文で足す。四角を学習していないモデル向けの、効き方の保証が無い渡し方 |
| **モデルの形で渡す** | 四角の形を公開しているプロバイダー | 各モデルの公開の形に変換する(FLUX 3 ならプロンプトの後ろの JSON)。プロバイダーごとの ADR で決める |

- 最初に作るのは、**ComfyUI に差し込む**と、OpenAI への**画像と文**の2つ。
- FLUX 3 や Krea 3 などの新しいプロバイダーは、この ADR では足さない。ADR-0001 の「他プロバイダー対応」を改める ADR を別に起こしてから足す。その ADR で「モデルの形で渡す」の変換を決める。
- 「画像と文」で足す文は、利用者の言語に合わせて文言の JSON(ADR-0015)に置く。足した文は `run.params` のプロンプトに入るので、何を送ったかは Run から分かる。
- 「そのまま残す」の四角は、モデルの形が対応していればアンカーとして渡す。「画像と文」では、文で「変えない」と伝える。

### 6. ComfyUI(ADR-0052 に足す)

- 差し込み先の種類に `bounding_boxes` を足す。差し込む先は Create Bounding Boxes の `bboxes` 入力。
- ワークフローの読み取り(ADR-0052 の規則)で、Create Bounding Boxes のノードを見つけたら、差し込み先の候補にする。
- 差し込む値は、主たる入力の画像の大きさで割合をピクセルに直した四角と、指示・描く文字(ノードの metadata の形に合わせる)。
- 正確な値の形は、実装のときに ComfyUI の本体のコードで確かめ、`docs/comfyui.md` に書く。ノードの形が変わったら、差し込みを止めて分かるように失敗させる(黙って違う形で送らない)。
- 差し込み先を持たないワークフローでは、フォームに「領域」を出さない。

### 7. 四角の検出

四角を自動で出す。出した四角は候補で、利用者が選んで札に指示を書いてから使う。検出は2通りで、管理者設定でどちらを使えるかを決める(両方使える)。

**VLM で検出する**
- LLM の接続先(ADR-0032)から、画像を受けられる接続を1つ選ぶ。使う側として `register_usage` で登録する(使用中の接続を消せないようにする)。
- 言葉で探せる(「カップ」「左の人の服」など)。言葉が無ければ、主な物を一通り挙げさせる。
- 応答は JSON のスキーマで受ける(生成のアシスタントの構造化出力と同じ作り)。座標はモデルに 0〜1000 で答えさせ、3章の形に直す。範囲外の値と、空の四角は捨てる。
- 外部の AI へ送る前の入口(ADR-0051)に、用途 `region_detection` を足す。接続先がローカル(ADR-0051 の接続先の区分)でも同じ入口を通す。

**ローカルのモデルで検出する**
- ONNX の物体の検出のモデルを、WD Tagger と同じダウンローダーと置き場(`model_store`)で扱う。リビジョンと sha256 を固定し、管理者設定でダウンロードする。同時に載せるモデルを抑える仕組み(`residency`)に、使う側を1つ足す。
- CPU で動き、仮想マシンの CPU で数秒以内に答えられる大きさにする。使う前に空きメモリを確かめる(WD Tagger と同じ)。
- **イラストに強い検出器から入れる**(2026-10-20 のユーザーの指示)。生成画像はイラストが多く、写真で学習した検出器(COCO の 80 種類)では見落としが多いため。写真向けの検出器は、必要になったら後から足す。
- **使うモデル(2026-10-20 にユーザーが選んだ):** deepghs のイラスト向けの検出モデルの、人物(`anime_person_detection`)・顔(`anime_face_detection`)・頭(`anime_head_detection`)。どれも1種類だけを見つける別々のモデルで、軽い版(n か s。ONNX で 12〜45MB 程度)を使う。版(どのサブフォルダのモデルか)とリビジョンは、実装のときに精度(モデルカードの F1)と速さを見て決め、この ADR に書き足す。推論は onnxruntime だけで行い、学習の仕組みのコードは使わない。
- **ライセンスの扱い:** Hugging Face の表記は MIT。ただし、モデルの大きさと学習の結果のファイル名から、Ultralytics の YOLOv8 で学習したものとみられる。Ultralytics は、自分の仕組みで学習したモデルにも AGPL-3.0 が及ぶという立場を取っている。学習済みの重みにこの主張が及ぶかは定まっていない。そこで次のようにする。
  - GAKEI のリポジトリにも Docker イメージにも同梱しない。管理者が管理者設定でダウンロードしたときだけ取得する(既定はダウンロードしない)。
  - ダウンロードの前に、Hugging Face の表記と、Ultralytics の主張があることを示し、管理者が同意してから取得する。
  - docs と第三者ライセンス表記に、同じことを書く。
  - ライセンスの緩い仕組み(Apache-2.0 の RF-DETR など)で学習したイラスト向けの重みが出てきたら、差し替えを検討する。
- それ以外のモデルでも、ライセンスは商用でも使えるもの(Apache-2.0 か MIT)を原則とする。GPL・AGPL を明示したもの(文字の検出の `AnimeText_yolo`、YOLO-World、YOLOE など)と、学習データが学術利用に限られるもの(Manga109 で学習したものなど)は使わない。
- 言葉で探すことはしない(決まった種類だけを見つける)。言葉で探すのは VLM の役割にする。
- 第三者ライセンス表記(ADR-0021)に、モデルのライセンスを足す。

**共通**
- API は `POST /api/assets/{id}/regions/detect`(`require_user`。見える Asset だけ)。入力は検出の方法と、任意の言葉。応答は候補の四角の一覧(四角、名前、確からしさ)。
- 検出は同期の要求で答える(時間がかかるときは、画面で待っていることを示す)。結果は保存しない。
- `FAKE_PROVIDER=1` では、ダミーの検出(決まった位置の四角を返す)にする。

### 8. ほかの機能での扱い

- **再実行・パラメーターセット(ADR-0040):** 再実行では `run.regions` から四角を戻す。パラメーターセットには四角を入れない(四角は画像ごとのもの)。
- **MCP(ADR-0023):** Run を作るツールに `regions` を足す(REST と同じドメイン関数を通す)。検出のツールも足す。どちらも後の段でよい。
- **系列(ADR-0003)と系列の ZIP(ADR-0037):** `run.regions` は Run の記録として持ち出す。種類 `regions` の Asset は、スケッチと同じ扱いで系列に入れる。
- **Mod(ADR-0051):** `ai.before_send` の `subject` に、四角の数と指示(テキスト)を入れる(外へ送る中身なので、検査の対象にする)。

### 9. ADR-0001 の扱い

- 非ゴール「高機能な画像編集」の但し書きに、「領域の指示の四角(ADR-0053)」を足す。四角は指示の範囲で、画像に描く図形ツールではない。
- 非ゴール「承認ワークフロー、コメント」に、四角の指示は人どうしのコメントではない(Run の入力の指示である)ことを注記する。

## Options Considered

| 案 | 判断 |
|---|---|
| A: どのモデルにも依らない四角のデータを持ち、渡すときにモデルごとに変換する | 採用。ComfyUI と同じ作り。新しいモデルには変換を足すだけでよい |
| B: 特定のモデルの形(FLUX 3 の 0〜1000 など)をそのまま持つ | 簡単だが、ほかのモデルに渡すときに形の間で変換することになり、元の値が分からなくなる |
| C: 四角をマスクに変えて渡す | 既存の Edit の入力で送れるが、四角ごとの指示を表せない |
| D: 四角を `run.params` だけに入れる | ADR-0003 4項に反する(API に送らない値を入れることになる)。ComfyUI と「画像と文」では、送る値と利用者が付けた四角が別の形になる |
| E: 四角を描いた画像をブラウザで作る(スケッチと同じ) | MCP と再実行で同じ画像を作れない。描くのはサーバーにする |
| F: 検出をローカルのモデルだけにする | 言葉で探せない。VLM なら言葉で探せるが、外へ送る。両方を用意して、管理者が選べるようにする |
| G: ローカルの検出に、写真向けの検出器(COCO の 80 種類。RT-DETR、D-FINE、RF-DETR など)を使う | ライセンスは緩いが、イラストでは見落としが多い。イラスト向けの配布済みの重みは見つからなかった |
| H: RF-DETR(Apache-2.0)をイラストで学習し直して配る | ライセンスの心配は最も小さいが、学習データの用意(権利の確認と注釈)に時間がかかる。ADR-0001 はモデルの学習を非ゴールにしている(GAKEI の機能としての学習ではないが、配る重みを作るのは開発の範囲を超える) |
| I: 言葉で探せるローカルのモデル(Florence-2 など)を使う | 重く、CPU で数秒以内に答えるのが難しい。言葉で探すのは VLM に任せる。軽いものが出れば、この ADR を改めて足す |

## Trade-off Analysis

- 「画像と文」は、四角を学習していないモデルに伝える苦肉の策で、効き方は保証しない。docs に、効きやすい書き方と、効かないことがあることを書く。画面では、この渡し方であることを示す。
- 四角の検出を保存しないので、同じ画像で何度も検出すると、そのたびに計算する(VLM なら費用がかかる)。検出は四角を付けるときの下書きで、使う頻度は低いと見て、保存の仕組みを作らない。
- ComfyUI の Create Bounding Boxes は本体に入って日が浅く、値の形が変わることがある。差し込みの形を1か所に閉じ込め、形が変わったら分かるように失敗させる。

## Consequences

- Run に列が1つ増える(`run.regions`。マイグレーション)。Asset の種類が1つ増える(`regions`)。種類を列挙している場所を直す。
- ADR-0051 の用途が1つ増える(`region_detection`)。Mod の契約の版を上げる。
- ローカルの検出のモデルの分だけ、ダウンロードとメモリが増える(管理者が使うと決めたときだけ)。
- 新しいプロバイダー(FLUX 3 など)を足すときに、四角の渡し方を変換として足せばよい。
