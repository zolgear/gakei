# ADR-0045: プロンプト(指示)の埋め込みで、Run を指示の意味で探す

**Status:** Proposed
**Date:** 2026-10-11

## Context

画像の埋め込み(ADR-0033)で保存しているのは、画像のベクトルだけである。文章での検索は、検索の文章と画像のベクトルを比べる。そのため、画像に写っているものでしか探せない。

Edit の指示には、出来上がった画像には残らない内容が多い。「背景の人物を消す」「髪を赤に変える」「文字を削除」などの指示を出したことは、子の画像だけを見ても分からない。「何を指示したか」で Run を探したいとき、画像のベクトルでは代わりにならない。

今のキーワード検索(`GET /api/search`)は、Run のプロンプトの文字列で探せる。ただし、言い回しや言語が違うと当たらない(「消す」と「削除」、「remove」など)。

EmbeddingGemma 2(ADR-0044)は、文章を 8,192 トークンまで多言語で扱え、画像と同じ空間で文章どうしも比べられる。CLIP 系は 77 トークンで切れるため、長いプロンプトや指示文には向かなかった。

2026-10-11 にユーザーが、プロンプトのベクトルを画像とは別に保存し、文章での検索をプロンプトに当てられるようにしたいと決めた。長いプロンプトを切り捨てる前に、タイトル(ADR-0024)を要約として先頭に付けて、意味の損失を減らす案もユーザーが出した。

## Decision

### 1. 範囲

- Run のプロンプトの埋め込みを、画像の埋め込みとは別に保存する。
- 文章での検索の API で、探す対象を「画像」と「指示(プロンプト)」から切り替えられるようにする。画面は埋め込みの状況だけにする(6章)。
- 対象は、出力のある Run(Generate と Edit)。失敗・中止の Run と、削除済みの Run は対象外。
- 対象のモデルは、長い文章を扱えるモデル(今は `embeddinggemma-2-q8`)だけ。カタログにモデルごとの可否を持つ。CLIP 系を選んでいるときは、この機能を出さない。
- 埋め込みは証跡ではない。来歴の列(`run`、`run_input`、`asset`)には書かない(ADR-0033 1章と同じ)。
- 次は今回作らない。
  - 似たプロンプトの Run を並べる(Run 詳細から)、プロンプトのマップ。保存したベクトルで後から作れるので、要望があれば足す。
  - 画像の検索とプロンプトの検索の結果を混ぜる順位づけ(RRF など。ADR-0044 1章)。
  - プロンプトと画像のずれのスコア(ADR-0001 の非ゴール「自動品質採点」)。
  - アップロード画像の埋め込みメタ情報のプロンプト(ADR-0018)。Run が無いので、要望があれば別に考える。
  - MCP のツール(ADR-0023)への追加。

### 2. 埋め込む文章

- プロンプトは、ワイルドカードを展開した最終のプロンプト(`text_outputs` の `final_prompt`)があればそれを、無ければ `run.prompt` を使う。ネガティブプロンプトは使わない。
- 文書のタスクのプレフィックス(`Document`)を付ける。検索の文章には、今までどおりクエリのプレフィックス(`SearchQuery`)を付ける(ADR-0044 3章)。
- **長さの上限:** 検索の文章と同じ 1,024 トークンで切る(ADR-0044 3章。数え方も同じ)。計算中のメモリは約 520MiB で、画像の計算(約 0.72GB)より小さい。
  - 実データのプロンプトは最長で約 4,200 トークンあった。上限を超えるのは一部の長いプロンプトだけ。
- **タイトルを要約として先頭に付ける:** プロンプトが上限を超えるときだけ、その Run のタイトルを先頭に付けてから切る(`{タイトル}\n{プロンプト}`)。後ろが切れても、タイトルが全体の意味を補う。
  - タイトルは、Run の最初の出力(`output_index = 0`)の Asset のタイトル(ADR-0024)。自動で付いたものも、人が編集したものも使う。
  - 上限に収まるプロンプトには付けない(付けると、短いプロンプトの意味が薄まるため)。
  - タイトルがまだ無い(自動のタイトルが待ち行列にある、無効)ときは、タイトル無しで埋め込む。後からタイトルが付いたり変わったりしたら、上限を超えるプロンプトの Run だけ埋め込み直す。
- 埋め込んだ文章の sha256 を行に保存する。タイトルが変わったときに、埋め込み直しが要るかをこれで判断する。

### 3. 保存

```sql
run_prompt_embedding (
  run_id UUID NOT NULL REFERENCES run(id),
  model_key VARCHAR(200) NOT NULL,
  status VARCHAR(16) NOT NULL,      -- queued / running / succeeded / failed
  dim INTEGER NULL,
  vector BLOB NULL,                 -- float32、L2 正規化済み
  text_sha256 VARCHAR(64) NULL,     -- 埋め込んだ文章(タイトル込み)の sha256
  truncated BOOLEAN NOT NULL DEFAULT FALSE,
  error TEXT NULL,
  updated_at TIMESTAMP NOT NULL,
  PRIMARY KEY (run_id, model_key)
)
INDEX (model_key, status)
```

- 作りは `asset_embedding` と同じにする(ADR-0033 4章): BLOB に保存し、PostgreSQL で pgvector が使えるときは `embedding vector` の列と、モデルごとの部分 HNSW 索引も持つ。
- `model_key` は画像の埋め込みと同じ値を使う。同じモデルなので、画像とプロンプトのベクトルは同じ空間にある。ただし、今回は混ぜて比べない。

### 4. 計算のタイミング

- 埋め込みの worker(`worker/embedder.py`)が、画像と同じく待ち行列(`status='queued'`)から1件ずつ処理する。モデルのセッションは画像と共有する(文章側だけで足りる)。
- **取り込み時の自動実行:** 埋め込みの自動実行がオンで、選んだモデルがプロンプトの埋め込みに対応していれば、Run が成功したときに待ち行列に入れる。
- **一括実行:** 既存の一括実行(`POST /api/settings/embeddings/backfill`)で、画像と一緒にプロンプトも埋める。
- **タイトルの変更:** 2章の条件で埋め込み直す。
- 画像を先に処理し、プロンプトは後にする(検索の画像の結果が先にそろうように)。

### 5. 検索

- `GET /api/search/semantic` に、探す対象 `target=image|prompt` を足す。既定は `image`(今までどおり)。
- `target=prompt` の応答は Run の単位にする。Run の要約(最初の出力の Asset、プロンプトの先頭、Operation)と類似度を返す。同じ Run の出力を何枚も並べない。
- 見える範囲(ADR-0025)と削除済みの除外で絞るのは、画像の検索と同じ。
- numpy と pgvector で同じ口・同じテストにする(`domain/vector_index.py`)。

### 6. 画面

画面は最低限にする(2026-10-11、ユーザーの指示)。今回は、埋め込みの状況が分かることだけを作り、使い方の画面は後で作り込む。

- 埋め込みの設定に、プロンプトの埋め込みの件数(済み・待ち・失敗)を、画像の件数と並べて出す。選んだモデルが対応していないときは出さない。
- 検索画面の「画像で探す / 指示で探す」の切り替えと、結果の Run のカードは、今回は作らない。検索は API(5章)だけで使える。

## Options Considered

### プロンプトのベクトルを持つか

| 案 | 評価 |
|---|---|
| A. 画像だけ(ADR-0044 のまま) | 画像に残らない指示(消す、書き替える)では探せない |
| B. プロンプトも保存し、検索の対象を切り替える(採用) | 指示の意味で探せる。保存は Run あたり 3KB |
| C. 保存せず、検索のたびにプロンプトを埋め込む | Run が増えるたびに検索が遅くなる。1件 0.2 秒以上かかり、現実的でない |

### 長いプロンプトの扱い

| 案 | 評価 |
|---|---|
| A. 切らない | 長い文章で計算中のメモリが 2GB を超える(4,168 トークンで約 2.3GB) |
| B. 上限で切るだけ | 後ろの指示が失われる |
| C. 上限を超えるときだけ、タイトルを先頭に付けて切る(採用) | タイトルが全体の要約になり、意味の損失を減らせる。タイトルが付くまでは B と同じ |
| D. 分割して複数のベクトルにする | 検索と保存の作りが複雑になる。今回の規模では要らない |

## Trade-off Analysis

画像の検索と別の検索の軸ができる。画像に残らない Edit の指示で探せるのが大きい。代わりに、Run ごとに文章の計算が1回増える(短いプロンプトで 0.2 秒台、上限の 1,024 トークンで約 1.3 秒)。画像の計算(1枚約 3 秒)に比べれば小さい。

タイトルを先頭に付ける工夫は、タイトルの質(LLM の自動のタイトル)に頼る。タイトルが無い環境では、ただ切るだけになる。

## Consequences

- 新しいテーブル `run_prompt_embedding` と、そのマイグレーションが加わる。
- 埋め込みの worker が、画像とプロンプトの2つの待ち行列を処理する。
- タイトルの更新(自動・人の編集)が、プロンプトの埋め込み直しのきっかけになる(上限を超えるプロンプトだけ)。
- 文章での検索の API に `target` が加わる。応答の形が `target` で変わる。画面から使えるようになるのは、使い方の画面を作ってから。
- カタログのモデルに、プロンプトの埋め込みに対応するかの印が加わる。

## Action Items

1. ADR-0044 の実装(EG2 のエンジン)の後に着手する。
2. (済み)文章の上限は 1,024 トークン(計算中のメモリの実測から)。
3. `run_prompt_embedding` のモデルとマイグレーション、pgvector の列と索引。
4. 埋め込む文章の組み立て(final_prompt、タイトル、上限、sha256)と、そのテスト。
5. worker の待ち行列、自動実行、一括実行、タイトルの変更での埋め込み直し。
6. `GET /api/search/semantic` の `target=prompt` と、numpy・pgvector の両方のテスト。
7. 設定画面の件数、文言(ja / en)、`docs/embeddings.md`。
8. 実データで、Edit の指示(消す、書き替えるなど)を言い回しを変えて API で探し、キーワード検索と比べて確かめる。
9. 検索画面での使い方は、別に作り込む(切り替え、Run のカード、似たプロンプトなど)。
