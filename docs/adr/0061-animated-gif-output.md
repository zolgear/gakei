# ADR-0061: アニメーション GIF の出力(GPT Image 2.6)

**Status:** Proposed
**Date:** 2026-11-05

2026-11-05 に、ユーザーが GPT Image 2.6 への対応を決めた(#233。段1 モデルと `complexity`、段3 GIF、段2 markup、段4 SVG の順)。この ADR は段3(アニメーション GIF の出力)を決める。

## Context

- GPT Image 2.6(Sunburst / Flare)は、Generate と Edit で `output_format: "gif"` を受け、アニメーション GIF を返す(ガイドは Generate だけと書いているが、2026-11-05 の実機で Edit も 512x512 の4コマの GIF を返した。入力画像の内容を動かせる)。
- 2026-11-05 に、実機(`quality=low`)で次のことを確かめた。
  - コマの数は `frame_count` で、2〜16(既定 9)。17 を送ると 400 になる。公式のガイドは 2〜64 と書いているが、API は 16 までしか受けない。
  - 1コマの表示時間は `frame_duration_ms` で、20〜2000(既定 200)。返る GIF は無限にループする。
  - `size` は1コマの大きさを表す。API は全コマを1枚のシートに並べて描き、そのシートが通常のサイズの制約(総ピクセル 655,360〜8,294,400、長辺 3840 以下)に収まらなければ 400 を返す。
    - 例: 1024x1024 の2コマ、256x256 の9コマは断られた。512x512 の4コマは通った。
    - `auto` にすると、API がコマの大きさを選ぶ(4コマで 512x512)。
    - シートへの並べ方は公開されていない。
  - 料金は、通常の画像と同じく出力のトークンで決まる(512x512 の4コマ、low で 555 トークン)。式は公開されていない。
  - ストリーミングと途中経過画像は使えない。
- 今の GAKEI は、原本の形式を PNG / JPEG / WebP に限っている(取り込み、プロバイダーの拡張子の対応、派生の作り方)。派生は WebP で、ビューアは初めにプレビューの派生を出し、拡大したときだけ原本に切り替える(ADR-0004)。

## Decision

1. **フォーム:** 2.6 の Generate と Edit で、ファイル形式に GIF を出す。GIF のときだけ「コマ数」(2〜16)と「1コマの時間」(ミリ秒、20〜2000)を出す。途中経過の表示と圧縮率は、GIF では使えない。
2. **大きさの検証:** GIF のときは、サイズ欄を1コマの大きさとして検証する。
   - 制約は capabilities の `gif_frame_size` に持つ: 16 の倍数、縦横比 1:3〜3:1、長辺 1920 以下、総ピクセル 65,536〜2,073,600。シートは少なくとも2×2のコマを並べるので、通常の上限の半分の長辺・4分の1の総ピクセルを上限にした。
   - 並べ方が公開されていないため、シートに収まるかは確かめない。API の 400 の文をそのまま失敗の理由として見せる。
   - フォームでは、GIF にしたときにサイズを `auto` にするよう説明で勧める。
3. **保存:** 生成の結果(`kind = generated`)に限って GIF を原本として受け入れ、変換せずに保存する(ADR-0004 3章のとおり、原本は不変)。アップロードでは受けない。
4. **派生:** サムネイル・カード・プレビューは、1コマ目から作る WebP のまま(作り方は変えないので、ADR-0036 の版は上げない)。一覧が軽いままになる。
5. **表示:** ビューアは、GIF のときだけ最初から原本を出す(ブラウザの `<img>` が再生する)。一覧のタイルは派生の静止画のまま。
6. **入力にしない:** GIF の Asset は、Run の入力(Edit の入力、参照画像)に使えない。Run の作成で 422 にする。1コマ目だけを送ると、利用者が思った画像と違うものが送られるため。使いたいときは、ビューアで静止画として保存し直す方法を後で考える。
7. **系列の埋め込み(ADR-0014):** GIF のダウンロードには系列の情報を埋め込まない(原本をそのまま返す)。
8. **参考価格:** GIF は見積もらない(式が公開されていないため)。実行後の料金は、これまでどおり応答の `usage` から求める。

## Options Considered

### サイズ欄の意味

| 案 | 評価 |
|---|---|
| A: 1コマの大きさとして検証し、シートは API に任せる(採用) | API の `size` の意味と同じ。並べ方を推測しないので、API が変わっても壊れない |
| B: シートの並べ方を推測して、GAKEI で総ピクセルを確かめる | 送る前に断れるが、並べ方は公開されておらず(2コマで 4×2 を試すなど)、外れると正しい指定まで断る |
| C: GIF ではサイズを `auto` に固定する | 単純だが、コマの大きさを選べなくなる |

### 入力に使うとき

| 案 | 評価 |
|---|---|
| A: 入力にしない(採用) | 送る画像と見えている画像が食い違わない |
| B: 1コマ目を PNG にして送る | 便利だが、利用者の知らない変換が証跡(`run_input`)の外で起きる |

## Trade-off Analysis

GIF の原本をそのまま再生すると、ビューアは派生より重い原本を読む。ただし、コマが小さく(最大 1920px)、コマ数も 16 までなので、4K の PNG の原本より大きくなることは少ない。一覧は派生の静止画のままなので、一覧の重さは変わらない。

## Consequences

- 2.6 の Generate と Edit で GIF を作り、履歴とビューアで再生できる。
- GIF は Edit の入力にできない。編集を重ねたいときは、PNG で作り直す。
- 原本の形式が4つになる。原本の形式で分けている処理(拡張子、ダウンロード、Mod の書き出し)は GIF も扱う。

## Action Items

1. [ ] GIF を静止画(1コマ目、または選んだコマ)として保存し直す操作を考える(入力にしたいとき)
2. [ ] GIF の出力のトークン数を、コマ数と大きさごとに実測し、参考価格の式を探す
