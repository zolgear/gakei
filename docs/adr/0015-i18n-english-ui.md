# ADR-0015: 画面の多言語化(日本語と英語)

**Status:** Proposed
**Date:** 2026-09-24

## Context

ソースの公開(ADR-0011)と、個人が手軽にセルフホストできる形(ADR-0012)に向けて、日本語を読めない利用者も GAKEI を使えるようにしたい。今は画面の文言、サーバーが返すエラー、フォームの見出し(`capabilities()` の `label` / `choice_labels`)、起動スクリプトの表示、README が日本語だけで書かれている。

画面の文言はフロントの約80ファイルに直接書かれている。サーバー側にも利用者に見える文言がある。

- `capabilities()` が返すパラメーターの見出しと選択肢の表示名(ADR-0005。フォームはこれから組み立てる)。
- API のエラー(`HTTPException` の `detail`)。フロントはこれをそのまま通知に出す。
- ComfyUI のワークフロー解析の警告や、接続テストの結果(ADR-0013)。
- Run が失敗したときの `error_message`。worker(api プロセス内の runner)が、リクエストの外で書き込む。
- ランチャー(`run.sh`、`backend/app/launch.py`)が端末に出す案内。

## Decision

1. **対応する言語は日本語(`ja`)と英語(`en`)の2つ。** ほかの言語は受け付けるが、翻訳は用意しない。
2. **文言は言語ごとに1つのリソースファイル(JSON)に置く(2026-09-24 改訂)。** ライブラリ(i18next など)は追加しない。
   - フロントは `frontend/src/i18n/locales/{ja,en}.json`、サーバーは `backend/app/locales/{ja,en}.json`。それぞれ言語ごとに1ファイルで、中は画面やモジュールの領域ごとに入れ子のキーで分ける。日本語を正とする。
   - 差し込みは `{count}` のような名前付きの置き場所で書く。数で文言が変わるもの(英語の単数・複数)は `{"one": "...", "other": "..."}` のオブジェクトにし、`count` で選ぶ。日本語も同じ形にそろえる(2つとも同じ文でよい)。条件で文が変わるものは、キーを分けてコードの側で選ぶ。
   - フロントは JSON を import し、日本語の JSON の型に英語を当てはめる。キーの欠けは型検査(`tsc -b`)で落ちる。キーの余り、置き場所の名前の不一致、英語に日本語が混ざっていないことはテストで確かめる。コンポーネントは `useI18n()` の `t`、React の外の関数は `msg()` で辞書を得て、差し込みは `fmt()` で行う。
   - サーバーは `t("runs.missingApiKey", count=...)` の形でキーを引く。コードに書いたキーが両方の JSON にあることと、置き場所の一致はテストで確かめる。
   - 当初は領域ごとの TypeScript ファイル(18ファイル × 2言語)と、関数による差し込み、サーバーはその場に日英を並べる `tr("日本語", "English")` にしていた。ファイルが多いとブランチ間のマージで衝突しやすく、人間の翻訳者や翻訳ツールも扱えないため、1ファイルの JSON に改めた。
   - `run.sh` の案内(uv のインストール確認の数行)だけは、Python が動く前に出すので、スクリプトの中に日英を並べて書く。
   - 言語の既定値はブラウザの言語から決める(`ja` で始まれば日本語、それ以外は英語)。設定画面の先頭のコンボボックスで切り替えられ、選んだ言語は localStorage(`gakei.locale`)に保存する。切り替え欄の見出しと選択肢は、どちらの言語で表示していても読めるよう、日英併記の固定の文字列にする(「表示言語 / Language」「日本語 (Japanese)」「English (英語)」)。切り替えたら画面を描き直し、サーバーから取得したデータ(capabilities など)も取り直す。`<html lang>` も合わせる。
   - 日時と数値の表示は、選んだ言語で `Intl` に任せる。
3. **サーバーはリクエストの `Accept-Language` で言語を選ぶ。** フロントは選んだ言語を、すべての API 呼び出しの `Accept-Language` に明示して送る。ヘッダーがないとき(`curl` やテスト)は日本語にする(これまでと同じ)。
   - API のエラーの形(`detail` が文字列)と OpenAPI のスキーマは変えない。
4. **Run に記録する文言は、記録した時点の言語のまま残す。** `run.error_message` はリクエストの外で書かれるので、サーバーの既定(日本語)になる。フロントは `error_code` が分かるものを自分の言語で表示し、`error_message` は詳細として添える。Run の記録は追記のみ(ADR-0003)なので、後から翻訳し直さない。プロンプト、プロンプトセット、ワークフロー名など、利用者が入力した文字列も翻訳しない。
5. **ランチャーの案内は、OS のロケールが日本語なら日本語、それ以外は英語にする。**
6. **文書は README だけ英語版(`README.en.md`)を用意する。** 日本語の `README.md` はそのまま残し、互いにリンクする。ADR、CLAUDE.md、README から参照する補足の文書(`docs/configuration.md`、`docs/localization.md`)、コード中のコメントは日本語のままにする(補足の文書は 2026-09-24 追記)。例外は起動スクリプト `run.sh` と `run.bat` で、コメントは英語で書く。`run.bat` は cmd がコンソールのコードページで読むため ASCII に限る必要があり、対になる `run.sh` も同じ言語で揃えて保守する(2026-09-27 追記。利用者に見せる案内文は Decision 3 のとおり日英を選ぶ)。

## Options Considered

| 案 | 評価 |
|---|---|
| A: 自前の辞書 + 型検査(採用) | 依存が増えない。キーの欠けをコンパイル時に検出できる |
| B: i18next / react-i18next | 機能は十分だが、2言語には大きい。キーの欠けは実行時まで分からない(型付けには追加の設定が要る) |
| C: 英語だけにする | 単純だが、今の利用者(日本語)にとって後退になる |

| 辞書の置き方 | 評価 |
|---|---|
| A: 言語ごとに1つの JSON(採用、2026-09-24 改訂) | マージの衝突が1か所に集まり、翻訳ツールにそのまま載る。差し込みの名前の一致は型では守れないのでテストで確かめる |
| B: 領域ごとの TypeScript ファイル + 関数(当初) | 型で差し込みの引数まで守れるが、ファイルが多く、翻訳者には読めない |
| C: 言語ごとに1つの TypeScript ファイル | ファイルは減るが、翻訳者とツールが扱えない点は変わらない |
| D: フロントとサーバーで1つの JSON を共有する | 置き場所は1つになるが、フロントのビルド(ADR-0012 のハッシュ判定)と Vite の読み込み範囲の設定が増え、画面に不要なサーバーの文言も配信される |

| サーバーの文言 | 評価 |
|---|---|
| A: `Accept-Language` で選び、サーバーの辞書を引く(採用) | API の形が変わらない |
| B: サーバーはコードだけ返し、文言はフロントが持つ | 筋は良いが、`detail` と警告の形を全部変える必要があり、ComfyUI の解析結果など可変の文言が多い |
| C: サーバーは日本語のまま | 英語の画面にエラーだけ日本語で出る |

## Consequences

- 文言を足すときは、日本語と英語の両方の JSON に書く(フロントは英語が欠けるとビルドが通らず、サーバーはテストで落ちる)。
- コードの上では元の文が見えず、キーだけになる。キーは領域とその意味で名付ける。
- 失敗した Run の `error_message` は日本語で残る。英語の画面では、既知の `error_code` だけが英語で表示される。
- 画面の幅は日本語を前提に調整しているので、英語で文言が長くなる箇所は表示を確かめる必要がある。
