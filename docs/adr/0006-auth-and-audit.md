# ADR-0006: 認証と証跡

**Status:** Proposed
**Date:** 2026-09-21

## Context

組織でのAI利用として、「誰が、いつ、何を入力し、何が出力されたか」を後から示せる必要がある。また単一組織向けのツールなので、利用者は組織の Entra ID ユーザーに限られる。

証跡に求められる性質は、漏れなく記録されること、後から改変されないこと、実行者が本人と結び付くことの3点。

## Decision

### 認証

- **Entra ID によるシングルサインオン。** ホスティング基盤の組み込み認証(Container Apps / App Service の Easy Auth)を前段に置き、未認証のリクエストはアプリに届かせない。
- API は基盤が付与するヘッダー(`X-MS-CLIENT-PRINCIPAL` 等)からユーザーの oid、名前、メールを取得し、初回アクセス時に `user` テーブルへ登録する。
- ロールは `user` と `admin` の2つだけ。Entra ID のアプリロール(またはグループ)で割り当てる。
- ローカル開発では、環境変数で有効化する開発用の固定ユーザーを使う。本番では無効であることを起動時に検査する。
- Azure OpenAI、Blob Storage、PostgreSQL へはマネージド ID で接続する。APIキーや接続文字列をアプリに持たせない。

### 認可

- プロジェクト単位。作成者が所有者で、メンバーを追加できる。メンバーは閲覧と実行ができる。
- `admin` は全プロジェクトを閲覧できる(証跡確認のため)。
- (要確認)全社員が全プロジェクトを見られる方が運用に合うなら、メンバー管理を省略して更に単純にできる。

### 証跡

証跡は2層で持つ。

1. **Run の記録(正本)。** ADR-0003 の `run` / `run_input` / `asset`。プロンプト、API に送ったパラメータ、入力画像、出力画像、モデルとデプロイメント名、usage、実行者、時刻、失敗内容を含む。追記のみ。
2. **`audit_event` テーブル。** Run に現れない操作を記録する。

| 列 | 内容 |
|---|---|
| id, occurred_at | |
| user_id | 実行者 |
| action | `asset.upload`, `asset.download_original`, `asset.delete`, `project.create`, `project.member_add`, `export.create`, `admin.view` など |
| target_type, target_id | 対象 |
| detail(JSONB) | 補足 |
| ip, user_agent | |

- どちらも UPDATE / DELETE をアプリのDBロールに許可しない(`audit_event` は INSERT と SELECT のみ)。
- 削除は論理削除のみ。物理削除は保存期間の方針が決まってから、管理者の手動運用として別途定める。
- 管理者向けに、期間・ユーザー・プロジェクトで絞った Run の一覧と CSV エクスポートを用意する(Phase 2)。

## Options Considered

### 認証の実装場所

| 案 | 評価 |
|---|---|
| A: 基盤の組み込み認証(採用) | アプリのコードがほぼ不要。トークン検証の実装ミスが起きない。ローカル開発には代替が要る |
| B: SPA で MSAL、API で JWT 検証 | 基盤に依存しないが、実装と設定(アプリ登録2つ、スコープ、CORS)が増える |
| C: 独自のID/パスワード | 組織内ツールでは論外。退職者の無効化が連動しない |

### 証跡の持ち方

| 案 | 評価 |
|---|---|
| A: 来歴データ自体を追記のみにする+操作ログ表(採用) | 証跡と実データがずれない。追加の仕組みが不要 |
| B: アプリのログ(Log Analytics)だけに頼る | 保存期間と検索性が弱い。画像との結び付けが難しい |
| C: イベントソーシング | 改変耐性は高いが、この規模には過剰 |
| D: C2PA / IPTC を画像に埋め込む | 画像が外に出た後の来歴証明には有効だが、組織内の証跡の代わりにはならない。Phase 3 |

## Trade-off Analysis

A の認証は Azure の基盤に依存するが、ホスティング先を Azure と決めている(ADR-0007)ので実害はない。将来オンプレに移す場合は、リバースプロキシ(oauth2-proxy 等)で同じヘッダーを付ければアプリは変えずに済む。

証跡は「特別な監査機能」を作るのではなく、「普段のデータが消せない・書き換えられない」ことで満たす。これが最も漏れが少なく、実装も小さい。

## Consequences

- 利用者の入社・退職は Entra ID に連動する。
- 「消してほしい」という要望には論理削除で応える。完全な削除が必要な場合(誤って機微な画像をアップロードした等)の手順を運用として決めておく必要がある。
- DB管理者権限を持つ者による改変までは防げない。必要になれば、Run のハッシュチェーンや不変ストレージへの定期エクスポートを検討する。

## Action Items

1. [ ] 閲覧範囲(メンバー制か全員閲覧か)を決める
2. [ ] 保存期間を運用する組織の規程に合わせて決める
3. [ ] Entra ID のアプリ登録とアプリロール(`user` / `admin`)を作成する
4. [ ] アプリ用DBロールの権限を最小にする(`run_input`, `audit_event` は INSERT / SELECT のみ)
