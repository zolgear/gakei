# ADR-0031: 設定画面をページに分け、保存のしかたをページ単位で揃える

**Status:** Proposed
**Date:** 2026-10-01

2026-10-01 に、ユーザーから次の指摘があった。

- 設定画面の至る所に保存ボタンがある。
- チェックボックスですぐに保存されるものと保存ボタンで保存するものがあり、項目ごとに挙動が異なる。
- 設定内容によっては幅が狭い。
- 改善案として、上部の「戻る」と一緒に保存ボタンを置くことが挙がった。

同日、提案(設定をページに分ける、有効化のスイッチも保存まで反映しない、保存は上部に置きスマホも上部)がユーザーに承認された。

## Context

設定画面(`/settings`)は1ページで、ユーザー設定と管理者設定のセクションが幅 640px の1列に縦に並んでいる(ADR-0019 5章)。セクションは機能を足すたびに増えてきた。その結果、2026-10-01(dev `f99fb4c`)の時点で次の状態になっている。

- **保存系のボタンが9か所ある。** 自動タイトル・タグ(ADR-0024)には「保存」が3つあり、どれを押してもセクション全体が保存される。
- **保存のしかたが3系統、混在している。**
  - ブラウザに即時保存するもの: 表示言語、表示。
  - サーバーに即時保存するもの: moderation、MCP と共有リンクの有効化、自動タイトル・タグのスイッチとモデル選択。
  - 保存ボタンで保存するもの: API キー、接続先、MCP の上限、ComfyUI のタイムアウト、自動タイトル・タグの表と数値。
  - MCP、ComfyUI、自動タイトル・タグでは、同じセクションの中でも混ざっている。
- **成功の表示がばらばら。** 即時保存でも、トーストが出るものと出ないものがある。
- **未保存の変更に気づけない。** 未保存の表示は自動タイトル・タグにしかなく、ページを離れるときの確認はどこにも無い。
- **幅が狭い。** 本文は `max-width: 640px`。自動タイトル・タグの使い方の表(ADR-0024)は、1マスが約 250px になる。
- **ADR が無い。** 保存の方式を決めた ADR は無く、セクションごとに実装のときに決めてきた。

一方、サーバーの設定 API は、ほぼセクション単位の部分更新(`PATCH /api/settings/{general,mcp,share,annotation}`)になっている。送ったキーを全部確かめてから保存するので、画面の作りを揃えるだけで済み、バックエンドは変えなくてよい。

## Decision

### 1. 設定をページに分ける

| ページ | パス | 区分 | 中身 |
|---|---|---|---|
| プロフィール | `/settings/profile` | ユーザー(oidc のみ) | アバター(ADR-0020) |
| 表示 | `/settings/display` | ユーザー | 表示言語、タブのアイコンで進捗を示す、生成画面の入力欄の配置 |
| 共有リンク | `/settings/shares` | ユーザー(共有が有効なときのみ) | 自分の共有の一覧と取り消し(ADR-0029) |
| アクセストークン | `/settings/access-tokens` | ユーザー(oidc のみ) | 発行と失効(ADR-0023) |
| OpenAI | `/settings/openai` | 管理者 | API キー、接続先(Base URL)、moderation(これまでの「生成」セクション) |
| LLM の接続先 | `/settings/llm-connections` | 管理者 | LLM・VLM の接続先(2026-10-01 追加。ADR-0032) |
| 自動タイトル・タグ | `/settings/annotation` | 管理者 | ADR-0024 の6小節。順序は変えない |
| 埋め込み | `/settings/embeddings` | 管理者 | 画像の埋め込みのエンジン、モデル、計算、重複のしきい値の既定(2026-10-03 追加。ADR-0033) |
| ComfyUI | `/settings/comfyui` | 管理者 | 接続、タイムアウト、ワークフロー管理への入口 |
| MCP | `/settings/mcp` | 管理者 | 有効化、1時間の上限、接続先 |
| 共有リンクの公開 | `/settings/share-links` | 管理者 | 共有リンク機能の有効化(ADR-0029) |
| GAKEI について | `/settings/about` | どちらでもない | ADR-0011、ADR-0021 |

- **目次。** 設定ページの中の左列に、「ユーザー設定」「管理者設定」の見出しで括った目次を置く。どのページを出すかの条件は、これまでの `visibleSections` と同じにする。非管理者には管理者設定の見出しも出さない(無効な機能は隠す)。
- **幅が十分なとき。** 設定ページの幅で判定する(コンテナクエリ。720px 以上)。目次と本文を横に並べる。`/settings` では「表示」のページを出す。
- **幅が狭いとき。** スマホや、右のリソースのパネルで狭くなったとき。`/settings` は目次だけのページにし、各ページは別の画面として開く。
- **本文の幅。** 最大 760px にする。項目は、左にラベルと説明、右に入力を置く2列で並べる。幅が足りなければ縦に積む。
- **パスの付け替え。**
  - ワークフロー管理の画面は `/settings/comfyui/workflows`、`/settings/comfyui/workflows/new`、`/settings/comfyui/workflows/:id` に移す。
  - これまでの `/settings/comfyui/new` と `/settings/comfyui/:id` は、新しいパスに転送する。
  - これまでの `/settings#comfyui` などのハッシュ付きのリンクも、対応するページに転送する。

**2026-10-01 追記(ワークフロー管理を枠に入れる):** ユーザーの指示で、ComfyUI のワークフロー管理も設定の枠(目次とヘッダー)の中に入れた。
- ワークフローの一覧は、ComfyUI のページ(`/settings/comfyui`)の一節として出す。一覧だけのページ(`/settings/comfyui/workflows`)は ComfyUI のページへ転送する。
- 登録と編集(`/settings/comfyui/workflows/new`、`/settings/comfyui/workflows/:id`)も設定の枠の中で開き、目次は ComfyUI を選んだ状態にする。「戻る」は ComfyUI のページへ戻る。
- 登録・編集の画面は「保存で反映」のページとして扱う。保存はヘッダーの1か所にし、保存していない変更があれば離れる前に確認する(3章・4章)。
- ワークフローの削除は「操作」(確認のあとすぐ実行)にする。

### 2. 項目を4つの種類に分ける

| 種類 | 反映のしかた | 当てはまるもの |
|---|---|---|
| 保存で反映 | 値を変えてもすぐには送らない。ページ上部の「保存」でまとめて送る | moderation、ComfyUI のタイムアウト、MCP の有効化と上限、共有リンクの公開の有効化、自動タイトル・タグのスイッチ・モデル選択・使い方の表・言語・上限・しきい値 |
| 即時 | ブラウザに保存し、その場で反映する | 「表示」のページの項目すべて |
| 操作 | ボタンを押すとその場で実行する。取り消せないものは確認ダイアログを出す | アバター、共有の取り消し、トークンの発行と失効、ONNX モデルのダウンロードと削除、一括実行 |
| 接続 | 状態をカードで見せ、変えるときはダイアログで入力し、確かめてから登録する | OpenAI の API キーと接続先、ComfyUI の接続、自動タイトル・タグの接続先 |

- **ページ単位で揃える。** 「保存で反映」の項目が1つでもあるページには保存のボタンを出し、そのページの「保存で反映」の項目はすべて保存まで待たせる。
- **スイッチも例外にしない。** 機能を有効・無効にするスイッチも、保存を押すまで反映しない。
- **即時のページ。** 「即時」の項目しか無いページ(表示)には、保存のボタンを出さない。
- **ボタンの名前。** 「保存」と書くのは、ページ上部のボタンだけにする。操作と接続のボタンには、何が起きるかを書く(例: 「確かめて登録」「キーを差し替える」「トークンを発行」)。
- **接続をダイアログにする理由。** 接続は、登録するときに相手に接続して確かめる。OpenAI のキーは最大約15秒かかる。ページの保存に混ぜると、保存が遅くなり、失敗したときにどの値が原因か分かりにくい。そこで別にする。
- **キーは見せない。** キーは一部も表示しない(ADR-0019 5章、ADR-0012)。
- **保存前は操作を押せないことがある。** ページに保存していない変更がある間は、保存済みの設定で動く操作を押せなくする(例: 自動タイトル・タグの一括実行)。押せない理由は、ボタンの近くに短く書く。

### 3. ページのヘッダー

- **並び。** 各ページの上部に、「戻る」、ページ名、変更の件数、「変更を取り消す」、「保存」を1行に並べる。スクロールしてもヘッダーは上に残す。スマホでも上に置く。
- **「戻る」の行き先。**
  - 幅が十分なとき: 設定を開く前の画面に戻る(今の `useBackNavigate` と同じ)。
  - 幅が狭いとき: 目次に戻る。
- **「保存」を押せる条件。** 変更があり、入力の検証が通っているときだけ押せる。
  - 保存中は「保存中…」と出して押せなくする。
  - 成功したら、トーストで「保存しました」と出す。
  - 失敗したら、ヘッダーの下にエラーを出す。どの欄が原因か分かるときは、その欄にも出す。
- **変えた欄の示し方。**
  - 変えた欄は、縁をアクセント色にする。
  - 目次のそのページの項目にも、点を付ける。
- **「変更を取り消す」。** 保存済みの値に戻す。確認は出さない。
- **1回の保存で送る先。** 1ページの「保存で反映」の項目は、1つの `PATCH` で送る。
  - OpenAI と ComfyUI のページは、`PATCH /api/settings/general` の別のキーを送る。
  - 送るのは変えたキーだけにする(今の自動タイトル・タグの `diffAnnotationForm` と同じ)。
  - サーバーは全部を確かめてから保存するので、途中までしか保存されないことはない。

### 4. 保存していない変更があるときは、離れる前に確認する

- **確認する場面。**
  - アプリの中での移動: 目次の別のページ、「戻る」、App バーなど。
  - ブラウザの戻る。
  - タブを閉じる・再読み込み(`beforeunload`)。
- **ダイアログ。** 文言は「保存していない変更があります」。ボタンは「変更を破棄して移動」と「このページに残る」にする。
- **ルーターの変更。** アプリの中の移動を止めるには、React Router の `useBlocker` を使う。これはデータルーターでしか動かない。
  - そこで `main.tsx` の `BrowserRouter` を `createBrowserRouter` に変える。
  - 今の `<Routes>`(`App.tsx`)は、`path: '*'` の1つのルートの中にそのまま置く。
  - ルートの定義は書き換えない。

### 5. 共通の部品

- 部品を共通にする。
  - ページの枠: 目次、ヘッダー、本文。
  - 項目の行: ラベル、説明、入力。
  - 下書きを持つフック: 保存済みの値、下書き、差分、検証、保存、取り消し、離れる前の確認。
  - 接続のカード。
- 今は7つの CSS Module に `.section`、`.saveButton` などが複製されている。これを1つにまとめる。

## Options Considered

### 保存のしかた

| 案 | 評価 |
|---|---|
| A. ページに分け、ページで1回保存する(採用) | 何が保存されるかがページの範囲で分かる。1ページが1つの PATCH に収まる |
| B. 1ページのまま、上部の保存を全体で1つにする | ボタンは1つになる。ただし自動タイトル・タグのように長いセクションがあり、何が保存されるのかが見えにくい。保存先が4つの API にまたがり、途中まで保存されることがありうる |
| C. すべて即時保存にする | 保存ボタンが無くなる。ただし数値や表の入力途中で送ることになり、検証のエラーが入力中に出続ける。接続は時間がかかるので即時にできない |
| D. 今のまま、ボタンの見た目だけ揃える | 混在が残る |

### スイッチの扱い

| 案 | 評価 |
|---|---|
| 保存まで待たせる(採用) | 例外が無く覚えやすい |
| スイッチだけ即時 | 1クリックで済む。ただし同じページの中で挙動が分かれる |

### 保存の位置

| 案 | 評価 |
|---|---|
| 上部の「戻る」と同じ行。スマホも上(採用) | ユーザーの提案。他の画面に下部固定のバーが無いので、見た目が揃う |
| スマホだけ下部に固定 | 親指で押しやすい。ただし、この画面にしか無い形になる |

## Trade-off Analysis

- **クリックが1回増える。** 有効化のスイッチは、これまで1回押せば済んだ。今後は保存も押す必要がある。代わりに、どのページでも「変えて、保存」で同じになる。
- **一覧が見られなくなる。** ページに分けると、設定全体を1回のスクロールで見渡せなくなる。目次で補う。
- **ルーターの影響。** `createBrowserRouter` への切り替えはアプリ全体に及ぶ。今のルート定義をそのまま包むだけにして、影響を抑える。

## Consequences

- 設定画面の構成は、ADR-0019 5章の「設定ページを見出しで括る」から、「目次を見出しで括り、ページに分ける」に変わる(ADR-0019 に追記する)。
- ADR-0024 の「設定画面の配置」は、1ページの中での順序として残る。スイッチとモデル選択が「保存で反映」に変わる(ADR-0024 に追記する)。
- 新しい設定を足すときは、まず2章の4つの種類のどれに当たるかを決め、該当するページに置く。新しいページを作る場合は、1章の表に足す。

## Action Items

1. 共通の部品(5章)とルーター(4章)を用意する。
2. 小さいページ(MCP、共有リンクの公開、表示)から移す。
3. OpenAI と ComfyUI のページを移す。接続をカードとダイアログにする。
4. 自動タイトル・タグのページを移す。
5. 古いパスとハッシュを転送する(1章)。README と docs の画面の説明を更新する。
