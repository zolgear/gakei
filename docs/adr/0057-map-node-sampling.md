# ADR-0057: マップのノードの抽出(全体から均等に選ぶ)

**Status:** Proposed
**Date:** 2026-11-01

## Context

マップ(ADR-0033 8章、ADR-0047)は、絞り込みに合いベクトルのある画像(候補)を新しい順に並べ、上限(`limit`。500 / 1000 / 2000 / 5000、既定 1000)で先頭から切っている。`GET /api/embeddings/graph` と `GET /api/embeddings/graph/scores` は、どちらも `candidate_ids`(新しい順)の `[:limit]` を使う。

利用者から次の報告があった。1つのグループに 1000 枚を超える生成をしたところ、マップが直近の 1000 件で埋まり、それより前の画像が1枚も出なくなった。上限を広げても、直近の作業の塊に点が密集するだけで、全体の分布や関連を俯瞰できない。

新しい順で切ると、並ぶのは「最近の作業」であって「手元の画像の全体」ではない。全体を見たいときにグループやタグで絞る方法は、グループに入っていない画像には効かず、絞っても同じ偏りが残る。

関連する決まり:

- ADR-0033: 埋め込みは `model_key` ごとに保存し、使うのは管理者が選んだ1つ。見える範囲(ADR-0025)で絞ってから使う。
- ADR-0047 8章: 同じ引数なら `graph/scores` の `ids[i]` は `graph` の `nodes[i].id` と一致する。画面は ID で突き合わせる。
- ADR-0054 3章: 履歴の似た画像の順に、球面 k-means(k ≈ √n、k-means++、乱数の種は固定、最大 8 回)と、プロセス内のキャッシュ(鍵は `model_key`、埋め込みの版、見る人の範囲、対象の id の要約)を使っている。

## Decision

### 1. 抽出方法を選べるようにする

| 抽出方法 | 値 | 内容 |
|---|---|---|
| 全体から均等に(既定) | `spread` | 候補の全件をクラスタに分け、クラスタごとに配分して上限に収める(2章) |
| 新しい順 | `recent` | 今の挙動。新しい順の先頭から上限まで |

- 候補が上限以下なら、どちらも全件を並べる(抽出しない)。
- ノードの並びは、どちらも候補の並び(新しい順)のまま返す。抽出は「どれを残すか」だけを決める。
- 埋め込みは証跡ではない。抽出の結果も来歴の列には書かない(ADR-0033 1章と同じ)。

### 2. 全体から均等に選ぶ方法

1. 候補の全件のベクトル(正規化)に、球面 k-means を掛ける。k ≈ √n(上限を超えない)。ADR-0054 の部品(`history_sort` の k-means++ と繰り返し)を使い、最初の中心は最も新しい画像、乱数の種は固定する。
2. **配分:** どのクラスタにも1枚は配り、残りを √(クラスタの大きさ) に比例して配る。クラスタの大きさを超える分は、ほかのクラスタへ回す。端数は取り分の大きい順に1枚ずつ配る。合計はちょうど上限になる。
   - 大きさに比例させると、大きな塊(同じ作業の大量の生成)が上限の大半を取り、今と同じ偏りが残る。均等に配ると、数枚の塊と数百枚の塊が同じ扱いになり、分布の手がかりが消える。平方根はその間を取る。
3. **クラスタの中の選び方:** 重心に近い順の次の点(代表点)と、選んだ点との最大の類似度が最も小さい点(最も離れた点)を、交互に選ぶ。同点は新しい画像を取る。代表点だけだと塊の中心に寄り、離れた点だけだと外れ値ばかりになるので、交互にして塊の広がりを残す。
4. **代表数:** 間引いた画像を、同じクラスタの中で最も近い選んだ点に数える。選んだ点は自分を数えるので、どのノードも1以上で、合計は候補の数になる。

同じ入力なら同じ結果になる(乱数の種は固定、同点の扱いも決めてある)。

### 3. キャッシュ

- 抽出の結果(選んだ Asset の id と代表数)をプロセスの中に持つ。直近の数件だけ(`MapSampleCache`)。
- 鍵は `model_key`、埋め込みの版(`Embedder.version(model_key)`)、見る人と絞り込みの範囲(利用者・グループ・タグ)、候補の id の要約(sha256)、上限。画像の追加・削除や埋め込みの更新で鍵が変わり、作り直す(ADR-0054 の `EmbeddingOrderCache` と同じ考え方)。
- `graph` と `graph/scores` は同じ関数を通り、同じ鍵を引くので、同じ引数ならノードの並びが一致する(ADR-0047 8章の約束を保つ)。
- 新しい順は計算が要らないのでキャッシュしない。

### 4. 時間とメモリの目安

- 主な計算は k-means の `n × k × 次元 × 繰り返し` と、クラスタの中の選択の `選ぶ数 × クラスタの大きさ × 次元`。**想定は 1万枚まで。**
- n = 1万、768 次元、上限 1000 で、一般的な VM の CPU の numpy でおよそ1秒。上限 5000 でも塊が分かれていれば同程度。
- ほとんど同じ画像が大半を占めて1つのクラスタが極端に大きいとき、上限 5000 では十数秒かかりうる(クラスタの中の選択が大きなクラスタに集中するため)。初回だけで、2回目からはキャッシュが効く。
- メモリは候補の全件のベクトルの行列(1万 × 768 × 4 バイト = 約 30MB)と、n × k の類似度(約 4MB)。pgvector のときは、候補の全件のベクトルを一度読む(numpy の索引では、既にメモリにある行列から取り出す)。

### 5. API

- `GET /api/embeddings/graph` と `GET /api/embeddings/graph/scores` に `sampling`(`spread` / `recent`。既定 `spread`)を足す。ほかの引数(`limit`、`group_id`、`tag`)の既定と上限は変えない。
- ノード(`EmbeddingGraphNode`)に `represents`(代表数、自分を含む)を足す。新しい順と、抽出しないときは 1。
- 応答に、使った `sampling` を返す。
- `total`(絞り込みに合い、ベクトルのある画像の数)と `truncated`(上限を超えたので、すべては返していない)の意味は変えない。
- MCP には足さない(マップは画面の機能)。

### 6. 画面

- マップの「絞り込み」パネルの上限の隣に「抽出」(全体から均等に / 新しい順)のセレクトを置く。ボタンのバッジには数えない(上限と同じく規模の調整のため。ADR-0047 9章)。
- 選択は URL(`sample=recent`。既定の全体から均等には URL に出さない)と、ブラウザの `gakei:map-prefs`(項目を足すだけなので版は 1 のまま)に覚える。優先は URL > 覚えた値 > 既定(ADR-0033 8章)。
- **ノードの大きさ:** 代表数に応じて、サムネイルと点を少し大きく描く。倍率は `1 + 0.15 × log₂(代表数)` で、上限は 1.6 倍(16 枚以上)。大きくしすぎると周りを隠すので、塊の大きさの手がかりにとどめる。当たり判定も描いた大きさに合わせる。
- **切り詰めの表示:** canvas の隅の断りを抽出方法に合わせる。全体から均等にのときは「全 N 枚から、似た画像の塊ごとに M 枚を選んで並べています。大きく描いた画像は、近くの似た画像を代表しています。」、新しい順のときは今の文言(新しい M 枚だけ)。
- 文言は日本語と英語(ADR-0015)。

## Options Considered

### 抽出の方法

| 案 | 評価 |
|---|---|
| A. k-means のクラスタごとに √サイズ で配分(採用) | 大きな塊を抑えつつ、塊の大小も残る。部品は ADR-0054 にある。決定的 |
| B. 新しい順のまま(上限を上げて対応) | 変更は要らないが、報告の偏りが直らない。上限を上げても直近の塊が密になるだけで、5000 を超えると描画が重くなる(ADR-0047 3章) |
| C. グループで層を分ける(グループごとに配分) | グループの単位では均等になるが、グループに入っていない画像には効かない。1つのグループの中の偏り(報告のケース)も残る |
| D. 一様な無作為抽出 | 計算は軽いが、件数の比がそのまま残る(大きな塊が上限の大半を取る)。乱数の種を固定しても、候補が1枚増えると選ばれる画像が大きく入れ替わる |
| E. 全件の farthest-point sampling | 広がりは最もよく残るが、外れ値に寄り、塊の中心が薄くなる。計算は `上限 × n × 次元` で、1万枚・上限 5000 では重い |

### 配分

| 案 | 評価 |
|---|---|
| A. √サイズ に比例(採用) | 大きな塊を抑え、小さな塊も必ず出る |
| B. サイズに比例 | 件数の比のままで、偏りが残る |
| C. 均等 | 塊の大小の手がかりが消える |

### 代表数の見せ方

| 案 | 評価 |
|---|---|
| A. ノードを対数で少し大きくする(採用) | 説明の文を足さずに塊の大きさが分かる。上限を付けて周りを隠さない |
| B. 数字のバッジ | 正確だが、数千のノードに数字を重ねると読めない |
| C. 見せない | 間引いたことが分からず、薄い塊と濃い塊の区別が付かない |

## Trade-off Analysis

全体から均等に選ぶと、俯瞰はしやすくなる代わりに、直近の作業の画像がすべては並ばない。直近だけを見たいときのために新しい順を残し、切り替えられるようにした。

k-means の境目では、似た画像が別のクラスタに分かれ、片方の代表に数えられないことがある。代表数は目安で、厳密な「似た画像の数」ではない。眺める用途では許容できる。

キャッシュの鍵に候補の要約を入れたので、生成のたびに作り直しになる。目安の規模なら1秒前後で、作り直すのはマップを開いた(取り直した)ときだけ。

既定を全体から均等にしたので、ADR-0047 までの「ノードは新しい順に上限まで」という前提は、新しい順を選んだときだけのものになる。ノードの並び自体は新しい順のままなので、画面の突き合わせ(ID)と配置の計算は変わらない。

## Consequences

- `GET /api/embeddings/graph` と `GET /api/embeddings/graph/scores` に `sampling` が、ノードに `represents` が、応答に `sampling` が増える。
- 上限を超える候補があるとき、既定でマップに出る画像が変わる(新しい順から、全体から均等にへ)。
- 候補が多いとき、初回の表示に1秒前後(偏った場合は十数秒)の計算が加わる。
- `history_sort` の k-means を、マップの抽出からも使う(`spherical_kmeans` として公開)。
