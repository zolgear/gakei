# ADR-0051: Mod とフック(取り込み・AI へ送る前・生成後に、外部のシステムや手元の処理をつなぐ)

**Status:** Proposed
**Date:** 2026-10-16

2026-10-16 に、ユーザーが次のように指示した。

- GAKEI に Mod(拡張機能)を作る。ストック・入力画像の前処理の後のフックや、生成の後のフックなどを処理できるようにする。
- 目的は次の3つ。
  - 企業などで、AI の処理に使われる前にチェック・記録を行うシステムと連携する。
  - 生成の後に、類似画像のチェックや侵害の判定を行うサービスと連携する。
  - 自動でローカルに保存する。

同日、ユーザーは次の3点を選んだ。

- Mod の形: 入出力を版付きの JSON の契約として1つ決め、HTTP(Webhook)と Python の Mod の両方で受ける。
- AI へ送る前のチェック: 画像の生成だけでなく、外部へ送るすべての処理に掛ける。
- フックの効力: 許可・拒否と判定の記録まで。プロンプトや画像の書き換えはしない。

## Context

- 組織での利用では、生成 AI に送る前に、送る内容(プロンプト、入力画像、送り先)を社内のシステムで検査し、記録したいことがある。情報の持ち出しの検査、利用の台帳、禁止語の確認などに使う。
- 生成した画像を、既存の著作物との類似や権利の侵害を判定するサービスに通し、その結果を画像と一緒に残したいことがある。
- 生成物を、決まったフォルダ(共有のファイルサーバー、同期されるフォルダ)に自動で書き出したいことがある。
- いま GAKEI が外部の AI へ送る処理は、次のとおり。どこかを検査から漏らすと、検査の意味がなくなる。
  - 画像の生成(`ImageProvider.execute`。OpenAI、ComfyUI、SD WebUI)
  - 自動タイトル・タグの LLM・VLM(ADR-0024)
  - アシスタントの LLM(ADR-0048)
  - リモートの埋め込み(ADR-0033、ADR-0045)
- 取り込みの後処理(自動タイトル・タグ、レーティング、埋め込み、焦点)は、`domain/ingest_hooks.py` の1か所から待ち行列に入れている。生成の出力、アップロード、スケッチ、配置、MCP、系列の取り込みが、すべてここを通る。
- ADR-0001 は、承認ワークフローと、ノードエディタ・ワークフロー構築を非ゴールにしている。ADR-0003 は「API に送った値をそのまま保存する」としている。

## Decision

### 1. 範囲

Mod は、決まった時点(イベント)で GAKEI から呼ばれ、次のどれかをする。

- **事前のチェック:** 外部の AI へ送る直前に呼ばれ、許可か拒否を返す。
- **判定の記録:** 画像や Run についての判定(類似の疑い、スコア、外部の受付番号など)を返し、GAKEI がそれを記録して画面に出す。
- **手元の処理:** 通知を受けて、Mod の側で何かをする(ローカルへの保存、外部の台帳への記録など)。GAKEI は結果を記録するだけ。

Mod にはさせないこと(この ADR では作らない):

- プロンプト、パラメーター、画像の書き換え。送った値をそのまま記録する原則(ADR-0003)を守るため。
- 人による承認待ち(「保留」にして誰かの判断を待つ)。ADR-0001 の非ゴール「承認ワークフロー」は変えない。拒否は、外部のシステムが自動で即答する場合だけ。
- 画面、API のルート、プロバイダー、設定の画面の追加。Mod の設定は、7章のマニフェストに書いた項目を、GAKEI が共通の形で出すだけ。
- Mod どうしをつないで処理の流れを組むこと(ADR-0001 の非ゴール「ワークフロー構築」)。
- Mod の配布・インストール(URL からの取得、マーケット)と、Python の Mod のサンドボックス。

### 2. イベント

| イベント | いつ | 呼び方 | 返せるもの |
|---|---|---|---|
| `asset.ingested` | Asset を取り込み、前処理(原本の保存、形式と大きさの確認、生成メタ情報の読み取り)を終えて commit した後 | 非同期 | 判定(Asset に) |
| `ai.before_send` | 外部の AI へ送る直前(下の表) | 同期(待つ) | 許可・拒否 |
| `run.finished` | Run が succeeded / failed / canceled になり、出力の Asset を commit した後 | 非同期 | 判定(Run と出力の Asset に) |

- `asset.ingested` は、取り込みの経路(`source`: `upload`、`url`、`sketch`、`mask`、`composite`、`generated`、`import`、`mcp`)を付けて呼ぶ。生成の出力も呼ぶ。受ける側が経路で絞れるよう、6章の購読に絞り込みを持たせる。
- `ai.before_send` の目的(`purpose`)と、どの時点で呼ぶか:

| `purpose` | 呼ぶ時点 | 拒否されたとき |
|---|---|---|
| `image_run` | worker が Run を running にした後、`provider.execute` の前(どのプロバイダーでも。ローカルの ComfyUI・SD WebUI も含む) | Run を failed にする。`error.code = hook_denied`、理由と Mod の名前を記録する |
| `annotation` | 自動タイトル・タグで LLM・VLM を呼ぶ前(タグの訳を含む)。ローカルの WD Tagger(ONNX)は呼ばない | その Asset の自動付与を failed にし、理由を記録する |
| `assistant` | アシスタントが LLM を呼ぶたび(道具の呼び出しの往復を含む) | その回の応答を止め、理由をチャットに出す |
| `embedding` | リモートの埋め込み(画像・文章・プロンプト)を呼ぶ前。ローカルの ONNX は呼ばない | その埋め込みを failed にし、理由を記録する |

- 外部の AI を呼ぶ処理は、上の4つの入口のどれかを通るように作る。新しく外部の AI を呼ぶ機能を足すときは、`ai.before_send` を通すことを、その機能の ADR の条件にする。
- 管理者設定の「接続を確認」(接続のテストの往復)は、送るのが検査用の固定の文だけなので対象にしない。

### 3. 契約(イベントの中身)

- すべてのイベントは、同じ形の JSON を持つ。`schema_version`(最初は `1`)、`event`、`event_id`(UUID)、`occurred_at`、`instance`(GAKEI のバージョンと、管理者が決めた名前)、`actor`(実行したユーザーの id・メール・表示名。個人モードでは `null`)、`subject`(イベントごとの中身)。
- `ai.before_send` の `subject`:
  - `purpose`
  - `target`: プロバイダー、モデル、接続先のホスト名。API キーは出さない。
  - `text`: プロンプト、ネガティブプロンプト、アシスタントのメッセージなど、送る文
  - `params`: 送るパラメーター
  - `images`: 送る画像の一覧。Asset の id、sha256、大きさ、形式、使い方(主たる入力、参照、マスク、添付)
  - `run_id`: `image_run` のとき
- `asset.ingested` の `subject`: Asset の id・種類・sha256・大きさ・形式・`source`、作った Run の id(生成の出力のとき)、レーティング(判定済みのとき)。
- `run.finished` の `subject`: Run の id・状態・プロバイダー・モデル・プロンプト・パラメーター・入力の一覧・出力の一覧(Asset の id、sha256、大きさ)・usage・エラー。
- 契約は `docs/mods.md` に書き、JSON Schema を `uv run python -m app.tools.export_mod_schema` で書き出せるようにする。項目を足すのは版を上げずに行い、消す・意味を変えるときは `schema_version` を上げる。
- **画像の渡し方:** Webhook では、購読ごとに「画像を送る」を選べる(既定はオフ。メタ情報だけ)。オンのときは `multipart/form-data` で、JSON の部分と画像の原本の部分を送る(受ける側から GAKEI へ取りに来させない。社内のシステムから GAKEI へ届かない配置が多いため)。base64 にはしない(ADR-0004)。Python の Mod には、画像を開く関数を渡す。

### 4. 応答

- `ai.before_send` の応答: `{"decision": "allow" | "deny", "reason": "...", "reference": "..."}`。`reason` は利用者に見せる文、`reference` は外部のシステムの受付番号など。
- `asset.ingested` と `run.finished` の応答: 判定の配列(省略できる)。判定は、対象の Asset(または Run)、`verdict`(`ok` / `flag` / `deny`)、`label`(短い名前。例: 類似の疑い)、`score`(0〜1、任意)、`message`、`reference`、`url`(外部の詳細へのリンク、任意)。
- **判定の効力:** Asset に対する最新の判定が `deny` の Mod が1つでもあれば、その Asset は外部の AI へ送らない。入力に使った Run は `ai.before_send` を呼ぶ前に GAKEI が拒否する(`error.code = hook_denied`)。アシスタントへの添付、VLM、リモートの埋め込みも同じ。`flag` は表示だけで、動作は変えない。
- 判定は、後から同じ Mod が送り直せば上書きされる(記録は追記で、最新を使う)。外部のシステムが後で判定を変えるときのために、受付の API を用意する(8章)。

### 5. 記録

新しい表を2つ作る。どちらも追記のみ(ADR-0003 1項)。

- `mod_invocation`: Mod の呼び出しの記録。イベント、`event_id`、Mod、対象(Run・Asset)、結果(`allow`、`deny`、`ok`、`error`、`timeout`、`skipped`)、理由、`reference`、かかった時間、日時。`ai.before_send` は、許可も拒否もすべて残す(「何を・いつ・誰が送り、何が許可したか」の証跡)。
- `mod_verdict`: 4章の判定。Asset または Run、Mod、`verdict`、`label`、`score`、`message`、`reference`、`url`、日時。

非同期のイベントの配達は、DB の待ち行列(`mod_delivery`。`queued → delivering → done | failed`。Run の表と同じ考え方、ADR-0005)にする。サーバーが落ちても、再起動の後に配り直す。失敗したら間隔を延ばしながら決まった回数まで送り直し、最後に `failed` を残す。`mod_delivery` は状態の行で、証跡ではない(古い `done` は消してよい)。

画面:

- Run の詳細に、`ai.before_send` の結果(Mod の名前、許可・拒否、理由、`reference`)を出す。
- ビューアの詳細に、判定(`label`、`score`、`message`、外部へのリンク)を出す。
- ストックとビューアで、`deny` の判定がある Asset に印を付ける。`flag` にも別の印を付ける。
- 管理者設定の Mod のページに、直近の呼び出しと配達の失敗を出す。

### 6. 失敗のとき

- `ai.before_send`: Mod ごとに待つ時間(既定 10 秒)と、失敗・時間切れのときの扱いを選ぶ。
  - 「止める」(既定。fail-closed。拒否と同じ扱いで、理由は「チェックに失敗した」)
  - 「通す」(fail-open。通したことを `mod_invocation` に残す)
- 複数の Mod が `ai.before_send` を購読しているときは、管理者が決めた順に呼び、最初の拒否で止める。
- 非同期のイベントの失敗は、GAKEI の動作を止めない。

### 7. Mod の2つの形

どちらも管理者設定の新しいページ「Mod」(`/settings/mods`。`require_admin`)で、有効・無効、購読するイベントと絞り込み(`purpose`、`source`、プロバイダー)、順番、失敗のときの扱いを決める。既定ではどれも無効。

**Webhook:**

- 画面で登録する。URL、署名の鍵、購読するイベント、画像を送るか、待つ時間を決める。
- 送る要求に署名を付ける(`X-Gakei-Signature`: 鍵による本文と時刻の HMAC-SHA256、`X-Gakei-Timestamp`)。受ける側が、GAKEI からの要求か・古い要求の再送でないかを確かめられるようにする。
- 鍵は API キーと同じく、一部も画面と API の応答に出さない。設定済みかどうかだけを出す。
- 「テスト送信」で、ダミーのイベントを送って応答を確かめられる。

**Python の Mod:**

- `MODS_DIR`(既定は `DATA_DIR/mods`)に、Mod ごとのフォルダを置く。フォルダには、マニフェスト `gakei-mod.toml` と Python のモジュールを置く。
  - マニフェストに書くもの: id、名前、版、対応する契約の版、購読するイベント、設定の項目(文字列・数値・真偽・パス・秘密。秘密は Webhook の鍵と同じく出さない)。
- 起動のときにマニフェストを読む。置いただけでは動かず、管理者が画面で有効にしたときに読み込む。
- Mod は、公開する1つのモジュール `gakei_mod` の型(イベント、判定、画像を開く関数、設定の値)だけを使う。GAKEI の内部のモジュールを import した Mod は、動作を保証しない。
- 呼ばれ方: イベントごとに `async def` の関数。同期の重い処理はスレッドへ逃がす。時間切れと例外は、Webhook と同じく6章の扱いにする。
- Mod は GAKEI のプロセスの中で、GAKEI と同じ権限で動く。置けるのはサーバーのファイルを書ける人(管理者)だけで、画面からは置けない。docs にその危険を書く。
- 依存のパッケージは同梱しない。必要なら、利用者が GAKEI の環境に入れる。Docker なら、イメージを派生させて入れる。docs に手順を書く。

**同梱の Mod「ローカルに保存」:** Python の Mod の例を兼ねて、GAKEI に同梱する(既定は無効)。

- `run.finished`(と、選べば `asset.ingested`)で、原本を決めたフォルダへ書き出す。
- ファイル名は、日時・Run・番号を使ったひな形で決める。
- 選べば、系列の情報を埋め込んだ PNG(ADR-0014)と、Run の情報の JSON を横に置く。
- 書き出せなかったときは、配達の失敗として残す。
- 保存先は GAKEI のサーバーの上のフォルダ(利用者の PC ではない)。docs にそのことを書く。

### 8. 外部からの判定の受付

非同期の判定を後から返したいシステムのために、`POST /api/mods/{mod_id}/verdicts` を作る。

- 認証は Webhook の鍵による署名(ユーザーのセッションでもアクセストークンでもない)。
- 受けた判定は、4章の応答と同じ扱いで `mod_verdict` に追記する。
- 送れる対象は、その Mod が購読しているイベントで届いた Asset と Run だけにする(`mod_invocation` で確かめる)。

### 9. ほかの機能での扱い

- **MCP(ADR-0023):** MCP で作った Run も `ai.before_send` を通る。Mod を操作するツールは作らない。Asset の情報に判定を含める。
- **見える範囲(ADR-0025):** 判定は、その Asset が見える人にだけ見せる。イベントには、実行した人の情報を含めて外部に送る。外部に送ってよいかは組織の判断で、管理者が Mod を有効にすることでその判断をしたことになる。docs にそのことを書く。
- **共有リンク(ADR-0029)、系列の ZIP(ADR-0037):** 判定は含めない(組織の内部の情報のため)。`deny` の Asset を共有・持ち出しで止めるかは、この ADR では決めない。
- **繰り返し(ADR-0042):** Run ごとに呼ぶ。
- **ADR-0001:** ゴールに「外部のシステムとのつなぎ込み(Mod とフック)」を足す。非ゴール「承認ワークフロー」に、Mod の自動の拒否はこれに当たらない、という注記を足す。

## Options Considered

| 案 | 判断 |
|---|---|
| A: 契約を1つ決め、Webhook と Python の Mod の両方で受ける | 採用。社内のシステムとは Webhook でつなぎ、手元の処理(ローカルに保存)は Python で書ける。契約が1つなので、試験と docs も1つで済む |
| B: Webhook だけ | 隔離はよいが、ローカルに保存するにも受け口のサーバーが要る。保存を組み込みの機能にすると、似た口が2つになる |
| C: Python の Mod だけ | 社内のシステムとつなぐたびに、アダプターを書いてサーバーに置くことになる。任意のコードが常に GAKEI の権限で動く |
| D: 事前のチェックは画像の生成だけ | 範囲は小さいが、VLM・アシスタント・埋め込みから画像とプロンプトが検査なしで外に出る |
| E: Mod がプロンプトや画像を書き換えられる | Run の記録に「元の値」と「送った値」の2つが要り、ADR-0003 の原則が崩れる |
| F: 人の判断を待つ「保留」 | ADR-0001 の非ゴール「承認ワークフロー」に当たる。待つ間の Run の状態、通知、画面が要る |
| G: 外部のシステムが GAKEI へ画像を取りに来る(署名付き URL) | 送る量は減るが、社内のシステムから GAKEI へ届かない配置が多い。届く前に Run が進む問題もある |

## Trade-off Analysis

- 同期の `ai.before_send` は、外部の AI を呼ぶたびに待ちが入る。自動タイトル・タグと埋め込みは取り込みのたびに走るので、検査のシステムへの要求が多くなる。購読の `purpose` の絞り込みで、管理者が範囲を決められるようにする。
- fail-closed を既定にすると、検査のシステムが止まったときに GAKEI の生成も止まる。組織の検査として使う以上、漏らさないほうを既定にする。
- Python の Mod はプロセスの中で動くので、作りの悪い Mod は GAKEI を遅くしたり落としたりできる。時間切れと例外は捕まえるが、隔離はしない。
- 判定の `deny` で外部の AI へ送らないことは、Mod が明示した拒否だけに効く。外部のシステムが判定を返す前に Edit を始めれば、その Run は止まらない。漏らしたくない場合は、`ai.before_send` を購読してそこで止める。

## Consequences

- 外部の AI を呼ぶ処理の入口が4つに決まり、新しい機能はそのどれかを通る必要がある。
- 管理者設定に「Mod」のページが増える。表が3つ増える(`mod_invocation`、`mod_verdict`、`mod_delivery`)。
- 契約(`schema_version`)と、Python の公開モジュール `gakei_mod` の互換性を保つ責任が生まれる。
- Run の失敗の理由に `hook_denied` が加わる。
