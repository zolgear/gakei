# ADR-0034: 認証の設定を管理者設定の画面から行う

**Status:** Proposed
**Date:** 2026-10-04

2026-10-04 に、ユーザーが次のように指示した(Issue #73)。

- 管理者設定に「認証」を足し、認証モードの有効化と、有効にした後の操作を画面から行えるようにする。
- OIDC を選んだ場合、管理ユーザーの設定と、設定画面からの管理者のテストログインに成功するまでは、ログイン画面を出さない。
- 通常は DB の設定が優先する。ただし、OIDC を緊急に無効化する回避策を設定ファイルに用意する。

同日、次の4点もユーザーが決めた。

- `.env` に `AUTH_MODE` を書いたら、DB より優先する(none でも oidc でも)。
- 既存の `.env` の `OIDC_*`・`AUTH_ADMIN_EMAILS` などは、DB に値が無い項目の初期値として使う。
- 画面で設定できるのは OIDC の全項目(`AUTH_SECRET` を除く)。
- テストログインはポップアップで行う。

## Context

- ADR-0019 1章では、認証モードを `.env` で切り替える。モードは起動時に固定される。
  - `main.py` は、`SessionMiddleware`(`gakei_oidc`)、`/docs` の有無、`app.state.oidc_client` をモードで組み立てる。
  - 利用者は `.env` を書いて再起動しないと OIDC を使えない。
- 誤った設定のまま有効にすると、管理者も含めて全員がログインできなくなる。
  - 誤った設定の例: 発行者の URL、リダイレクト URI、管理者のメールの書き間違い。
  - 気づくのは再起動した後で、直すにはまた `.env` を書き換えて再起動するしかない。
- 他の管理者設定はすでに画面で変えられる(ADR-0017、0024、0029、0031)。認証だけが `.env` に残っている。

## Decision

### 1. 値の出どころと優先順位

| 項目 | 優先順位 |
|---|---|
| 認証モード | `.env` に `AUTH_MODE` が**明示**されていれば `.env` → DB → 既定 `none` |
| 発行者、クライアント ID、スコープ、`PUBLIC_BASE_URL`、管理者のメール、許可ドメイン、セッションの長さ | DB → `.env` → 既定 |
| クライアントシークレット | `DATA_DIR/secrets.json` の `oidc_client_secret` → `.env` の `OIDC_CLIENT_SECRET` |
| `AUTH_SECRET` | これまでどおり(画面では扱わない) |

- DB は `app_setting` の `auth.*` キーに置く。シークレットは DB に置かない(OpenAI のキーと同じ。ADR-0012)。
- `.env` で `AUTH_MODE` を明示している間は、画面のモード切り替えを押せなくし、出どころが「.env」であることを示す(ADR-0017 の Base URL と同じ扱い)。
- **緊急の無効化:** `.env` に `AUTH_MODE=none` を書いて再起動する。DB の認証の設定は消さないので、`.env` から消して再起動すれば元に戻る。
- 画面には、各値の出どころ(画面 / .env / 既定)を出す。
- クライアントシークレットは一部も返さない。返すのは「設定済みか」と出どころだけ(ADR-0019 5章)。
- `.env` だけで oidc を使っている既存の利用者は、何もしなくても今までどおり動く。

### 2. 有効にする手順(締め出しの防止)

1. **接続を登録する。** 管理者が、ダイアログで次を入力する。
   - 発行者、クライアント ID、シークレット、スコープ、`PUBLIC_BASE_URL`
   - 入力したものは**仮登録**になり、形式の検査と Discovery 文書の取得まで行う。
   - 画面には、IdP に登録するリダイレクト URI(`{PUBLIC_BASE_URL}/api/auth/callback`)を出す。
2. **管理者のメールを設定する。**
3. **テストログインをする。** ポップアップで、仮登録の設定を使って IdP にログインする。
   - 戻り先は、通常のログインと同じ `/api/auth/callback` にする。手続き中の Cookie `gakei_oidc` に印を付けて区別する。こうすれば IdP に登録する URI を増やさずに済む。
   - 成功の条件は次の2つ。
     - ID トークンの検証が通る(ADR-0019 2章)。
     - メールが確認済みで(ADR-0019 3章 M-1)、管理者のメールに含まれている。
   - 成功したら、次のことを行う。
     - 仮登録を本登録にする。
     - 接続設定の指紋(発行者、クライアント ID、シークレットのハッシュ、スコープ、`PUBLIC_BASE_URL`)と、ログインしたメールを記録する。
4. **認証モードを oidc にして保存する。** 保存できる条件は、次の2つを満たすときだけ。
   - 記録した指紋が、今の接続設定と一致する。
   - テストでログインしたメールが、保存後の管理者のメールに含まれる。

- テストログインを個人モード(none)の間に行ったときは、そのログインのセッションを作り、Cookie を渡しておく。
  - 個人モードの間、この Cookie は使われない。
  - oidc に切り替えた瞬間から、操作していた管理者はログイン済みとして残る。
- oidc が有効な間にテストログインをしたときは、セッションを作らない。今のセッションはそのまま残る。
- 有効にするとき、`.env` から来ていた値を DB に書き写す。以後は `.env` から消しても動く。

### 3. 有効にした後の操作

- **接続を差し替える。** 2章の1と3を、もう一度行う(テストに成功するまで差し替わらない)。
  - 発行者を変えると、`app_user`(発行者とサブジェクトで一意)は別人として作り直される。
  - データの付け替えはしない。ダイアログで注意を出す。
- **管理者・許可ドメイン・セッションの長さを変える。** ページの「保存」で反映する(ADR-0031 の「保存で反映」)。
  - oidc が有効な間は、保存後の管理者のメールに、**操作している本人**が含まれていなければならない。
- **無効にする(oidc → none)。** 確認ダイアログを出してから保存する。
  - セッションと `app_user` は消さない。
  - もう一度有効にすると、そのまま使える。

### 4. 再起動なしで切り替える

- 実効の設定と、作り終えた OIDC クライアントを、プロセス内に置く(`app.state.auth_runtime`)。
  - 起動時に DB から読む。
  - 設定 API の保存が成功したら作り直す。api は1プロセスで、worker もその中で動く。
- リクエストごとにこれを見る。これまでモードや `AUTH_ADMIN_EMAILS` を `Settings` から読んでいた箇所は、すべてこちらに置き換える。
- `SessionMiddleware` は常に入れる。手続き中でなければ中身が空なので、Cookie は出ない。
- `/docs`・`/redoc`・`/openapi.json` は常にルートを置く。oidc の間は 404 を返す。
- 起動時の検査(ADR-0019 1章)は、DB を読んでから実効の設定に対して行う。
  - oidc なのに必須の値が欠けていれば、起動を中止する。
  - 中止するときは、`.env` に `AUTH_MODE=none` を書いて再起動するよう案内する。

### 5. 画面

- 管理者設定に「認証」(`/settings/authentication`)を足す(ADR-0031 1章の表に加える)。
  - 個人モードでは常に表示する。oidc では管理者にだけ表示する。
- 項目は ADR-0031 2章の種類に当てはめる。
  - 接続先: 「接続」。カードとダイアログで扱い、テストログインもここで行う。
  - モード、管理者のメール、許可ドメイン、セッションの長さ: 「保存で反映」。
- モードのスイッチは、条件を満たすまで押せなくする。理由はスイッチの近くに書く。
  - 条件は、テストが済んでいること、管理者のメールにテストした人が含まれていること、`.env` でロックされていないこと。

## Options Considered

### 緊急の無効化

| 案 | 評価 |
|---|---|
| `.env` の `AUTH_MODE` を DB より優先(採用) | ユーザーの選択。既存の変数のまま使える。none にも oidc にも固定できる |
| 専用の変数(`AUTH_FORCE_NONE=1` など) | 意味は明確だが、変数が増える。oidc に固定する手段にはならない |
| none のときは 127.0.0.1 だけで待ち受ける | LAN から認証なしで触られずに済む。ただし Docker では `-p` の都合で入れなくなる |

### テストログインの形

| 案 | 評価 |
|---|---|
| ポップアップ(採用) | 設定画面の入力が失われない。結果を元の画面に返せる |
| 同じタブで遷移 | ポップアップのブロックを気にしなくてよい。ただし、戻るまで画面を離れる |

## Consequences

- ADR-0019 の次の章は、この ADR で改める。
  - 1章「認証モードは `.env` で切り替え」
  - 3章「Admin は `.env` のメール一覧で決める」
  - `.env` は初期値と緊急時の手段になる。管理者を決める規則(メールの一覧、リクエストのたびに再評価する)は変えない。
- モードを起動時に固定しなくなる。認証を見る箇所は、すべて `auth_runtime` を経由する。
- `docs/auth.md` は画面での手順を主にし、「締め出されたとき」の節を設ける。
