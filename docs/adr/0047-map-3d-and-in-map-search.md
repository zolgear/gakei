# ADR-0047: マップを立体で見せ、マップの中で意味検索する

**Status:** Proposed
**Date:** 2026-10-11

## Context

マップ(ADR-0033 8章)は2つのタブを持ち、どちらも平面である。「地図」は umap-js の2次元の配置、「ネットワーク」は d3-force の2次元の力学モデルで、canvas にサムネイルを並べる。

ADR-0044 で EmbeddingGemma 2(768 次元)を使えるようにしてから、検索の質は上がった一方で、地図の距離感が合わなくなった。確認用のインスタンス(画像 190 枚、k=15)で近傍の類似度を測ると、次のようになる。

| 指標 | 値 |
|---|---|
| 1位の類似度(中央値) | 0.957 |
| 15位の類似度(中央値) | 0.859 |
| 1位と15位の差(中央値) | 0.079 |

距離(`1 − 類似度`)が 0.04〜0.14 の狭い帯に詰まっており、この状態で2次元に落とすと局所の構造が潰れて「近い・遠い」が読み取れない。高次元のベクトルほど、2次元の平面に収めるときの無理が大きい。

マップの中で探せないことも分かってきた。今は絞り込み(グループ・タグ)しかなく、「この文章に近い画像がどこにあるか」を知るには一度検索ページへ出る必要がある。既存の `GET /api/search/semantic` は上限 50 件(`SEARCH_MAX_LIMIT`)で、マップのノード(最大 5,000)すべてに順位を付けられない。

2026-10-11 にユーザーが「ADR にとらわれず、手元の環境で出来るかどうか・イメージ通りかを試す」と決めた。実験ブランチで作り、確認用のインスタンス(画像 190 枚に EmbeddingGemma 2 のベクトルを付けたもの)で手触りと数値を確かめてから、この ADR に起こしている。

## Decision

### 1. 範囲

- マップに**立体の見せ方**を加える。地図とネットワークの両方を立体で見せ、既定を立体にする。
- 平面の見せ方は**残す**。利用者が切り替えられるようにする(2章)。
- マップの中に**意味検索**を置く。マップのノード全件に順位を付け、強調と移動に使う(7章)。
- 地図の配置で使う**距離の取り方**を選べるようにする(6章)。
- 埋め込みは証跡ではない。来歴の列(`run`、`run_input`、`asset`)には書かない(ADR-0033 1章と同じ)。
- 次は今回作らない。
  - VR・立体視(ADR-0001 の非ゴール「凝った 3D ビューア」に近い)。見るのは普通の画面だけにする。
  - 立体の配置をサーバーで計算すること(ADR-0033 の「2D の配置」の判断と同じ理由。ブラウザで計算する)。
  - 立体の配置の保存。ブラウザの中でだけ覚える(5章)。
  - マップ内検索の結果を並べたリスト。並べて見るのは検索ページの仕事にする。

### 2. タブと見せ方を分ける

- **タブ = 何を並べるか**: 「ネットワーク」(類似度の辺でつないだ力学モデル)と「地図」(埋め込みの近さで並べた配置)。
- **見せ方 = どう見せるか**: 「立体」と「平面」。タブと直交し、どちらのタブにも効く。既定は立体。
- 見せ方は URL(`shape=flat`。既定の立体は URL に出さない)と、ブラウザの `gakei:map-prefs`(ADR-0033 8章の仕組み。項目を足すだけなので版は 1 のまま)に覚える。優先は URL > 覚えた値 > 既定。
- 立体にしか意味の無い操作(座標のライン、表示をリセット)は、平面では出さない。

### 3. 立体は canvas 2D の透視投影で描く(WebGL を使わない)

- 既存の canvas の描画(サムネイル、点、辺、選択、プレビュー)をそのまま使い、**点を透視投影してから奥行きの順に描く**。three.js などの WebGL のライブラリは入れない。
- 奥に行くほど背景色に溶かす(フォグ)。奥行きは点の大きさと濃さで表す。
- サムネイルは手前から 400 枚まで。それより奥と、小さくなったものは点にする(ADR-0033 の `THUMB_MIN_PX` の考え方を引き継ぐ)。
- 辺は投影した画面の座標で描く。カメラの後ろに出た端点を持つ辺は描かない。
- **ネットワークの辺は描く本数を 6,000 本に制限する**(`MAX_DRAWN_NETWORK_EDGES`)。類似度の高い順に、かつ「1つのノードにつき 6 本」を先に満たしてから、余りを類似度の高い順に埋める。濃い塊だけで上限を使い切らず、どのノードにも辺が残るようにするため。**力学モデルには間引く前のすべての辺を渡す**ので、配置は変わらない。

### 4. カメラと操作

- 注視点を中心に回る軌道カメラ(方位角・仰角・距離)。
- ドラッグで回転(離すと慣性)、ホイールとピンチで拡大縮小、**中ボタン・右ボタン・Shift+ドラッグ・2本指で平行移動**(掴んだ点が指に付いてくるよう、注視点の奥行きで換算する)。クリックとタップで選択。
- **開いたときに一度だけ回す。** 120°(`INTRO_SPIN_ANGLE`)を 5.6 秒(`INTRO_SPIN_DURATION_MS`)かけて、動き出しと終わりを滑らかにして止まる。立体であることを伝えるための動きで、**常時の自動回転はしない**(動き続けると狙った画像へ行きにくい)。
  - 回すのは「そのビューを開いて配置が初めて出たとき」と「表示をリセットのボタン」だけ。配置の途中経過が何度届いても回し直さない。
  - 利用者の操作(カメラを動かす、選ぶ)と**画面の設定の変更**で即座に止め、戻さない。設定を変えたあとは回し直さない。
- ボタンは「表示をリセット」(向き・距離・注視点を開いた直後に戻す。立体だけ)、「全体を表示」(今の向きのまま収める)、拡大、縮小、座標のライン。
- **座標のライン**(既定はオフ、ブラウザに覚える): 原点で交わる X・Y・Z の軸と、X-Y 平面の薄い格子。格子の間隔はデータの広がりから 1・2・5 × 10ⁿ に丸め、1方向の線が 21 本を超えるときは間隔を倍にする。向きと距離感の手がかりにする。
- 狭い幅(768px 未満)でも、回転・平行移動・拡大縮小・選択ができること(ADR-0009)。

### 5. 配置

- **地図:** umap-js を 3 成分で回す。入力(k 近傍を `setPrecomputedKNN` で渡す)と種のつけ方は ADR-0033 のまま。
- **ネットワーク:** `d3-force-3d` で 3 軸の力学モデルにする。反発・リンクの距離・乱数の種は平面と同じで、同じデータ・同じしきい値なら同じ配置になる。
- 配置はブラウザの中でだけ覚える。平面と立体、地図とネットワークで別の鍵にして混ざらないようにする。
- 配置が別のものに入れ替わったら、表示を全体に合わせ直す。

### 6. 距離の取り方を選べるようにする(地図)

Context のとおり、近傍の距離が狭い帯に詰まる。UMAP に渡す距離の作り方を3つから選べるようにする(既定は従来どおり)。

| 取り方 | 距離 |
|---|---|
| 類似度(既定) | `1 − 類似度`(従来) |
| 行ごとに正規化 | 各行(ある画像の近傍)の距離を、その行の最小〜最大で 0〜1 に伸ばす |
| 順位 | 近傍の順位を 0〜1 に正規化する(等間隔) |

- どの取り方でも、`toUmapInput` の性質(先頭は自分自身で距離 0、昇順、行の長さをそろえる)は保つ。
- 選択は URL(`dist=`)とブラウザに覚える。取り方ごとに別の配置として覚える。
- ネットワークには効かない(しきい値で辺を作るため)ので、地図のときだけ出す。

### 7. マップの中の意味検索

- マップの上部に文章の入力欄を置く。入れるとマップと同じ絞り込み(グループ・タグ・上限)で、**ノード全件の類似度**を取る。
- **絶対値のしきい値は使わない。** 使うモデルによって類似度の帯が狭く(確認用のインスタンスでは文章との類似度が 0.50〜0.67 に収まる)、固定の値では意味を持たないため。
  - **一致は順位で決める**(上位 10 / 25 / 50 / 100 件から選ぶ。既定 25)。
  - 濃淡は、返ってきた範囲(最小〜最大)で正規化して使う。
- 一致したノードを強調し、ほかを薄くする。1位は分かるようにする。一致した範囲に表示を合わせ、`n` / `p` で順位の高いほうから巡れる。
- 検索の文章は URL(`q=`)に置く。ブラウザには覚えない(次に開いたときに勝手に絞り込まれないように)。
- 検索の結果は前の文章の結果を残さない(別の一致を一瞬強調してしまうため)。

### 8. API

マップのノード全件にスコアを付けるため、`GET /api/embeddings/graph/scores` を足す。

- クエリは `q`(必須)、`limit`、`group_id`、`tag`(繰り返しで AND)。`GET /api/embeddings/graph` と同じ既定・同じ上限。
- 応答は `model_key`、`query`、`ids`、`scores`(コサイン類似度、小数4桁)、`total`、`truncated`。**同じ引数なら `ids[i]` は `graph` の `nodes[i].id` と一致する**(同じ `candidate_ids` → `index.subset` を通るため)。画面は ID で突き合わせる。
- 対象は画像だけ。指示(プロンプト。ADR-0045)は対象外。
- `GET /api/search/semantic` の上限(50 件)は変えない。利用者に見せる検索の意味を変えないため。

### 9. 画面

- マップの上部は**1段**にする: 見出し / タブ(ネットワーク・地図)/ 見せ方(立体・平面)/ 文章で探す / 「絞り込み」/「表示」。
  - **絞り込み**(どのデータを並べるか): グループ、タグ、上限、近傍の数。ボタンのバッジは**グループとタグの数だけ**を数える(上限と近傍の数は常に値を持つ規模の調整で、覚えた値のせいで既定のつもりの画面にバッジが残るため)。
  - **表示**(どう見せるか): 類似度のしきい値と系列の辺(ネットワーク)、距離の取り方(地図)、一致の件数(検索中)。
  - どちらも canvas に**重ねて**開く(表示エリアの高さを奪わない)。`aria-expanded` / `aria-controls`、Esc で閉じてボタンに焦点を戻す、外側を押しても閉じる(このときは焦点を戻さない。押した先の操作を奪わないため)。
  - 現在の値はボタンに添える(「表示 · 0.80」など)。
- 「辺 N 本」「一致 N 件」「上限で切った旨」は canvas の隅に薄く重ねる。
- 狭い幅(768px 未満)では見出しを省いて2段にし、パネルは下からのシートにする。
- ADR-0033 8章の、選択カード・プレビューパネル・サイドバーの扱い・覚える値の規則は、そのまま引き継ぐ。

### 10. 依存

- フロント: `d3-force-3d`(MIT)を足す。`d3-force`(ISC)は平面で使い続ける。`umap-js` はそのまま(成分の数を変えるだけ)。
- 第三者ライセンス表記(ADR-0021)は既存の仕組みで自動的に入る。
- バックエンドの依存は増えない(スコアの計算は既存の numpy / pgvector の経路)。

### 11. 実機での確認(2026-10-11)

**近傍の保持**(元の空間での上位近傍が、配置でも上位近傍に残る割合。確認用のインスタンス、190 枚、k=15)

| 距離の取り方 | 2D(K=5 / K=10) | 3D(K=5 / K=10) |
|---|---|---|
| 類似度 | 57.1% / 64.6% | 62.2% / 67.1% |
| 行ごとに正規化 | 58.1% / 64.7% | 63.4% / 66.9% |
| 順位 | 63.1% / 66.9% | 65.7% / 70.0% |

**点数による差**(合成データ。256 次元、塊あり、K=10)

| 点数 | 2D | 3D |
|---|---|---|
| 300 | 17.8% | 26.1% |
| 1,000 | 6.7% | 12.4% |
| 2,500 | 2.5% | 5.0% |

点が増えるほど平面の混雑が効き、立体は約2倍の近傍を保つ。

**辺の描画**(ソフトウェア描画のヘッドレスの Chrome、1600×900、点 4,000 個、1フレーム)

| 辺の本数 | 1フレーム |
|---|---|
| 2,000 | 8.8ms |
| 6,000 | 9.6ms |
| 20,000 | 14.8ms |
| 40,000 | 22.7ms |

点と消去だけで 8ms ほどかかるので、辺そのものの代価は 6,000 本で約 1ms。60fps(16.7ms)に収まる限界は 2 万本あたりで、余裕を見て既定を 6,000 本にした。

**表示エリア**(上部を1段にまとめた効果): 1920×1080 で 812px → 956px、768 幅で 756px → 862px。

## Options Considered

### 立体の描画

| 案 | 評価 |
|---|---|
| A. canvas 2D の透視投影(採用) | 新しい依存が要らない。既存の描画(サムネイル、辺、選択、プレビュー)をそのまま使える。実測で 4,000 点 + 6,000 辺が 1フレーム 10ms 弱に収まる |
| B. three.js(WebGL) | 点が数万でも滑らかで、見た目の演出もしやすい。一方で依存が大きく、サムネイルをテクスチャに載せる仕組みを作り直すことになる。今の規模(上限 5,000 点)では必要ない |
| C. 立体にせず、距離の取り方だけ直す | 最も安いが、改善は限定的(2D で 57% → 63%)。点が増えるほど平面の混雑が効く(11章) |

B は、点の上限を大きく上げたくなったときに改めて検討する。

### 次元削減

| 案 | 評価 |
|---|---|
| A. UMAP を 3 成分で(採用) | 入力(k 近傍)も種のつけ方も今のまま。計算時間もほぼ変わらない |
| B. PCA の 3 成分 | 依存は無いが、塊が分かれにくい(ADR-0033 の判断と同じ) |
| C. ベクトルの次元を落として直接使う | 768 → 3 は情報が落ちすぎる。MRL の 256 次元でも地図にはならない |

### マップの中の検索のスコア

| 案 | 評価 |
|---|---|
| A. 全件にスコアを返す API を足す(採用) | マップのノードすべてに順位が付く。並びが `graph` と一致するので突き合わせが軽い |
| B. `GET /api/search/semantic` の上限を上げる | 利用者に見せる検索の意味(上位 N 件を並べる)が変わる。マップのためだけに上限を 5,000 にするのは筋が悪い |
| C. ブラウザで検索のベクトルを作る | 文章側のモデルをブラウザに持つことになる。重く、モデルの管理も二重になる |

### 一致の決め方

| 案 | 評価 |
|---|---|
| A. 順位(上位 N 件)(採用) | モデルによらず意味が同じ。帯が狭いモデルでも効く |
| B. 絶対値のしきい値 | モデルごとに適切な値が違い、EmbeddingGemma 2 では 0.50〜0.67 に収まるため、利用者が決められない |

### ネットワークの立体化

| 案 | 評価 |
|---|---|
| A. `d3-force-3d`(採用) | MIT。API が d3-force とほぼ同じで、変更は 40 行程度。依存は d3 系の小さなものだけ |
| B. 自前の3次元の力学モデル | 作る意味が無い |
| C. ネットワークは平面のままにする | 見せ方の切り替えが片方にしか効かず、分かりにくい。立体の canvas は共通なので、平面のままにしても削れるコードは無い |

## Trade-off Analysis

- **立体は読み取りやすさと引き換えに操作が要る。** 静止画(スクリーンショットや資料)では奥行きが伝わらず、平面のほうが分かりやすい。だから平面を残し、切り替えられるようにした。
- **常時の自動回転はしない。** 立体感は伝わるが、狙った画像へ行くのが難しくなる。開いたときの一度だけにして、操作で即座に止める。
- **canvas 2D のままにしたので、点と辺の数に上限が要る。** 辺は 6,000 本、サムネイルは手前 400 枚で間引く。上限はどれも名前付きの定数にして、後から調整できるようにした。
- **距離の取り方を増やすと、配置の再現性の説明が増える。** 取り方ごとに別の配置として覚え、画面にも選択を出すことで、「同じ条件なら同じ配置」を保つ。
- **マップ内の検索のための API が1つ増える。** 既存の検索 API の意味を変えずに済む代わりに、絞り込みの引数を二重に持つ(呼ぶ側が揃える責任を持つ)。

## Consequences

- マップの見せ方は、この ADR が ADR-0033 8章のマップの記述を置き換える(ADR-0033 のそれ以外の決定はそのまま)。
- 画面に新しい依存(`d3-force-3d`)が1つ増える。第三者ライセンス表記に載る。
- 平面と立体の描画が1つの canvas に統合され、見せ方の違いは投影の実装(平面 / 立体)に閉じる。マップに機能を足すときは1か所で済む。
- 2次元の地図のビュー(`UmapView`)は、見せ方の「平面」で使い続ける。
- `docs/embeddings.md` のマップの説明を書き直す必要がある。
