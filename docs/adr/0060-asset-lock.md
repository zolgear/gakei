# ADR-0060: ロック(納品・共有・提出した画像を消せないようにする)

**Status:** Proposed
**Date:** 2026-11-01

2026-11-01 にユーザーが次のように決めた。

- 「納品済み」のような状態は持たない。
- 代わりに、納品・共有・提出したものにロックを付け、削除を防げるようにする。
- ロックした画像の祖先(元になった画像と Run)も消せないようにする。

## Context

預かった素材から作った画像(ADR-0059)や、取引先に渡した画像は、渡した後も「何を渡したか」と「どう作ったか」を示せなければならない。今は、本人なら Run も画像もいつでも消せる(論理削除。ADR-0003、ADR-0008)。消しても行は残るが、画面からは見えなくなり、系列のグラフからも外れる。整理のつもりで消した中に、渡した画像やその元が混ざると、後から示すのに手間がかかる。

「納品済み」の状態を持つと、承認や確認の流れ(ADR-0001 の非ゴール)に近づき、状態の意味も組織ごとに違う。必要なのは状態ではなく、「これは消さない」という印である。

## Decision

### 1. ロックの対象と効果

- **ロックは Asset に付ける。** 個人モードでも認証モードでも使える。
- **ロックした Asset は消せない。** Asset の削除と、その Asset を出力した Run の削除を拒否する(409。理由を出す)。
- **ロックした Asset の祖先も消せない。** 主たる親に限らず、系列をたどって現れる入力の Asset と、それを作った Run(ADR-0003)。どう作ったかを示すため。祖先の削除のボタンは押せない状態にし、理由をツールチップで示す(4章)。
- ロックは削除だけを止める。グループの出し入れ、タイトル・タグの編集、お気に入りは、これまでどおりできる。

### 2. 付け方と外し方

- **付けられる人:** その Asset が見える人(ADR-0025、IP の派生物は ADR-0059 6章)。
- **付けるときの項目:** 種類(`delivered` 納品 / `shared` 共有 / `submitted` 提出 / `other` その他)と、メモ(任意。渡した先や受付番号など。形式は縛らない)。
- **外せる人:** 付けた人と管理者。IP の派生物は、その IP の担当者も外せる。
- ロックは `asset_lock`(asset_id、kind、note、locked_by_user_id、locked_at、unlocked_by_user_id、unlocked_at)に持つ。外すときは行を消さず、外した人と時刻を書く(状態の遷移。ADR-0003 の追記のみの規則と同じ扱い)。1つの Asset に、外していないロックは1つまで。付け直すと新しい行。
- 付けたことと外したことは、証跡(ADR-0059 7章の `audit_event`。`asset.lock`、`asset.unlock`)にも残す。

### 3. ほかの処理での扱い

| 処理 | 扱い |
|---|---|
| `reconcile_storage`(ADR-0046) | 原本の無いロックした Asset とその祖先は、消さずに報告だけする |
| Mod の拒否による「画像を残さない」(ADR-0051 4章) | ロックより優先する(安全のための処理なので)。ロックは残り、画像が無いことを示す |
| IP 素材の原本の破棄(ADR-0059 9章) | 素材はロックの対象にしない。祖先として守られていても、契約に基づく破棄はできる(行と来歴は残る) |
| 系列の書き出し(ADR-0037)、共有リンク(ADR-0029) | ロックの有無と種類を含めない(組織の内部の情報のため) |

### 4. 画面

- 付け外しはビューアで行う。上の操作の並びに錠前のボタン(お気に入りの右)を置き、押すと種類とメモの小さなダイアログを開く。ロック中は錠前を塗り、同じボタンで中身(種類、メモ、日時、付けた人)を見て、外せる人には「ロックを外す」を出す。
- ロックした画像は、履歴のカードとストックのタイルで、お気に入りの下に鍵の印を出す。
- ロックした画像と祖先の削除のボタンは、押せない状態にし、理由をツールチップで示す(ビューア、履歴のカード、ストックのタイル)。
- 履歴の絞り込みに「ロック」を足す(ADR-0054 の絞り込みの並び)。
- 狭い幅でも付け外しができること(ADR-0009)。

## Options Considered

### Option A: 「納品済み」の状態を持つ
**Pros:** 一覧で状態が分かる。
**Cons:** 状態の意味が組織ごとに違い、確認や承認の流れに広がりやすい(ADR-0001 の非ゴール)。

### Option B: ロック(採用)
**Pros:** 意味が「消さない」の1つで明確。種類とメモで、何のためのロックかを残せる。
**Cons:** 祖先まで守るので、消せない理由が利用者に分かるよう画面で示す必要がある。

### Option C: 削除をなくす(全部消せない)
**Pros:** 記録が確実に残る。
**Cons:** 試行錯誤の画像を整理できない。ストックと履歴が使いにくくなる。

### 祖先を守るか

| 案 | 評価 |
|---|---|
| ロックした画像だけ守る | 単純だが、元の画像や素材を消すと、どう作ったかを画面で示せなくなる |
| 祖先も守る(採用) | 系列が欠けない。消せない理由の表示が要る |

## Trade-off Analysis

決め手はユーザーの判断で、状態ではなく印にする。守る範囲を祖先まで広げるのは、渡した画像について「どう作ったか」を後から示せることが、この印の目的だから。削除は論理削除なので行は消えないが、画面から外れると示すのに手間がかかる。

## Consequences

- `asset_lock` の表が加わる(マイグレーション)。
- Asset と Run の削除の API が、ロックとその祖先を確かめるようになる。
- `reconcile_storage` が、ロックした Asset とその祖先を消さなくなる。
- 履歴の絞り込みに「ロック」が加わる。
