# ADR-0004: 画像の保存と配信(4K対応)

**Status:** Proposed
**Date:** 2026-09-21

## Context

本ツールを作る直接の動機は、Open WebUI のようなチャット型の UI で4K以上の画像が表示できないことにある。原因は、画像を base64 のままメッセージ本文(Markdown)に載せる構造にある。4KのPNGは十数MB以上になり、base64 では更に約1.33倍になる。

また、API のレスポンスは `b64_json` で返るため、誰かがデコードして保存しなければ成果物は残らない。入力画像は1枚最大50MBまでありうる。

## Decision

1. **画像は必ずバックエンドでデコードして Azure Blob Storage に保存する。base64 をブラウザに渡さない。DBにも入れない。**
2. Blob のキーは内容のハッシュから作る: `assets/{sha256の先頭2文字}/{sha256}.{拡張子}`。同じ内容は1つだけ保存される。
   - 注記(2026-09-29): ローカルFS(`LocalFsStore`)のキー規則は [ADR-0026](0026-storage-directory-hierarchy.md) で改めた(プロバイダー・モデル別、月別のフォルダに日時_短ID のファイル名で保存し、同じ内容は DB で探して最初のファイルを共有する)。既存の原本はこのキーのまま読み出す。本線(Azure Blob)のキー規則は本線の着手時に改めて決める。
   - 注記(2026-09-30): [ADR-0028](0028-object-storage-option.md) で、Azure Blob Storage と S3 互換ストレージも保存先に選べるようにし、キー規則はローカルFSと同じ(ADR-0026)と決めた。
3. 原本は不変。上書きも変換もしない(証跡の正本)。ただし `download=1` で PNG の原本をダウンロードするときは、応答にだけ GAKEI の系列情報(iTXt チャンク `gakei`)を加える。保存している原本は変えない(2026-09-24 追記、ADR-0014)。
4. 保存時に worker が派生画像を作る。
   - サムネイル: 長辺 512px, WebP(ギャラリー用)
   - プレビュー: 長辺 2048px, WebP(詳細画面の初期表示用)
   - 原本: ズーム時とダウンロード時のみ読み込む
5. 配信は API 経由のストリーミングとする(`GET /api/assets/{id}/content?variant=thumb|preview|original`)。認可チェックを通し、`ETag` と `Cache-Control: private, immutable` を付ける。
6. ビューアは通常の `<img>` とパン/ズームで実装する。タイル分割(Deep Zoom)は行わない。
7. アップロードは API に multipart で送る。上限は 50MB(API の入力上限に合わせる)。

## Options Considered

### 配信方式

| 案 | 評価 |
|---|---|
| A: API 経由でストリーミング(採用) | 認可と監査が1か所で済む。Blob をプライベートエンドポイントに閉じられる。利用者が組織内の少人数なら負荷は問題にならない |
| B: 短時間有効な SAS URL にリダイレクト | API の負荷は減るが、ブラウザから Storage に直接届くネットワーク経路が必要。URL が有効期間中は持ち出せる |
| C: Blob を公開/CDN 配信 | 組織内専用・証跡の要件に反する |

### ビューア

| 案 | 評価 |
|---|---|
| A: `<img>` + パン/ズーム(採用) | 最大 3840×2160(約830万画素)はブラウザが普通に扱える。実装が小さい |
| B: タイル分割(OpenSeadragon 等) | 数万px級の画像向け。4Kには過剰 |

## Trade-off Analysis

A の配信方式は API がボトルネックになりうるが、サムネイルとプレビューで転送量の大半を削れるため、原本の転送は「ズームした時」と「ダウンロード時」に限られる。負荷が問題になったら B に切り替えられるよう、URL の発行はサーバー側の1関数に閉じ込めておく。

## Consequences

- 4K 画像が劣化なく表示・ダウンロードできる。
- 原本のダウンロードを監査イベントとして記録できる(ADR-0006)。
- ストレージは原本+派生2種で増える。派生は再生成できるので、バックアップ対象は原本のみで良い。
- Blob Storage の論理削除とバージョニングを有効にして、誤削除に備える。
