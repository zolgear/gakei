# ADR-0026: 原本をプロバイダー・モデル別のフォルダに保存する(ローカルFS)

**Status:** Proposed
**Date:** 2026-09-29

2026-09-29 にユーザーが次の3点を決めた。

- 原本そのものの置き場所を階層にする(閲覧用のリンクを別に作る方式は採らない)。
- フォルダは「モデル/年月」、ファイル名は「日時_短ID」にする。
- 既存の画像は移さず、新しい画像だけを新しい階層に保存する。

同日、この ADR の内容がユーザーに承認された。

## Context

ADR-0004 は、原本を内容のハッシュで決まるキー `assets/{sha256の先頭2文字}/{sha256}.{拡張子}` に保存すると決めた。同じ内容は 1 つのファイルを共有でき、キーの衝突も起きない。一方で、`data/` をファイルマネージャーで開いても、どのプロバイダーのどのモデルで、いつ作った画像なのか分からない。モデル単位での退避やバックアップもしにくい。

Issue [#16](https://github.com/zolgear/gakei/issues/16)。

## Decision

### 1. キーの規則(ローカルFS)

新しく保存する原本のキーを、次のようにする。

| 種類 | キー |
|---|---|
| 生成画像 | `assets/{プロバイダー}/{モデル}/{YYYY-MM}/{YYYYMMDD-HHMMSS}_{短ID}.{拡張子}` |
| ComfyUI の生成画像 | `assets/comfyui/{ワークフロー名}/{YYYY-MM}/{YYYYMMDD-HHMMSS}_{短ID}.{拡張子}` |
| アップロード | `assets/uploads/{YYYY-MM}/{YYYYMMDD-HHMMSS}_{短ID}.{拡張子}` |
| マスク | `assets/masks/{YYYY-MM}/...` |
| スケッチ | `assets/sketches/{YYYY-MM}/...` |

例: `assets/openai/gpt-image-2.5-sunburst/2026-09/20260929-093015_1a2b3c4d.png`

- **短ID** は Asset の id(UUID)の先頭 8 文字。同じ秒に同じモデルで複数枚作っても区別できる。万一同じ名前のファイルがあれば、末尾に `-2`、`-3` を付ける。
- **日時** は、サーバーのローカル時刻で、Asset を作った時刻。Docker では `TZ` で変えられる。
- **ComfyUI** の Run の `model` はワークフローの ID なので、保存する時点のワークフロー名をフォルダ名にする。あとでワークフロー名を変えても、保存済みのファイルは動かさない。
- 利用者ごとのフォルダは作らない。ファイルの置き場所は画面や API に出ないため、見える範囲(ADR-0025)には影響しない。
- 派生画像(サムネイル、プレビュー)は、これまでどおり `derived/{sha256}/` に置く。人が見るためのものではなく、内容から作り直せるため。

### 2. フォルダ名の正規化

プロバイダー名、モデル名、ワークフロー名をフォルダ名にするときは、次のようにする。

- 英数字と `.` `_` `-` 以外の文字は `_` に置き換える。日本語のワークフロー名も `_` になる。どの OS でも、どのファイルシステムでも同じ名前で扱えるようにするため。
- `_` が続いたら 1 つにまとめ、前後の `.` `_` は取り除く。
- 長さは最大 64 文字にする。
- 空になった場合は `unknown` にする。Windows の予約名(`CON`、`NUL`、`COM1` など)に当たる場合は、先頭に `_` を付ける。

### 3. 同じ内容の画像

- 原本を保存する前に、同じ sha256 の Asset(論理削除済みを含む)があるかを DB で探す。あれば、そのファイル(`blob_key`)を共有し、新しいファイルは書かない。ファイルの重複を作らないという ADR-0004 の性質を保つため。
- そのため、同じ内容の画像は、最初に保存したときの場所に 1 つだけ置かれる。後から別のモデルで同じ画像ができても、そのモデルのフォルダには現れない。
- 共有するのはファイルだけで、Asset の行は別になる。ファイルを誰と共有しているかは画面に出ない(ADR-0025)。

### 4. 既存の画像

- 既存の画像は移さない。`asset.blob_key` はそれぞれの保存場所を指したまま残り、読み出しは古いキーでも新しいキーでも動く。
- 移行ツールは作らない。必要になったら、この ADR を改めて足す。

### 5. 注意

- `data/` の中のファイルを、ファイルマネージャーで直接消したり動かしたりしない。DB の `blob_key` と合わなくなり、画像が表示できなくなる。削除は画面から行う(論理削除)。この注意は `docs/` に書く。
- フォルダをまるごとバックアップに取るのは構わない。

### 6. 本線(Azure Blob)との関係

この ADR の対象はローカルFSの実装(`LocalFsStore`)だけ。本線の Blob のキー規則(ADR-0004)は、本線に着手するときに改めて決める。保存の抽象(`AssetStore`)には、キーを決めるための情報(種類、プロバイダー、モデル、作成時刻、Asset の id)を渡せるようにする。

## Options Considered

### Option A: 原本の置き場所を階層にする(採用)
**Pros:** ファイルの実体が 1 つで分かりやすい。フォルダをそのままバックアップに取れる。
**Cons:** 同じ内容の画像は最初の場所にしかない。保存の前に DB で同じ内容を探す必要がある。

### Option B: 内容アドレスのまま、閲覧用のハードリンクを並べる
**Pros:** DB と保存の仕組みを変えない。同じ内容の画像を、複数のモデルのフォルダに見せられる。
**Cons:** リンクを消しても容量は空かない。ハードリンクは同じファイルシステムの中でしか張れない。実体と見かけが二重になり、分かりにくい。

### Option C: 既存の画像も移す(移行ツール)
**Pros:** 古い場所と新しい場所が混ざらない。
**Cons:** 移動の途中で失敗したときの復旧を考える必要がある。ユーザーの判断で見送った。

## Trade-off Analysis

決め手はユーザーの判断で、実体が 1 つで分かりやすい Option A を採る。同じ内容の画像が最初の場所にしかない点は、実際にはほとんど起きない(生成画像が他の画像とバイト単位で一致することはまれで、起きるのは同じファイルの再アップロードくらい)。

## Consequences

- 新しい原本は、プロバイダー・モデル別、月別のフォルダに、日時順に並ぶ。
- 古い原本は `assets/{2文字}/` に残り、しばらくは 2 つの規則が混ざる。
- 保存の前に、sha256 で DB を 1 回引く(`asset.sha256` には索引がある)。
- ADR-0004 のキー規則のうち、ローカルFSの部分をこの ADR で改める。
