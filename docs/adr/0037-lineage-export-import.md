# ADR-0037: 系列の持ち出し(エクスポート)と取り込み(インポート)

**Status:** Proposed
**Date:** 2026-10-07

## Context

ある画像の系列(祖先の Asset と Run、プロンプト、パラメーター)を、ファイルにまとめて持ち出す手段がない。今あるのは次の2つで、どちらも系列の画像そのものは渡せない。

- ダウンロードした PNG への系列情報の埋め込み(ADR-0014)。祖先の記録は入るが、祖先の画像は入らない。取り込んだ側では「埋め込み(未検証)」のノードとして見える。
- 共有リンク(ADR-0029)。ログイン不要で見せるだけで、相手の GAKEI には取り込めない。

利用者からの要望(Issue #87、2026-10-07):

- 系列を ZIP で持ち出す。範囲は共有リンクと同じく「この画像と祖先」か「系列全体(子孫も)」。中身は原本の画像と Run の記録(JSON)。
- **別の利用者が出力した系列を、自分の GAKEI(同じインスタンスの別の利用者、または別のインスタンス)にコピーして、続きの Edit ができるようにしたい。**

取り込みは、この GAKEI で実行していない Run の記録を DB に書くことになる。Run の来歴は「この GAKEI で実際に API を呼んだ証跡」(ADR-0003)なので、取り込んだ記録と見分けがつかなくなってはいけない。

## Decision

### 1. 持ち出し
- Asset の画面(ビューアの操作、系列グラフのノードのメニュー)から「系列を書き出す」。範囲は **「この画像と祖先」/「系列全体」** から選ぶ。範囲の計算は共有リンクと同じ `shares.collect_scope`(`ancestors` / `lineage`)を使う。見える範囲(ADR-0025)、論理削除済みを含めないこと、ノード数の上限(1000)も共有リンクと同じ。
- 範囲の Asset を生んだ Run(`produced_by_run_id`)と、その Run の入力の対応を含める。入力のうち範囲に入らない Asset(見えない、削除済み)は、ID を出さず「含めていない入力」として数だけ書く。
- ZIP の中身:
  - `manifest.json`: 形式名と版(`gakei.lineage-export/1`)、書き出した日時、GAKEI の版、範囲、起点の Asset ID、Asset の一覧、Run の一覧。
    - Asset: ID、sha256、種類(upload / generated / mask / sketch)、MIME、寸法、バイト数、作成日時、生んだ Run の ID と出力の順番、スケッチの下地(`source_asset_id`)、ZIP の中のファイル名。
    - Run: ID、プロバイダー、モデル、操作、プロンプト、`params`(API に送った値そのまま)、状態、エラー、usage、作成・終了日時、実行者の表示名、入力(Asset ID、役割、位置)。
  - `assets/{asset_id}.{拡張子}`: 原本。**保存しているバイト列のまま**(系列情報を埋め込まない。sha256 で照合できるように)。
- 失敗した Run も、範囲の Asset に関わるものは含める(失敗も証跡。ADR-0005)。範囲の Asset を生んでいない失敗の Run は含めない。
- タイトル・タグ・グループ・埋め込みベクトルは含めない(証跡ではなく、取り込んだ側で付け直せる)。
- 書き出しはサーバーで ZIP を作ってダウンロードさせる(大きいときはストリーミング)。

### 2. 取り込み
- ストックのアップロードの近くに「系列を取り込む」を置き、ZIP を選ぶ。取り込んだ Asset と Run の持ち主は **取り込んだ利用者** になる(ADR-0025 の見える範囲もその人のもの)。同じインスタンスの別の利用者の系列も、取り込めば自分のものとして見え、続きの Edit ができる。
- 画像: 各原本を通常の取り込み(`ingest`)で Asset にする。ZIP の sha256 とファイルの中身が一致しなければ、その ZIP 全体を断る。同じ利用者がすでに同じ内容の Asset を持っていれば、それを使う(今のアップロードと同じ。ADR-0025 で他人の Asset は再利用しない)。
- Run: **新しい Run の行を作り、取り込んだものだと分かるようにする。**
  - `run.origin = 'import'`。状態は書き出し時のもの(成功・失敗)をそのまま入れ、キューには載せない(実行しない)。`created_by_user_id` は取り込んだ利用者。
  - 元の記録は、新しい表 `run_import`(run_id、書き出し元の Run ID、元の実行者の表示名、元の作成・終了日時、書き出した GAKEI の版、取り込んだ日時)に置く。来歴の列なので追記のみ(ADR-0003)。
  - `provider` / `model` / `params` / `prompt` は書き出し時の値をそのまま入れる。この GAKEI に無いプロバイダーやモデルでもよい(実行しないため)。
  - 入力(`run_input`)は、取り込んだ Asset に付け替える。ZIP に含まれていない入力は付けない(主たる親が欠けることがある)。
- 画面: Run の詳細と系列グラフで、取り込んだ Run に「取り込み」の印を付け、元の実行者と日時を出す。**検証していない記録である**ことを説明に書く(ZIP は書き換えられるため)。
- 取り込んだ Run は、MCP の生成の上限(ADR-0023 5章)、料金の集計、実行中・待機中の件数に数えない。
- 同じ ZIP を同じ利用者がもう一度取り込んだときは、`run_import` の書き出し元の Run ID で見つけて、新しい Run を作らない(Asset も内容で再利用されるので、何も増えない)。別の利用者が取り込めば、その人の分が別に作られる。
- 上限: ZIP の大きさ(既定 1 GiB、管理者設定は作らず定数)、ファイル数(Asset 1000 件)、1 ファイル 50 MB(アップロードと同じ)、展開後の合計。超えたら中身を読まずに断る。ZIP のパスはファイル名として使わない(展開してディスクに書かない)。
- 取り込みは 1 回の要求で行い、途中で失敗したら何も残さない(DB は1つのトランザクション。保存先に書いた原本は、内容で共有するので残っても害はない)。

### 3. 作らないもの
- MCP のツール(持ち出し・取り込み)。必要になったら決める。
- 書き出しへの署名、取り込んだ記録の検証(C2PA と同じく非ゴール。ADR-0001)。
- タイトル・タグ・グループの持ち出し。

## Options Considered

### 取り込んだ Run の扱い

#### A. `origin = 'import'` の Run を作り、元の記録を `run_import` に置く(採用)
**Pros:** 系列グラフ・Run の詳細・続きの Edit が、今の仕組みのまま使える。取り込んだものは印で見分けられる。
**Cons:** 実行していない Run の行が増える。集計などで `origin` を見て除く必要がある。

#### B. 画像だけ取り込み、記録は埋め込み(未検証)ノードとして見せる(ADR-0014 と同じ)
**Pros:** Run の表に手を入れない。
**Cons:** 祖先の画像を Asset にしても、Run でつながらないので系列グラフがつながらない。続きの Edit の親子は付くが、祖先は「未検証の埋め込み」としてしか見えず、要望(系列ごとコピー)に合わない。

#### C. 元の Run ID のまま行を作る
**Cons:** 別のインスタンスや同じインスタンスで ID が衝突する。同じインスタンスの他人の Run と同じ ID を持つと、見える範囲(ADR-0025)の判定が混乱する。

## Trade-off Analysis

要望の中心は「他人の系列を自分の系列として続けたい」ことで、系列グラフがつながらない B では満たせない。A は来歴の表に「実行していない Run」を加えるが、`origin` と `run_import` で区別でき、追記のみの規則も守れる。取り込んだ記録は ZIP を信じるしかないので、画面で未検証であることを明示する。

## Consequences

- Run に `origin = 'import'` が加わる。Run を数える処理(上限、料金、実行中の件数、履歴の絞り込み)は、取り込みを数えるかを決める必要がある(数えないのを既定にする)。
- 新しい表 `run_import`。
- 同じインスタンスの他人の系列も、ZIP を介せば自分のものとしてコピーできる(見える範囲の原則は変えない。見せたい側が書き出して渡す操作が要る)。
