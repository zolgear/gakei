# ADR-0054: 履歴の並べ替え(日付・グループ・似た画像の順)

**Status:** Proposed
**Date:** 2026-10-23

## Context

履歴ページ(ADR-0009)は Run を新しい順に並べるだけである。表示の形(重ねるカード、石積み、行揃え)を選べるようになり、画像を眺める使い方が増えた。利用者から次の3つの並べ方を求められた。

1. **日付:** 今の新しい順。日付の変わり目が分かるように区切りを入れたい。
2. **グループ:** ADR-0022 のグループごとにまとめて見たい。
3. **似た画像の順:** 見た目の似た画像が隣り合うように並べたい(ADR-0033 の画像の埋め込みを使う)。起点の画像は選ばず、履歴全体を1列にする。

関連する決まり:

- ADR-0003: Run と Asset の二部グラフ。履歴の単位は Run で、1つの Run が複数の出力を持つ。
- ADR-0022: 1つの Asset が属するグループは1つだけ(`ux_asset_group_member_asset_id`)。グループの並びは利用者が決める `position`。
- ADR-0025: 認証モードでは本人のものだけを見せる。一覧は `visible_runs_query` / `asset_visible` / `group_visible` を通す。
- ADR-0033: 埋め込みは `model_key` ごとに保存し、使うのは管理者が選んだ1つ。SQLite と pgvector の無い PostgreSQL では numpy で全件と比べる。

## Decision

### 1. 並べる単位

| 並べ方 | 単位 | 画像の無い Run(失敗・待機・実行中・キャンセル) |
|---|---|---|
| 日付(既定) | Run(今のまま。表示で出力ごとに展開するのも今のまま) | 出す |
| グループ | 画像(生成された Asset) | 出さない |
| 似た画像の順 | 画像(生成された Asset) | 出さない |

- グループと似た画像の順は、画像の並びなので、画像の無い Run は並べようがない。画面で特に断りは出さない。ソートのメニューに副題は付けず、絞り込みの「失敗」と組み合わせると一覧が空になる(「該当なし」の表示)ことで足りるとする。
- 対象の画像は、見える Run(`run_visible`、削除されていない)が作った、削除されていない生成画像(`kind = generated`)だけ。アップロード・スケッチ・マスクは履歴に出ないので、ここでも出さない。画像を残さなかった Asset(ADR-0051)は、日付の並びと同じく置き換えの表示で出す。
- ADR-0022 により画像のグループは1つだけなので、1枚の画像は1か所にだけ出る。将来グループが多対多に戻ったら、それぞれのグループに出す(同じ画像が2回出る)ことにし、その時にこの ADR を改める。

### 2. グループの並びと、中の順

- グループの並びはストックと同じ `position ASC, created_at DESC, id DESC`。見えるグループ(`group_visible`)で、削除されていないものだけ。
- 削除されたグループ、見えないグループに入っている画像は「グループなし」として扱う。
- どのグループにも入っていない画像は最後にまとめる(見出しは「グループなし」)。
- **中の順は古い順(生成した順)。** グループは案件や作業のまとまりなので、生成した流れ(試し → 直し → 仕上げ)を上から順に追えるほうが読みやすい。新しい順は日付の並びで見られる。「グループなし」も同じ規則にする(節ごとに向きが変わると混乱する)。
  - 同じ時刻の出力は `output_index` の順、最後は id で決める。

### 3. 似た画像の順の計算

- 管理者が選んだ有効な `model_key`(`semantic_search.require_active`)のベクトルを使う。埋め込みが無効・使えないときは、API は 409 を返し、画面のメニューにこの項目を出さない(無効な機能は利用者の画面から隠す)。
- 全件の距離行列は作らない(1万枚で 1億要素、float32 で 400MB)。次の順で並べる。
  1. 球面 k-means(コサイン)で、k ≈ √n のクラスタにまとめる。初期値は k-means++ で、乱数の種は固定する(同じ入力なら同じ順)。繰り返しは最大 8 回。
  2. クラスタの重心を、貪欲な最近傍の鎖でつなぐ。始点は最も新しい画像のクラスタ(並びの先頭に最近の画像が来る)。
  3. 各クラスタの中を、最近傍の鎖で並べる。始点は、直前のクラスタの最後の画像に最も近い画像(最初のクラスタは最も新しい画像)。クラスタの中の行列は √n × √n なので小さい。
- 埋め込みの無い画像(未計算、失敗、画像を残さなかったもの)は最後に、新しい順で並べる。
- **キャッシュ:** 結果の並び(Asset の id の列)をプロセスの中に持つ。鍵は `model_key`、埋め込みの版(`Embedder.version(model_key)`。ベクトルを書くたびに上がる)、見る人の範囲、対象の id の集合の要約(sha256)。画像の追加・削除や埋め込みの更新で鍵が変わり、作り直す。持つのは直近の数件だけ。
- **時間とメモリの目安:** 主な計算は k-means の `n × k × 次元 × 繰り返し`。n = 1万、k = 100、512 次元、8 回でおよそ 40 億回の積和で、一般的な VM の CPU(2〜4 コア)の numpy で数秒。メモリはベクトルの行列(1万 × 512 × 4 バイト = 約 20MB)と、n × k の距離(約 4MB)。**想定は 1万枚まで**。それを超える規模(数万枚)でも動くが、初回の表示に十秒以上かかりうる。キャッシュが効くので2回目からは速い。
- 順の計算は、見る人に見える画像だけを対象にする(範囲ごとにキャッシュする)。

### 4. API

- **日付:** `GET /api/runs` のまま(変えない)。
- **グループと似た画像の順:** 新しいエンドポイント `GET /api/history/assets?sort=group|embedding&limit=&cursor=` を作る。
  - 単位が画像なので、応答の形が Run の一覧と違う。`GET /api/runs` に `sort` を足すと、項目の意味が並べ方で変わってしまう。
  - 項目は `{asset_id, group_id, run: RunSummary}`。表示は日付の並びと同じ部品(`RunSummary` と出力の番号)で描く。
  - 応答に `groups: [{id | null, name | null, count}]`(グループの並び順。`id = null` は「グループなし」)を付ける(`sort=group` のときだけ)。見出しの名前と件数に使う。件数は、この並べ方に出る画像の数。
  - **カーソル:**
    - グループ: 位置の組(グループに入っているか、グループの `position`、`created_at`、`id`、画像の `created_at`、`output_index`、`id`)を keyset にする。新しい画像が入っても、読み込み済みの範囲がずれない。
    - 似た画像の順: 並びの中の順位(オフセット)。並びは鍵が変わると作り直すので、ページの間に画像が増えると、重なりや抜けが出うる。画面は同じ画像を2回出さないよう、読み込んだ項目を `asset_id` で重複なく扱う。
- **区切りはフロントで判定する。** 日と年の区切りは利用者の時間帯で決まるので、サーバーでは決められない。グループの区切りも、項目の `group_id` の変わり目で判定できる。判定は純粋関数にしてテストする。
- 見える範囲は ADR-0025 の関数(`run_visible`、`group_visible`)を通す。

### 5. 画面

- **ソートの選択:** ツールバーの右、絞り込みのボタンの左に、ソートのアイコンボタンと小さなメニュー(絞り込みと同じ作り。`menuitemradio`)を置く。項目は「日付 / グループ / 似た順」。似た順は埋め込みが使えるときだけ出す。日付以外を選んでいる間は、絞り込みと同じくボタンに印を付ける。
- 選択は localStorage の `gakei:history-sort`(`date | group | embedding`。既定は日付)に保存する。保存値が似た順でも、埋め込みが使えなければ日付として扱う。
- **区切りの見出し:** 区切りの位置で並びを節に分け、節の頭に、枠も背景も無い太字の文字だけの見出しを全幅で置く。節どうしの間は少し空ける。カードはその下から並べ直す。
  - 詳細の形(グリッド)、石積み、行揃えのすべてで、見出しは常に行の頭から始まる。石積みは節ごとに列を組み直し、行揃えは節ごとに行を組む(節の最後の行は引き伸ばさない)。節の終わりは列や行が揃わず、余白が出る。
  - 見出しは見出し要素(`h2`)にする。説明の文は付けない。
  - 日付の並びでは、日が変わる位置で節に分け(最初の日を含む)、見出しは月日と曜日(ja「10月23日(金)」、en「Fri, Oct 23」。`Intl` で)。件数は出さない(ページングで日の全件が分からないため)。
  - 年の見出しは別に置かない。今年でない日だけ、日の見出しに年を入れる(ja「2025年3月3日(月)」)。年の見出しと日の見出しを2段続けない。
  - 1日に多くの画像を作ると、画像ごとの月日は同じ表示が並ぶだけになるので、画像には月日を出さない。
  - グループの並びでは、各グループの節の見出しにグループ名と件数を出す。
  - 似た画像の順は見出しを置かず、1つの並びにする。
  - 当初は区切りを、並びの中でカード1枚分(ギャラリーでは1マス)を占めるバナーのカードにしていた。カードが大きく、どの画像に掛かる区切りか分かりにくかったため、字だけの見出しと節ごとの配置に改めた(2026-10-23)。
- 状態の絞り込み(すべて / 成功 / 失敗)は、どの並べ方でも Run の状態で掛ける。自動読み込みの番兵も同じに効く。

## Options Considered

### 似た画像の順の作り方

| 案 | 評価 |
|---|---|
| A. k-means + 重心の鎖 + クラスタの中の鎖(採用) | 全件の距離行列が要らず、メモリは O(n × k)。並びが大まかに似たもの同士でまとまる |
| B. 全件の最近傍の鎖 | 素直だが、n² の距離が要る(1万枚で 400MB、計算も遅い) |
| C. 1 次元の UMAP / 主成分 | 1 次元への射影は近いものが離れやすい。UMAP はサーバーに重い依存が増える(マップは ADR-0033 でブラウザ側) |
| D. マップ(2D)の座標を蛇行してなぞる | マップと見た目が揃うが、計算がブラウザ側にあり、サーバーでページングできない |

### API

| 案 | 評価 |
|---|---|
| A. 画像単位の別エンドポイント(採用) | 項目の意味が一定。日付の並び(`GET /api/runs`)を変えない |
| B. `GET /api/runs?sort=` | 入口は1つだが、並べ方で項目の単位(Run / 画像)が変わる |

### グループの中の順

| 案 | 評価 |
|---|---|
| A. 古い順(採用) | 作業の流れを追える |
| B. 新しい順 | 日付の並びと揃うが、新しいものを見るなら日付の並びで足りる |

## Trade-off Analysis

似た画像の順は、厳密な最適(巡回の最短)ではなく、手元の CPU で数秒で終わることを優先した。k-means の境目では似ていない画像が隣り合うことがあるが、眺める用途では許容できる。キャッシュの鍵に対象の集合の要約を入れたので、少しでも画像が増えると作り直しになる。生成のたびに作り直しが起きるが、目安の規模なら数秒で、作り直すのは並べ方を開いたときだけ。

グループのカーソルを keyset にしたのは、生成中に画像が増えても読み込み済みの範囲がずれないようにするため。似た画像の順は並びそのものが変わるので、keyset にしても意味がなく、オフセットにした。

## Consequences

- 新しいエンドポイント `GET /api/history/assets` と、その応答の型が増える。MCP には足さない(必要になったら別に決める)。
- 似た画像の順を初めて開いたとき、規模によっては数秒待つ。
- 履歴のツールバーにソートのボタンが増える。
