# ADR-0042: 繰り返し回数(同じ設定の Run をまとめて積む)

**Status:** Proposed
**Date:** 2026-10-10

## Context

同じ設定で何枚も試すとき、今は生成ボタンを何度も押す必要がある。SD WebUI にはバッチ回数(`n_iter`。ADR-0038 2章)があるが、これは API を1回呼んで全部が終わってから一度に返るので、次の点で使い勝手が違う。

- 結果が全部そろうまで1枚も見られない(サムネイルの生成も取り込みも最後にまとめて行う)。
- 途中で1回失敗すると全部が失われ、途中で止めることもできない(実行中の中断は作っていない。ADR-0013、ADR-0038 4章)。
- 記録は1つの Run になる。

2026-10-10 にユーザーから、GAKEI の機能としてループさせる機能も必要と要望があった。OpenAI と ComfyUI には、そもそもバッチ回数に当たるものが無い(OpenAI の `n` は1回の呼び出しの枚数)。

## Decision

### 1. 範囲

- 生成のフォームに **繰り返し回数**(1〜20、既定 1)を置く。全プロバイダー共通。
- 生成ボタンを1回押すと、同じ設定の Run を繰り返し回数だけ作り、まとめて待機(`queued`)に積む。各 Run は独立した Run で、これまでの Run と何も変わらない(ADR-0003、ADR-0005)。実行はプロバイダーごとのレーンで順に行う(ADR-0013 5章)。
- 繰り返し回数は Run の記録(`run.params`)には入れない。API に送った値ではないため(ADR-0003 ルール4)。同じ時に積んだ Run をまとめる印も、今は持たない(履歴で並んで見えるので足りるとする)。
- 既存のバッチ(OpenAI の `n`、SD WebUI の枚数とバッチ回数)はそのまま残し、繰り返しと掛け合わせられる。

### 2. seed

- seed の欄が「ランダム」なら、各 Run の seed はそれぞれサーバーが決める(今と同じ)。
- 「固定」なら、1つ目は指定の値、2つ目以降は 1 ずつ足す(WebUI のバッチ回数と同じ考え方)。足す幅は、そのプロバイダーの1回の枚数を考える(SD WebUI は1回で `n × n_iter` 枚、seed を1枚ごとに足すので、次の Run は `seed + n × n_iter` から始める。ComfyUI は1つの seed でバッチ全体を作るので 1 ずつ)。範囲の上限を超えたら 0 から回す。
- seed を持たないプロバイダー(OpenAI)では何もしない。

### 3. API

- `POST /api/runs` に `repeat`(1〜20、既定 1)を足し、応答で作った Run の一覧を返す(既存の応答の形は保ち、1件目を今の位置に、全体を別の項目に)。検証は1回だけ行い、どれか1つでも作れなければ1つも作らない(1つのトランザクション)。
- MCP の Run 作成(ADR-0023)には、今は足さない。

### 4. 画面

- 繰り返し回数は枚数の近く(SD WebUI ではサイズ欄の上の段)に置き、2 以上のとき「合計 N 枚」の表示を、1回の枚数 × 繰り返し回数にする。OpenAI では参考料金も掛けて示す。
- 積んだ後は、これまでの1回の生成と同じく結果エリアに順に出る。待機中の残りは、既存の取り消しで止められる。
- 生成ボタンの文言に回数を添える(例「生成 ×5」)。

### 作らないもの

- 繰り返しごとにパラメーターを変える機能(X/Y プロットなど)
- 実行中の Run の中断
- 同じ時に積んだ Run をまとめて扱う印や画面

## Options Considered

| 案 | 評価 |
|---|---|
| A: フォームで Run を N 個まとめて積む(採用) | 1つずつ結果が届き、途中で止められ、記録も1回ずつ残る。プロバイダーに依らない |
| B: SD WebUI のバッチ回数だけにする | API の1回で済み速いが、全部そろうまで見られず止められない。OpenAI と ComfyUI では使えない |
| C: サーバーの1つの「ループのジョブ」として持つ | 止める・まとめて見るなどがしやすいが、キュー(`run` テーブル)とは別の仕組みが要り、ADR-0005 の「キューは run テーブルそのもの」を崩す |

## Trade-off Analysis

SD WebUI では、Run ごとに API を呼ぶので、WebUI の画面で選んでいるのと違うチェックポイントを使うと、毎回チェックポイントの切り替えと復元が起き(ADR-0038 2章の `override_settings_restore_afterwards`)、バッチ回数より遅くなる。速さが要るときはバッチ回数、1枚ずつ確かめたいときや途中で止めたいときは繰り返し、と使い分ける。docs に書く。

## Consequences

- どのプロバイダーでも、同じ設定で続けて試せる。
- `POST /api/runs` の応答が広がる(後方互換)。フロントの型を作り直す。
