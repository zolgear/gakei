# ADR-0001: スコープと非ゴール

**Status:** Accepted
**Date:** 2026-09-21

## Context

gpt-image-2.5 系 API の Edit を組織で使いこなすには専用UIが必要になる。Open WebUI のようなチャット型の UI では、4K以上の画像が Markdown パーサーを通せず表示できない。また、試行錯誤の経過と生成物を管理する手段がなく、組織での利用に必要な証跡も残らない。

既存ツールを調査したが、セルフホストで「生成UI+世代管理+証跡」を満たすものはなかった。一方、Numonic や Layer のようなSaaSは機能が広く、同じ範囲を自作すると終わらない。

## Decision

セルフホスト、日本国内、単一組織向けのツールとして自作する。機能は下記のゴールに限定し、非ゴールは作らない。

### ゴール

1. Azure OpenAI の画像 Generate / Edit を、フォームとキャンバスで操作できる(複数入力画像、マスク、任意解像度)。
2. 4K(最大 3840px)の画像を劣化なく閲覧・ダウンロードできる。
3. すべての実行が自動で記録される(プロンプト、パラメータ、入力画像、出力、実行者、日時、usage、失敗も含む)。
4. 出力を元に次の Edit を行うと親子関係が記録され、世代を辿れる。
5. 大量に生成した結果を、採用/不採用で整理できる。
6. 組織の Entra ID で認証する。
7. よく使うプロンプトを名前を付けて保存し、フォームに読み込める(プロンプトセット。2026-09-21 追加、ADR-0009)。
8. 個人が自分の PC で、clone と起動スクリプトだけで手軽にセルフホストできる(ローカル版。2026-09-23 追加、ADR-0012)。

### 非ゴール

| 作らないもの | 理由 |
|---|---|
| ノードエディタ、ワークフロー構築 | ComfyUI の領域。本ツールは API を叩く側に徹する。ローカルの ComfyUI は、登録済みのワークフローに値を差し込んで実行するだけにする(2026-09-23 追記、ADR-0013) |
| マルチテナント、外部公開、課金 | 単一組織向けと割り切る |
| 承認ワークフロー、コメント、共有リンク | 運用で足りる。必要になったら再検討 |
| 高機能な画像編集(レイヤー、フィルター、図形・テキストツール、アウトペイント用キャンバス) | マスク用とスケッチ用の簡易ブラシのみ作る(2026-09-23 改訂、ADR-0010) |
| モデル学習、LoRA 管理 | 対象外 |
| C2PA 署名、IPTC 埋め込み | Phase 3。DBの記録が証跡の正本。ダウンロードする PNG に GAKEI 独自の系列参照(署名なし)を入れることは、これに当たらない(2026-09-24 追記、ADR-0014)。他のツールが埋め込んだ C2PA マニフェストの存在と claim generator を表示すること(署名は検証しない)も、これに当たらない(2026-09-26 追記、ADR-0018) |
| 類似画像検索、自動品質採点 | Phase 3 以降。自動タイトル・タグ付けは 2026-09-28 に前倒しした(ADR-0024)。埋め込みベクトルは保存しない |
| 汎用DAM機能(任意ファイル管理、フォルダ階層) | プロジェクト+フラグ+タグで足りる。「プロジェクト」に当たる階層なしのグループは 2026-09-27 に足した(ADR-0022)。フォルダ階層は引き続き作らない |
| モバイル最適化 | 主な対象は PC のブラウザ。スマートフォンの幅で一通り操作できる最低限の対応だけ行う(2026-09-21 改訂、ADR-0009)。専用画面、PWA、作り込みはしない |
| 他プロバイダー対応 | Phase 3。ただし差し込める構造にはしておく(ADR-0005)。同じ PC で動くローカルの ComfyUI だけは対象にする(2026-09-23 改訂、ADR-0013。実験中) |

## Options Considered

### Option A: 既存SaaS(Numonic / Layer)を導入
**Pros:** 開発不要。リネージ、監査、C2PAが揃う。
**Cons:** SaaSのみで国内・組織内で完結する要件に合わない。組織の Azure OpenAI デプロイを生成バックエンドにできない。

### Option B: Open WebUI を拡張
**Pros:** 認証やモデル接続の仕組みを流用できる。
**Cons:** チャットのメッセージ構造が前提で、4K表示の問題と Edit のUI不足が根本から解決しない。世代管理のデータモデルを載せる場所がない。

### Option C: OSSパネル(gpt-image-panel 等)をフォーク
**Pros:** 生成/編集UIの出発点がある。
**Cons:** 世代管理、認証、監査はほぼ全部自作になる。他人のコード構造に縛られる割に得るものが少ない。

### Option D: 範囲を絞って自作(採用)
**Pros:** 要件に正確に合う。データを組織のテナント内に保てる。
**Cons:** 開発と保守のコストを自分で負う。範囲が膨らむリスク。

## Trade-off Analysis

決め手は「セルフホストかつ組織の Azure OpenAI デプロイを使う」という制約で、A は外れる。B と C は根本課題(メッセージ構造、データモデル不在)を解決しない。D のリスクは範囲の膨張であり、非ゴールを明文化することで抑える。

## Consequences

- 要件に合った最小のツールが手に入る。データは組織のテナントから出ない。
- 保守は自前。依存を少なく保つ必要がある。
- 非ゴールの機能を求められたら、この ADR を更新してから着手する。
