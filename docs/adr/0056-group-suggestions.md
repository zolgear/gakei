# ADR-0056: グループの提案(画像の埋め込みで集まりを見つけ、グループにする案を出す)

**Status:** Proposed
**Date:** 2026-10-24

## Context

グループ(ADR-0022)は手で作る入れものである。生成と取り込みを重ねると、どのグループにも入っていない画像が数百枚たまり、手で振り分けるのは手間がかかる。ADR-0022 は入り口の (c) として「種類ごとに自動で分類する」を後続に置き、ADR-0033 1章は「埋め込みをもとにしたグループへの自動振り分け」を今回作らないものに挙げていた。

利用者から、画像の埋め込み(ADR-0033、ADR-0044)で似た画像の集まりを見つけ、グループにする案を出してほしいと求められた。決めるのは人で、案を見て受け入れたものだけをグループにする。

関連する決まり:

- ADR-0001: 非ゴールに「自動品質採点」と「汎用 DAM(フォルダ階層)」がある。
- ADR-0022: 1つの Asset が属するグループは1つだけ。グループに入れる操作は常に「移す」。グループは証跡ではない。
- ADR-0025: 認証モードでは本人のものだけを見せる。一覧は `asset_visible` / `group_visible` を通す。
- ADR-0033: 埋め込みは `model_key` ごとに保存し、使うのは管理者が選んだ1つ。無効・使えないときの API は 409。
- ADR-0041: タグ辞書(タグのカテゴリーと訳)。
- ADR-0051: 外部の AI へ送る処理は `ai.before_send` を通す。
- ADR-0054: 履歴の似た画像の順。球面 k-means と、プロセス内のキャッシュ。

## Decision

### 1. 範囲

- **自動では何も保存しない。** 提案は表示のたびに計算するだけで、DB に書かない。グループを作る・画像を入れるのは、人が提案を見て「グループにする」「(グループ名)に追加」を押したときだけ。
- 提案はグループの名前を付けない(名前の欄は空で、人が入力する)。LLM による名前の提案は後で検討する(6章)。
- 対象は似た画像・重複と同じ(`AssetFilter`。見える、削除されていない、マスクと領域の四角でない、画像を残さなかったものでない Asset)で、使うモデルのベクトルがあるもの。種類(生成・アップロード・スケッチ・合成)は問わない。
- 画像の良し悪しは判定しない。似ているものを集めるだけで、ADR-0001 の非ゴール「自動品質採点」には当たらない。グループは階層を持たないままで、「汎用 DAM」にも当たらない。

### 2. 集め方

検証(208 枚の実データ。Options Considered)で決めた方式。

1. 使うモデルのベクトルを L2 正規化する。
2. **HDBSCAN**(scikit-learn の `sklearn.cluster.HDBSCAN`)で集める。`metric=cosine`、`min_cluster_size=5`、`min_samples=2`。
   - **3000 件を超えたら**、メモリを守るため PCA で 50 次元に落とし、ユークリッド距離で集める。コサインの全組の距離(3000 件で約 72MB)を作らないため。正規化したベクトルなので、ユークリッド距離の順はコサインとほぼ同じになる。
3. **外れ値はそのまま外れ値として残す。** どの集まりにも入れない。HDBSCAN は全体を1つの集まりにはしない(`allow_single_cluster` は既定の false のまま)。対象の画像がどれも似ていて1つの塊にしか見えないときは、提案は出ず、すべて未分類になる。
4. **細かく分ける(選んだときだけ):** 対象全体の 20% を超える大きな集まりは、球面 k-means(k は 2〜6 からシルエット係数(コサイン)で選ぶ)で割る。割った各片が `min_cluster_size` に満たない k は選ばない。どの k も満たさなければ割らない。検証では、大きな集まりが意味のある細分に分かれた。既定は「標準」(割らない)。
5. 集まりの中の画像は、集まりの重心(正規化した平均)に近い順に並べる。先頭 12 枚を表紙にする。

**集める計算は、対象(1章)の全件で行う。** 既存のグループに入っている画像も含める。グループに入っている画像は、集まりの手がかり(どのグループに近いか)と、追加先の候補(4章)に使う。

### 3. 対象の範囲(既定は「グループ外だけ」)

- **グループ外だけ(既定、`scope=ungrouped`):** 提案に入れるのは、削除されていないどのグループにも入っていない画像だけ(ストックの「グループなし」と同じ定義)。グループに入っている画像は提案に入れないので、受け入れても**別のグループから移ることは起きない**。
- **すべて(`scope=all`):** グループに入っている画像も提案に入れる。受け入れると、ADR-0022 の規則で元のグループから移る。提案に `moving_count`(別のグループから移る枚数)を付け、1枚以上あれば画面は受け入れる前に確認する。
- 見えないグループ(認証モードで他人のもの)に入っている画像は、どちらの範囲でも提案に入れない(見えないところから黙って移さない)。

### 4. 既存のグループとの重なり

- 集まりの画像のうち **50% 以上が同じ既存のグループ**(見える、削除されていない)に入っていれば、その集まりは「(グループ名)に n 枚を追加」の提案にする(`target_group`)。提案の画像は、まだそのグループに入っていないもの(範囲の規則に従う)。追加する画像が無ければ、提案にしない。
- それ以外は「新しいグループにする」の提案。新しいグループの提案は、提案に入る画像が `min_cluster_size`(5)枚以上のときだけにする(大半が既存のグループに入っている集まりの残り数枚を、新しいグループにしない)。
- 提案に入らなかった、どのグループにも入っていない画像(外れ値と、上の規則で提案から落ちた画像)は「未分類」(`outlier_ids`)として返す。グループに入っている画像は、置き場所があるので未分類にしない。画面は最後に畳んで1つ出す。

### 5. 特徴的なタグと作品

名前は付けないが、何の集まりかの手がかりとして提案のカードに出す。

- **タグ:** 英語のタグ(ASCII の名前。WD Tagger などの元のタグで、訳したタグは数えない)を、画像ごとに数える(人が消したタグは数えない)。
  - informative Dirichlet prior 付きの log-odds(事前分布は対象全体での出現数)で、集まりとそれ以外を比べ、集まりに偏るタグを選ぶ。
  - 条件は z > 1.5、集まりでの出現率 25% 以上、対象全体での出現率 50% 以下。全体に広いタグ(1girl、solo など)は全体の出現率の上限で落ちる。
  - z の大きい順に最大 8 個。表示はタグ辞書の訳(あれば)で、無ければタグのまま。訳を出すのは、ほかのタグの表示と同じく、画面の言語が日本語で訳を出す設定のときだけ(ADR-0041)。
- **作品:** 次のどちらかを、画像ごとに作品の名前として数える(1枚の画像は同じ作品を1回だけ数える)。
  - 有効なタグ辞書(体系が `danbooru`)のカテゴリーが 3(作品)のタグは、その名前。
  - カテゴリーが 4(キャラクター)のタグ、または辞書に無いタグで、末尾が括弧書き(`aru (blue archive)`)なら、括弧の中(`blue archive`)。`cosplay` は除く。辞書に無いタグを括弧書きだけで数えるときは、一般のタグの括弧書き(`star (sky)` など)を作品と取り違えないよう、よく出る一般の括弧書き(sky、object、weapon など)も除く。
  - 辞書に載っていて、カテゴリーが 3・4 以外のタグは数えない。
  - 最も多い作品と、その割合(集まりの枚数に対する)を出す。2枚以上かつ 25% 以上のときだけ。訳があれば添える。

### 6. 名前の提案(後で検討)

- LLM で集まりの名前を提案するのは後で検討する(OpenAI のキーの更新を待って別途検証する)。
- そのときは、特徴的なタグ・作品・表紙の画像を LLM・VLM に送ることになるので、ADR-0051 の `ai.before_send` を通す(`purpose` の追加か既存の流用かはそのときに決める)。今回は外部の AI を呼ばないので通さない。
- API の応答に `name`(今は常に null)を置き、画面の名前の欄に差し込める形にしておく。

### 7. API

すべて `require_user`。

| メソッド | パス | 内容 |
|---|---|---|
| `GET` | `/api/asset-groups/suggestions?scope=ungrouped\|all&granularity=normal\|fine` | 提案の一覧。埋め込みが無効・使えなければ 409(`embeddings_unavailable`) |
| `POST` | `/api/asset-groups/suggestions/accept` | `{name?, target_group_id?, asset_ids}` のどちらか一方。名前なら新しいグループを作って入れ、`target_group_id` ならそのグループへ移す。1回のトランザクションで行い、更新後のグループの行を返す |

- 応答は `{model_key, scope, granularity, scanned, truncated, suggestions: [...], outlier_ids, assets: [...]}`。
  - 提案の各項目: `id`(提案の画像の id を並べた sha256 の先頭。同じ入力なら同じ)、`size`、`member_ids`(重心に近い順)、`cover_ids`(先頭 12)、`top_tags: [{tag, label, rate, global_rate}]`、`franchise: {name, label, rate} | null`、`target_group: {id, name, overlap} | null`、`moving_count` と `moving_ids`(別のグループから移る画像)、`name: null`。
  - `assets` は提案と未分類に出る画像のサムネイルに要る項目(種類、焦点、レーティング(ADR-0049)など。`AssetSummary`)。
- 受け入れは既存の作成(`POST /api/asset-groups`)とメンバーの追加(`POST /api/asset-groups/{id}/assets`、1〜200件)でもできるが、提案は 200 枚を超えうるので、作成と追加を1回で行う受け入れの API を足す(上限 5000 件)。可視性は既存の関数(`get_visible_group`、`add_members` の `asset_visible`)を通す。見えない・削除済みの画像を含めば 404 で全体を拒む。
- 新しいグループは既存の作成と同じく先頭に入る。
- 一度に見る画像は新しい順に 10000 件まで。超えたら古い画像を見ず、`truncated` を立てる。
- MCP には今は足さない(Action Items)。

### 8. 計算のコストとキャッシュ

- **コスト:** HDBSCAN(コサイン)は全組の距離を作るので、3000 件で約 0.5 秒・約 72MB。3000 件を超えたら PCA 50 次元のユークリッドにする。1万件で約 6 秒(一般的な VM の CPU)。タグの集計は画像とタグの行を1回読むだけ。
- **キャッシュ:** 集めた結果(集まりごとの画像の並びと外れ値)をプロセス内の LRU に直近 8 件持つ。鍵は `model_key`、埋め込みの版(`Embedder.version`。ベクトルを書くたびに上がる)、対象の asset_id の集合の要約(sha256)、パラメーター(粒度と HDBSCAN の設定)。永続化しない(再起動で消える)。
  - 範囲(`scope`)と、グループの所属・タグは鍵に入れない。集めた結果に後から当てはめるので、提案を受け入れてグループが変わっても、集め直さずに次の提案を返せる。
  - 画像の追加・削除や埋め込みの更新で鍵が変わり、集め直す。

### 9. 画面

- ストックの見出しの「⋯」に「グループの提案」を足す。埋め込みが使えるときだけ出す(重複の候補と同じ条件)。ページは `/stock/group-suggestions`。
- 上に「対象: グループ外だけ / すべて」と「粒度: 標準 / 細かく」の切り替え。説明文は置かない。
- 提案のカード: サムネイル(最大 12、多ければ「+n」で残りも開く)、枚数、特徴的なタグのチップ、作品、名前の入力欄(空)、「グループにする」のボタン。既存のグループへの追加の提案では、名前の欄の代わりに「(グループ名)に追加」のボタン。
- カードの画像は押すと提案から外せる(もう一度押すと戻す)。外した画像は受け入れの対象にしない。
- 受け入れたら、そのカードを畳んで結果(作ったグループ)を出す。ストックと履歴の一覧を取り直す。
- 最後に「未分類」の枠を1つ、畳んで出す。
- サムネイルはレーティングのマスク(ADR-0049)を既存の部品(`AssetThumb`)で守る。768px 未満でも使えること(ADR-0009)。

## Options Considered

### 集め方

検証は、管理者が選んだ埋め込みのモデルで 208 枚の実データを集め、利用者が手で作ったグループとの一致度(ARI)で比べた。

| 案 | 評価 |
|---|---|
| A. HDBSCAN(コサイン)(採用) | ARI 0.82。枚数を決めずに済み、外れ値を外れ値として残せる。20 枚の手作りのグループは1つの集まりにまとまり、グループ外の同種の画像 13 枚も同じ集まりに入った。7 枚の別のグループは、ちょうどその 7 枚の集まりになった |
| B. k-means(球面) | k を決める必要がある。外れ値もどこかの集まりに入れるので、まとまりの無い画像が提案に混ざる。大きな集まりを割る用途(2章の「細かく分ける」)には使う |
| C. 凝集型(平均連結など) | しきい値か枚数を決める必要がある。全組の距離が要り、1万件では重い。外れ値は小さな集まりとして残り、見分けにくい |
| D. UMAP で次元を落としてから HDBSCAN | まとまりははっきりするが、umap-learn と numba の依存が増える(サーバーに重い依存。ADR-0054 の案 C と同じ理由)。乱数で結果が揺れる。A で足りた |
| E. プロンプトの埋め込み(ADR-0045)と組み合わせる | プロンプトのある生成画像にしか使えず、アップロードには効かない。同じプロンプトで違う絵になる・違うプロンプトで同じ系統の絵になることもある。画像だけで ARI 0.82 が出たので、今回は組み合わせない |

### 受け入れの API

| 案 | 評価 |
|---|---|
| A. 作成と追加を1回で行う API を足す(採用) | 200 枚を超える提案も1回で、途中で失敗して空のグループだけが残ることが無い |
| B. 既存の作成と追加(200 件ずつ)を画面から呼ぶ | API は増えないが、呼び出しが分かれ、途中で失敗すると半端な状態が残る |

## Trade-off Analysis

依存に scikit-learn(BSD-3-Clause)を足す。scipy、joblib、threadpoolctl(どれも BSD-3-Clause)、narwhals(MIT)、cloudpickle(BSD-3-Clause)が一緒に入る。HDBSCAN を自前で書くより、検証した実装をそのまま使う方が確かである。主要な環境(Linux の x86_64 / aarch64、Windows、macOS)には wheel があり、Docker イメージも `uv sync --frozen` で入る。第三者ライセンス表記(ADR-0021)は起動している環境の配布物から作るので、自動で載る。ただし scikit-learn は Metadata 2.4(PEP 639)で、`License-File` が `.dist-info/licenses/` からの相対のパスなので、ライセンスの本文が載っていなかった。`licenses/` の下も読むように直した(同じ形の既存の依存の本文も載るようになる)。

提案を保存しないので、表示のたびに計算する。キャッシュが効く間(画像とベクトルが変わらない間)は速いが、生成のたびに集め直しになる。目安の規模(1万枚)なら数秒で、集め直すのは提案のページを開いたときだけ。

既定を「グループ外だけ」にしたので、利用者が手で整理したグループは提案で崩れない。グループに入っている画像も集める計算には使うので、手作りのグループに近い画像は、そのグループへの追加の提案として出る。

## Consequences

- 依存に scikit-learn が増える。イメージが大きくなる(scipy を含めて数十 MB)。
- 新しいエンドポイント `GET /api/asset-groups/suggestions` と `POST /api/asset-groups/suggestions/accept`、応答の型が増える。`npm run gen:api` が要る。
- ストックの「⋯」の項目と、`/stock/group-suggestions` のページが増える。
- ADR-0022 の入り口 (c)(自動の分類)は、自動で入れるのではなく、提案を人が受け入れる形で作る。ADR-0022 にその旨を追記する。ADR-0033 1章の「自動振り分けは作らない」は変わらない(提案は自動で振り分けない)。
