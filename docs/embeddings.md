# 画像の埋め込み(文章での検索、似た画像、重複の候補、マップ)

GAKEI は、画像を CLIP 系や EmbeddingGemma 2 のモデルでベクトル(埋め込み)にして、次の4つに使えます(ADR-0033、ADR-0044)。

- **文章での検索:** サイドバーの検索パネル(上部の虫めがねか `/` キー)か検索ページで「意味」に切り替え、自然文で画像を探します。結果は近い順です。プロンプトやタグの無い画像も見つかります。パネルの方式はブラウザに覚えます。
- **画像で探す:** 手元の画像に似た画像を、ストックに取り込まずに探します(下の「画像で探す」)。
- **似た画像:** 画像ビューアの情報欄に、似た画像を 12 件まで並べます。続きは「検索ページでもっと見る」で開きます(`/search?similar=<画像の ID>`)。
- **重複の候補:** ストックの「重複の候補」(`/stock/duplicates`)で、ほぼ同じ画像をグループにまとめて並べます。
- **マップ:** 上部のメニューの「マップ」(`/map`)で、似た画像を線で結んだネットワークと、似た画像が近くに集まる地図を表示します。

今までのキーワード検索(プロンプト、タイトル、タグなど)はそのまま使えます。キーワードと意味の結果を混ぜて並べることはしません。

ログインを有効にしている場合、検索・似た画像・重複の候補・マップに出るのは、その人に見える画像だけです(ADR-0025)。他人の画像は出ません。

## 有効にする

管理者設定の「埋め込み」(`/settings/embeddings`)で設定します。既定では無効で、無効の間は検索の「意味」、ビューアの「似た画像」、重複の候補、マップを画面に出しません。

1. 「埋め込みを使う」をオンにし、エンジン(ローカル / リモート)を選びます。
2. ローカルなら、使うモデルを選んで「ダウンロード」を押します。リモートなら、接続先とモデル名を入れます(下の「リモートの推論サーバー」)。
3. ページ上部の「保存」を押します。スイッチ、エンジン、モデル、接続先、取り込み時の計算、しきい値は、保存するまで反映されません(ADR-0031)。モデルのダウンロード・削除、一括実行、ベクトルの削除は、押したその場で行います。
4. 既にある画像は「まとめて計算する」で計算します(下の「計算のタイミング」)。

有効にしても、モデルをダウンロードしていない(リモートなら接続先とモデル名が無い)間は使えません。画面に「有効ですが、まだ使えません」と出ます。

## モデルを選ぶ

使うモデルはインスタンス全体で1つです。検索、似た画像、重複の候補、マップは、すべてこのモデルのベクトルを使います。

| モデル | ダウンロード | 言語 | メモリ目安(画面の値) | ライセンス |
|---|---|---|---|---|
| clip-vit-b32-u8(既定) | 約 345MB | 英語 | 約 0.7 GB | MIT(OpenAI CLIP) |
| clip-vit-b32 | 約 607MB | 英語 | 約 0.9 GB | MIT(OpenAI CLIP) |
| clip-japanese-base | 約 790MB | 日本語・英語 | 約 1.0 GB | Apache-2.0(LY Corporation) |
| embeddinggemma-2-q8 | 約 514MB | 多言語(日本語・英語を含む) | 約 1.0 GB(画像だけなら 約 0.75 GB、文章だけなら 約 0.6 GB) | Apache-2.0(Google) |

- **日本語で検索するなら clip-japanese-base か embeddinggemma-2-q8 を選びます。** clip-vit-b32-u8 と clip-vit-b32 は英語向けで、日本語の文章ではほとんど当たりません(英語の文章なら当たります)。設定画面と検索画面にもそう出ます。
- **embeddinggemma-2-q8(EmbeddingGemma 2)は、検索の質がいちばん高い代わりに、計算が重いモデルです**(ADR-0044)。日本語・英語のどちらでも、長いプロンプトを貼り付けた検索でも、CLIP 系より当たります。一方、画像 1 枚の計算に CLIP の数十倍の時間がかかります(下の「速度とメモリ」)。軽さを優先するなら CLIP 系のままにします。
- clip-vit-b32-u8 は、clip-vit-b32 の画像側を uint8 に量子化したものです(文章側は同じ fp32)。fp32 とのずれは小さく(コサイン類似度の平均 0.985)、速くて軽いので既定にしています。
- モデルは配布物に含まれていません。設定画面の「ダウンロード」で Hugging Face から取得し、`DATA_DIR/models/clip/<モデル>/` に置きます。リビジョンを固定し、ファイルごとにハッシュを確かめます。WD Tagger(`DATA_DIR/models/wd/`)とは別の場所です。
- CLIP 系のモデルは、画像を 224×224 に縮めて読みます。細部(小さな文字など)の違いはほとんど見ません。embeddinggemma-2-q8 は、縦横比を保って約 800×800 相当(16px のパッチ 2,520 個まで)に縮めて読むので、細部も見ます。そのため、CLIP 系はサムネイル(長辺 512px)から、embeddinggemma-2-q8 はプレビュー(長辺 2048px)から計算します。
- embeddinggemma-2-q8 の検索の文章は、1,024 トークン(日本語なら おおよそ 1,000〜2,000 字)で切ります。それより後ろは検索に効きません。CLIP 系は 77 トークンで切ります。

### 速度とメモリ(参考)

ローカルの ONNX(onnxruntime、CPU)で、画像 1 枚・文章 1 件を計算したときの時間です。

| モデル | Raspberry Pi 5(推論スレッド 2) | Windows(Ryzen、16 スレッド) | Pi 5 での最大メモリ |
|---|---|---|---|
| clip-vit-b32-u8 | 画像 約 75ms、文章 約 130ms | 画像 27ms、文章 31ms | 約 556MiB(実測) |
| clip-vit-b32 | 画像 約 230ms、文章 約 130ms | — | 約 0.83GiB |
| clip-japanese-base | 画像 約 710ms、文章 約 110ms | 画像 164ms、文章 19ms | 約 0.92GiB(文章だけなら 約 0.58GiB) |

- 最大メモリは、画像側と文章側の両方を読み込んで計算したときの GAKEI のプロセスの値です。GAKEI 本体と OS の分は別に要ります。画面の「メモリ目安」は、これに余裕を持たせた値です。
- 文章での検索だけのときは、文章側だけを読み込みます。
- 量子化した clip-vit-b32-u8 と clip-japanese-base の画像側は、常に 1 枚ずつ計算します(量子化したモデルはまとめる枚数で値が変わり、LY のモデルはまとめても速くならないため)。clip-vit-b32 は 8 枚ずつまとめます。embeddinggemma-2-q8 も、画像と文章を 1 件ずつ計算します。

**embeddinggemma-2-q8:** x86 の CPU(8 コア)、推論スレッド 4 での実測です(ADR-0044)。

| 計算 | 時間 | 計算中の最大メモリ |
|---|---|---|
| 画像 1 枚 | 約 3.2 秒 | 約 0.72GB |
| 検索の文章(短いもの) | 約 0.23 秒 | — |
| 検索の文章(512 トークン) | 約 0.64 秒 | 約 0.37GB(文章側だけ) |
| 検索の文章(1,024 トークン。上限) | 約 1.3 秒 | 約 0.52GB(文章側だけ) |

- 画像を計算するときは、画像側と文章側の両方を読み込みます(画像側の出力を文章側に渡して、最後のベクトルを作るため)。文章での検索だけのときは、文章側だけを読み込みます。
- 重みはファイルから必要な分だけ読む(mmap)ので、読み込んだ直後のメモリは小さく、計算している間に増えます。画面の「メモリ目安」は、計算中の最大に合わせています。
- 画像の計算のあと、画像側が読み込まれたままの間に長い文章(1,024 トークン)で検索すると、約 1.0GB まで増えます。画面の「メモリ目安」(約 1.0 GB)は、このいちばん重い場合の値です。
- 2〜4 vCPU の環境で 1,000 枚をまとめて計算すると、1 時間ほどかかる見込みです。取り込みのたびの計算も、1 枚に数秒かかります。

### モデルを切り替えたとき

- 前のモデルのベクトルは消しません。戻したときは計算し直さずに使えます。
- 新しいモデルのベクトルは、まだありません。「まとめて計算する」で計算します(画面でも促します)。
- モデルが違うベクトルどうしは比べません。同じ OpenAI CLIP でも、ローカルとリモートは別のモデルとして扱います。
- 「保存済みのベクトル」に、モデルごとの件数が出ます(使っているモデルに「使用中」)。要らないモデルのベクトルは、ここで削除できます。
- モデルのファイルを削除しても、そのモデルのベクトルは残ります。

## 計算のタイミング

ADR-0024 の自動タイトル・タグと同じ形です。

- **取り込み時に自動:** 「取り込み時に計算する」がオン(有効にしたときの既定)なら、生成・アップロード・スケッチのたびに計算します。マスクは対象外です。
- **一括実行:** 「まとめて計算する」で、使うモデルのベクトルが無い画像(失敗したものを含む。削除済みとマスクは除く)を待ち行列に入れます。実行前に件数を確かめます。保存していない変更がある間は押せません。
- **1 枚ずつ:** 画像ビューアの「似た画像」の欄で、ベクトルが無い・失敗した画像は「計算する」「計算し直す」を押せます。

計算は GAKEI のプロセスの中の worker が順に行います。送るのは thumb(512px)で、原本は使いません。設定画面に「未計算の画像」「待ち行列」「失敗」の件数が出ます。

### CPU とメモリ

- 推論のスレッド数は CPU コア数の半分です。一括実行の間も、画面の操作や API の応答が止まらないようにしています。普段は取り込みのたびに 1 枚ずつなので、負荷は小さいです。
- **WD Tagger(自動タグ)と埋め込みのモデルは、同時にメモリに載せません。** 片方が計算している間、もう片方は待ちます。両方の一括実行を同時に走らせると、交互に読み込み直すので遅くなります。文章での検索は、利用者を待たせないよう先に通します。
- 読み込む前に空きメモリ(Linux の MemAvailable。コンテナではメモリ上限の残りも)を確かめ、目安より少なければ読み込まずに失敗にします(WD Tagger と同じ。Windows と macOS では確かめません)。
- 読み込んだモデルは、10 分使わなければメモリから解放します。

## リモートの推論サーバー

GPU のある別のマシンで推論サーバーを動かし、GAKEI からそこに計算を頼めます。形式は今のところ [Infinity](https://github.com/michaelfeil/infinity) だけです。

**送るもの:** 選んだ接続先に、画像(thumb を 512px 以下の JPEG にしたもの。透明な部分は白で塗る)と、検索の文章を送ります。原本は送りません。手元や信頼できるサーバーだけを使います。

### Infinity を動かす

```bash
pip install "infinity-emb[all]"
infinity_emb v2 --model-id openai/clip-vit-base-patch32 --host 127.0.0.1 --port 7997
```

- 別のマシンから GAKEI でつなぐ場合は、`--host` をそのマシンのアドレスにします。キーを掛けるなら `--api-key` を付け、同じキーを GAKEI の接続先に設定します。
- **Windows:** infinity-emb 0.0.77 時点では、そのままでは起動しません。`pip install "click<8.2" aiohttp` を別に実行してください。
- **clip-japanese-base は Infinity では動きません。** 日本語で検索したいなら、ローカルの clip-japanese-base を使います。
- 参考: RTX 3060 で openai/clip-vit-base-patch32 を動かすと、画像 1 枚 約 37ms(32 枚まとめると 1 枚あたり 約 17ms)、VRAM 約 544MiB でした。

### GAKEI に登録する

1. 管理者設定の「LLM の接続先」(`/settings/llm-connections`)で接続先を追加します。Base URL は Infinity の URL(例: `http://127.0.0.1:7997`。`--url-prefix` を付けて起動したなら、それも含める)、キーは Infinity に掛けたキー(無ければ空)。API 形式は埋め込みでは使いません。
2. 「埋め込み」でエンジンを「リモート」にし、その接続先を選び、モデル名に Infinity で動かしているモデル(例: `openai/clip-vit-base-patch32`)を入れ、形式は Infinity のまま「保存」を押します。
3. 「まとめて計算する」で既存の画像を計算します。

- 「OpenAI の設定」の接続先は選べません(OpenAI の API は画像の埋め込みを受け付けないため)。
- 埋め込みに選んでいる接続先は、「LLM の接続先」から削除できません(カードに「埋め込み」と出ます)。
- 接続先の Base URL を変えても、同じ接続先なら同じモデルとみなし、ベクトルをそのまま使います。中身のモデルを変えたときは、「保存済みのベクトル」でそのモデルのベクトルを削除してから計算し直してください。
- リモートには 1 時間あたりの回数の上限はありません(手元のサーバーを想定しています)。1 回に送る件数(画像 32 枚、文章 32 件)と時間切れ(60 秒)だけがあります。

## 画像で探す

検索ページの「意味」で「画像を選ぶ」を押すか、画像を画面に落とすか、貼り付ける(Ctrl/Cmd+V)と、その画像に似た画像を探せます。サイドバーの検索パネルの「画像で探す」からも始められます。

- 画像はストックに取り込まず、サーバーにも保存しません(画像もベクトルも残りません)。URL にも残らないので、再読み込みすると消えます。
- 形式と大きさの上限はアップロードと同じです(PNG / JPEG / WebP、50MB 未満)。画素数は約 8950 万までです。
- 取り込み済みの画像と同じ派生画像(サムネイル。embeddinggemma-2-q8 ではプレビュー)の大きさに縮めてからベクトルにするので、取り込み済みの同じ画像は類似度 1.0 になります。
- リモートのエンジンでは、長辺 512px に縮めた画像が推論サーバーに送られます。
- ローカルのエンジンで画像側のモデルがまだ読み込まれていなければ読み込むので、メモリが足りないと失敗します。
- API は `POST /api/search/similar-image`(multipart の `file`。`limit`、`group_id`、`tag`(繰り返し)、`kind`)です。

## 重複の候補

ストックの「重複の候補」(`/stock/duplicates`)で、ほぼ同じ画像をグループにまとめて並べます。縮小や JPEG の再圧縮などで、sha256 では別の画像になったものを探すためのものです。

- **判定:** CLIP の類似度がしきい値以上で、かつ知覚ハッシュ(構図と色を見る、モデルに依らない小さなハッシュ)も近い組を、重複とみなします。CLIP だけでは、強く劣化した重複と、色違いのような別の画像を分けられないためです(ADR-0033 12章)。
- **しきい値:** モデルごとに持ちます。既定は CLIP 系とリモートが 0.90、embeddinggemma-2-q8 が 0.85(仮の値) です(embeddinggemma-2-q8 は類似度が全体に高く出るため)。管理者設定の「重複の候補」で、使っているモデルの既定を変えられ(0.5〜1.0)、変えた値はモデルごとに残ります(モデルを切り替えると、そのモデルの値になります)。ページの中でも一時的に変えられます。上げるほど、より似た画像だけがまとまります。知覚ハッシュの基準は固定で、画面には出しません。
- **グループの作り方:** 古い画像から順に代表(「最初」の印)にし、代表と重複と判定した画像を同じグループに入れます。A と B、B と C が似ていても、A と C が似ていなければ、同じグループにはなりません。
- **文字だけが違う画像**(同じ画面の日本語版と英語版のスクリーンショットなど)も、重複に見えます。消す前に「比べる」で確かめてください。
- 知覚ハッシュは、埋め込みを計算するときにいっしょに作ります。この機能より前に計算した画像の分は、worker が手の空いたときに少しずつ作ります。まだハッシュが無い画像は、CLIP の類似度だけで判定し、一覧に「簡易」の印を付けます(色違いなどの別の画像が入ることがあります)。
- 比べるのは新しい順に 5000 枚まで、表示するのは大きい順に 100 グループまでです。
- **自動では消しません。** 要らない画像は、その場の「削除」で消します。削除は通常の論理削除で、「元に戻す」で戻せます。

## マップ

上部のメニュー(「生成」「履歴」「マップ」)の「マップ」(`/map`)で開きます。埋め込みを計算した画像だけが並びます。開くとネットワークが出て、「地図」のタブ(`/map?view=map`)に切り替えられます。

- **ネットワーク:** 画像を点にし、各画像の近傍のうち類似度がしきい値(既定 0.8)以上のものを線にして、力学モデルで並べます。線が多すぎるときは、類似度の高い 40000 本までを描きます。「系列の辺を重ねる」で、どの画像から作ったか(主たる親)の線も重ねられます。
- **地図:** 似た画像が近くに集まるように、サムネイルを 2D に並べます。配置は UMAP で、ブラウザの中で計算します(サーバーは各画像の近傍だけを返します)。同じ画像と設定なら、毎回同じ配置になります。枚数が多いと時間がかかります(Raspberry Pi 5 の Node.js で 2000 枚 約 7 秒。途中の配置を描きながら進めます)。4 枚未満では作りません。
- **絞り込み:** グループ、タグ(複数を選ぶと、すべてのタグが付いた画像に絞ります)、上限(500 / 1000 / 2000 / 5000 枚。既定 1000)、近傍の数(5〜30。既定 10)。上限を超えると新しい画像から並べるので、全体を見たいときはグループやタグで絞ります。しきい値、系列の辺、選んだ画像も含め、表示の状態は URL に残ります。
- タブ、近傍の数、上限、しきい値、系列の辺は、ブラウザごとに覚えます(次に `/map` を開いたときに使います。URL に値があれば URL を優先します)。グループ、タグ、選んだ画像は覚えません。覚えた値は、設定の「表示」→「ブラウザに保存した設定」→「まとめて消す」で既定に戻せます。
- パン、ズーム、タップで選べます。選んだ画像のカードから、系列グラフと「似た画像を検索で見る」に移れます。カードの画像を押すと、ビューアで開きます。
- カードの「↗」で、マップの右側(狭い画面では下)に詳細のパネルを開きます。大きめのプレビューと画像の情報(種類、寸法、形式、サイズ、作成日時、タグ、プロンプト)を出します。読むだけで、編集はビューアで行います。一度開くと、別の画像を選んでもパネルで表示し、次にマップを開いたときもパネルで表示します(ブラウザに覚えます)。「↙」か Esc で小さなカードに戻すと、次からはカードで表示します。もう一度 Esc を押すと選択を外します。
- 「系列の辺を重ねる」の線は、親から子への向きで、子の側に矢じりを付けます。
- マップを開いている間は、右のサイドパネルを畳みます。離れると元のパネルに戻ります。マップの上でアイコンレールから開けば、そのときだけ出ます。

## 検索の方式(numpy と pgvector)

近傍の検索は、DB によって2つの方式があります。どちらも結果は同じです。

| DB | 方式 | 内容 |
|---|---|---|
| SQLite(既定) | numpy | 使うモデルのベクトルをメモリに持ち、全件と比べる。個人の規模(数万枚)なら十分速い |
| PostgreSQL + 拡張 `vector` | pgvector | DB の索引(HNSW)で探す |
| PostgreSQL(拡張なし) | numpy | SQLite と同じ |

- 方式は起動時に決まり、画面には出しません。`GET /api/settings/embeddings`(または `GET /api/capabilities` の `embeddings`)の `index_backend`(`pgvector` か `numpy`)で確かめられます。
- ベクトル自体は、どちらの方式でも DB(`asset_embedding`)に保存します。バックアップは DB を取れば足ります。モデルのファイル(`DATA_DIR/models/clip/`)はダウンロードし直せます。
- pgvector の入れ方、Compose のイメージ(`pgvector/pgvector:pg17`)、後から拡張を入れたときの扱いは [postgresql.md](postgresql.md) の「pgvector」にあります。`migrate_to_postgres` は埋め込みも移します。

## MCP

MCP サーバー(ADR-0023)では、`search_assets` の `mode="semantic"` で文章での検索を、`find_similar_assets` で似た画像を使えます。使えるかは `get_capabilities` の `embeddings` で分かります。詳しくは [mcp.md](mcp.md) の「文章での検索と似た画像」にあります。

## うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| 「空きメモリが足りないため、埋め込みのモデル … を読み込みませんでした」 | 空きメモリが目安より少ない。小さいモデル(clip-vit-b32-u8)を選ぶか、メモリを増やす。WD Tagger と同時には読み込まないので、自動タグの一括実行と重ねても目安は増えない |
| 日本語で検索してもほとんど当たらない | 英語向けのモデル(clip-vit-b32-u8、clip-vit-b32、Infinity の openai/clip-vit-base-patch32)を使っている。英語で検索するか、ローカルの clip-japanese-base に切り替えて計算し直す |
| 「推論サーバーに接続できませんでした」 | 推論サーバーが止まっている、または Base URL が違う。GAKEI のマシンから Infinity の URL に届くか確かめる(Docker の中からは `127.0.0.1` ではなく `host.docker.internal` など) |
| 「推論サーバーがエラーを返しました(HTTP …)」 | モデル名が Infinity で動かしているものと違う、キーが違う、など。応答の本文の先頭が出るので、それを手がかりにする |
| 似た画像の欄に「計算中です」と出たまま | 前に多くの画像が待っている(一括実行の直後など)。設定画面の「待ち行列」の件数を見る。自動タグの一括実行と重なると、モデルを交互に読み込み直すので遅くなる |
| 検索の「意味」や似た画像の欄が出ない | 埋め込みが無効か、まだ使えない(モデルをダウンロードしていない、リモートの接続先かモデル名が無い)。この間に取り込んだ画像は計算しないので、使えるようになったら「まとめて計算する」 |
| 「失敗」の件数が増える | 失敗は自動では再試行しない。原因を直してから「まとめて計算する」(失敗したものも入る)か、ビューアで「計算し直す」 |
| 「モデル … のファイルを読み込めませんでした」 | ダウンロードしたファイルが壊れている。設定画面でモデルを削除し、ダウンロードし直す |
| マップや重複の候補に一部の画像しか出ない | 上限(マップは選んだ枚数、重複の候補は 5000 枚)を超えると新しい画像から使う。絞り込むか上限を上げる。ベクトルが無い画像は出ない |
